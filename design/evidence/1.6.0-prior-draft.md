# ruan-project2doc 1.6.0 设计文档

编写日期：2026-11-11。本文是可独立交付给下一开发会话的完整设计，不是 Skill 本体。

`draft` 仅表示尚未得到用户对本份设计的确认，不表示正文仍有待补章节。依据仓库 `AGENTS.md`，确认后才能改为 `approved` 并成为开发目标；不能因为收到设计任务就自行批准设计。设计编制阶段仅新增设计资料；设计获批后的实现会话按本文第 11–13 章修改和验证 Skill，不修改历史设计或覆盖用户样本。

## 1. 产品目标与设计依据

### 1.1 交付什么

读取一个软件项目的全仓库源码，生成一套中文系统学习笔记：00 系统总览与阅读路线、链路篇与机制专题篇、99 复核说明，以及修改提示词文档。读者会写一般业务代码，能读懂源码，知道常见技术名词，但不了解本项目的业务，也未必理解相关机制怎样配合。

读者应当先理解系统在解决什么问题、由哪些部分协作、关键对象怎样变化，再理解每个重要机制的原理、实现、判断、失败行为和取舍。读完后既能复述完整过程，也能回答两三层技术追问。

**准确是底线，理解是目标，可读是手段，覆盖服从理解。** 通俗表达增加必要的关系与解释，不削弱事实、技术深度或结论的适用条件。覆盖服从理解是正文的组织原则：每个源码入口仍须有去向，重要机制、必要分支与异常不能以精简为由消失。

### 1.2 调查结论与证据边界

开发基线是本仓库 `src/ruan-project2doc/` 的 1.5.0；当前正式成品位于 `install/ruan-project2doc/`。调查时两者规范化内容一致，发布清单的设计及成品哈希均通过核验。

本次证据包括：1.4／1.5 设计、1.5 全部规则与模板及相关脚本和测试、历史表达要求、用户指定目录中的三个项目、另行定位的真实 1.5 EMG 实测材料。详细定位、采样范围与因果判断保存在 [1.6.0 调查依据](../evidence/1.6.0-analysis.md)。实施本设计不需要先重做该调查。

四项结论决定本版范围：

1. **现有生产框架成立。** 1.5 已提供理解稿、机制七问、流程六问、核心机制主讲篇与跨篇够用讲解、独立追问测试、源码抽查、表达校对，须完整继承。
2. **指定样本的有效规则存在版本差异。** `D:/AI workspace/claimYourPro/deepseek/ruan-project2doc/` 下的 nanyang、ruan-rag、EMG 归档任务包，规则、模板和工具与 1.4 发布内容一致；本机安装目录则为 1.5。它们反映真实阅读问题，但不能全部作为完整执行 1.5 的失败证据。当前有效任务包应被识别，安装版本不能代替这一事实。
3. **组织质量缺少足够具体的产出与检验。** 复杂篇章即使有总图、术语表、许多技术解释，仍可能让读者自己拼接参与方、执行边界和数据关系。1.5 的模板和追问更明确地约束了机制深度，尚未同样明确地检验整篇和复杂小节的组织。真实 1.5 EMG 笔记也提供了改进这一点的依据，而非只有旧任务包出现问题。
4. **错误由多种因素共同造成。** 旧规则把取证材料推入正文；执行中出现逐项检查通过但整体理解仍失败、校对期间正文变化等偏差；项目本身还存在多入口、多事务、生命周期管理和未接通适配器。不能把复杂性当作删细节的理由，也不能把所有问题归罪于规则。

### 1.3 本版范围与非目标

在现有规划、研读、成文、审读、收束和修改机制内完善组织与表达。工作集中于：系统总览、主题组织方式、章节职责、复杂子流程、术语与因果解释、图文一致性、整体理解验证，以及任务包实际版本辨识。

不重建编排系统，不增加一套独立写作流水线，不恢复百余项固定检查 ID，不按项目增加特殊规则。不按字数、标题数、图节点数或“AI 味词”数量判定文章质量。不强制所有主题变成线性执行流程。不把用户现有工程自动迁移到新版，不在设计阶段生成新版 Skill 或正式笔记。

### 1.4 触发与不适用

继续支持“把项目整理成学习笔记／业务文档／链路文档”“按主流程读懂仓库并写成能读下去的文档”“继续生成笔记”“按修改提示词修改第 N 篇”等原有入口。

单个函数或局部代码问答、建立 project-map、API／部署手册、需求分析、业务代码修改及没有执行链路的纯配置／纯文档仓库不进入本流程。库和 SDK 可以适用：公开调用、返回值、错误、回调与实例状态同样构成可讲解的执行关系。

## 2. 必须保留的能力与边界

以下是 1.6 的正式规则，不依赖阅读旧设计才能执行。

| 能力 | 完整要求 | 防止的退化 |
|---|---|---|
| 源码与 project-map 只读 | 所有输出放在独立笔记工程；不修改被分析仓库、map 状态或未决，不在其中运行写入命令 | 为写笔记顺手改业务代码或知识库 |

| 源码依据 | 写入正文的项目事实可追到理解稿及当前源码；不把测试存在当作运行通过 | 流畅叙事掩盖错误事实 |
| 实际调用核验 | 沿使用点确认配置、注册、调用分支、事务与异常捕获范围 | 组件有能力就声称当前业务已使用 |
| 理解稿 | 流程走查、机制卡、关键数据、追问答案、意图出处、核验材料和细节去向均保留 | 回到孤立的一行一条事实摘要 |
| 两类篇与机制分级 | 链路篇与机制专题篇并用；核心、支撑、细节分级；每个核心机制只有一个完整主讲篇 | 按目录堆篇、同一机制反复完整讲解 |
| 跨篇够用讲解 | 使用篇仍解释本流程中的问题、工作过程、失败行为，再说明主讲篇增加什么 | 一串参数加“见第 NN 篇” |

| 成文回读 | 可定点回读理解稿所指源码；新增事实先回写理解稿再成文；大缺口退回研读 | 成文无法补足理解，或凭记忆补事实 |
| 独立审读 | 每篇研读、成文、审读各为新会话步骤；审读首次作答仅接触正文与问题 | 作者用已有知识补齐文章没写出的部分 |
| G1–G6 | 仍为六道质量门；先检验理解，再核真，最后校对表达并复验 | 以 lint 或勾选清单替代阅读 |
| 编排职责 | ruan-dev-skills 2.0 管步骤、进度、恢复；本 Skill 不另建同类状态 | 双重进度和恢复口径 |
| 两个确认点 | 规划确认；每篇通过审读后确认。已有明确有效授权按其范围执行并记录，不重复索取 | 伪造确认或不顾已有授权反复停顿 |
| 修改机制 | 四区修改提示词文档、原位修改、用户有效例子保留、事实变化先核实 | 补丁堆积、把错误内容改名留下 |
| Git 边界 | 运行笔记任务时只提交笔记仓、不推送；资料仓由 dev-skills 管理。本 Skill 开发仓的提交与 Tag 按 AGENTS.md，须用户授权 | 混淆两个仓库的授权 |
| 技术栈中立 | 规则不假设 Java、Redis、MES、DAS 等存在；样例只说明讲解方式 | 为 nanyang 定制规则 |

Python 辅助脚本仍只用标准库，保留既有依赖要求与命令。正常长任务缺 Git 或 ruan-dev-skills 时说明缺项并停止，不自建替代；Python 或可选检查能力缺失时按既有人工检查路径如实记录，不能伪称脚本执行。缺少表达检查 Skill 时人工按表达规范检查，不因此取消质量门。

project-map 是导航材料。基准过期、挂未决或受限制的事实必须回源码核实；关键数据、状态变化和数字必须核实。其他借鉴事实按每个大步至少一处抽查，发现不一致即扩大到该模块其余借鉴事实。当前源码优先，不回改 map；无 map 时提示一次后按入口与终点发现继续，不降低准确性要求。

## 4. 组织：从系统地图到复杂小节

### 4.1 总览先提供可用的系统模型

00 在规划阶段即提供最低可用内容：谁使用系统、输入和产出是什么、系统内外有哪些参与方、哪些对象连接各模块，以及一两条代表性业务主线。已核实内容直接写；尚未研读的结论标为待补，不猜行为。

架构图说明组成与依赖，业务主线图说明数据与状态怎样走，阅读路线说明先读哪些文章。这三种关系不能混成一张带篇号的箭头图。必要时分图；简单系统可合图，但边的含义必须明确。

进入首篇成文前，本篇依赖的整体背景必须已经可用。不能把全部系统介绍推迟到最后收束。研读发现改变整体模型的事实时，在该篇相关范围内回填 00 的简述或图，不借此修改其他篇正文；大范围认知变化返回规划与编排。U-收束负责全套总览的一致性和完整性。

00 不承担逐个入口清点、配置穷举或证据陈列。尚未写完全部篇目时，不把规划清单或 00 骨架称为完成的全仓笔记。

### 4.2 篇目类型与组织方式分开判断

持久篇目类型仍只有“链路／专题”。在规划条目中补充一句“组织方式及理由”，不新建另一套篇型枚举、模板体系或进度状态。以下是可组合的组织方式，不是四种必填格式。

| 主题 | 主要组织依据 | 必须澄清的关系 |
|---|---|---|
| 一次业务或数据处理 | 发起到可观测结果的大阶段 | 每阶段输入、执行者、结果、交接；请求、线程、事务或进程何时改变 |
| 对象生命周期 | 建立、使用、变更、失效等状态与独立操作 | 谁在什么条件下触发；哪些操作可选、重复或互斥；不是每次都顺次发生 |
| 跨流程机制 | 共同问题、参与者与结构、关键操作及使用点 | 哪些能力由共用机制提供，哪些由调用方决定；适用与失败范围 |
| 架构或模块协作 | 职责与边界、关系、代表性协作过程 | 谁调用谁、交换什么、状态由谁管理；依赖关系不等于时间顺序 |

一篇可以包含“首次建立的一条流程＋后续生命周期分支”，也可以在专题中用代表性流程解释运行方式。切换组织依据时明说关系，例如“下面是凭据已经建立后，分别由业务请求和管理员操作触发的两类处理”。不能只因代码属于同一模块，就把管理动作、查询接口、初始化和异常恢复列为一串执行步骤。

入口是外部触发代码开始执行的位置；终点是可独立观察的响应、返回值、记录、状态、文件或消息；链路候选沿真实调用或交接追到这样的终点。候选按改变持久状态、跨系统交接、失败处理、可见结果、被其他链路依赖、用户点名六项辅助打分。默认每项一分：三分以上进入独立篇候选，一至两分优先并入相关篇或在 00 简述，零分优先登记不展开原因；数值可调整。成篇最终按学习价值、共同主题和复杂度判断。多个可观测终点可在同一生命周期或跨阶段业务篇中连讲，必须标清执行边界，不能因为多个终点就机械拆篇。

跨链路核心机制需要全貌、原理较多会长期打断链路，或用户点名时安排专题。只有一条使用路径且可就地讲清的核心机制留在链路篇。阅读顺序通常从代表性业务主线进入，再读相关机制，之后看其他链路；不强制先逐个读启动、配置、接口目录。

### 4.3 全篇先建立什么

篇首以普通语言回答：这是哪件事，为什么需要它，涉及谁与什么对象，怎样到达结果。对于复杂篇，先用一段连续概述或少量大阶段走完主题，再进入实现细节。保留原有“本篇回答”和前置关联；问题不是标题口号，要能在小结得到具体回答。

不要把“先讲整体”实施成一张涵盖所有字段、分支和错误码的大图。全貌必须能被直接复述；图表提供帮助，连续文字负责解释关系。必要条件在概述里保留，例如“当前仅模拟模式能完成以下登录链路”；不把完整的失败清单安排成读者看到的第一个处理阶段。

全篇可追踪一个业务对象、一组相互关联的对象或一次代表性操作。对象从一条记录变成另一条记录时必须说明对应关系，不能为维持“同一个对象贯穿全文”把临时凭据、业务身份和最终会话当成同一物。

### 4.4 章节应有职责，复杂小节也应先有骨架

每个主要章节承担一个明确问题或阶段。其起始说明读者现在在哪、拿到了什么、这一节要产生什么；纯结构主题则说明本节解释哪类职责或关系。可以用一句话自然完成，不机械复制“输入／处理／输出”标签。

在《_研读.md》中增设“讲述安排”，仅一处维护：

```markdown
## 讲述安排

组织方式与理由：……
读者先要建立的模型：……
贯穿对象／代表性场景及其事实边界：……

| 拟定章节 | 本节回答什么 | 与前后内容的关系 | 主要讲解及深入内容的安放 |
|---|---|---|---|
| …… | …… | 上一步产物／独立触发／共同依赖等 | 主干；就地展开；相关分支；留理解稿或99 |

复杂子流程：仅为确有多阶段、多执行者或多状态的部分列出内部步骤和出口。
```

这张表是把已有理解组织给读者的交接，不再复制机制卡、逐条事实或完整答案。简单章节不另写子表。成文时可以调整标题与位置，但要同步该安排；计划不能反过来限制已核实的实现。

复杂小节先走通内部过程，再展开其中的锁、哈希、字段、错误、配置和取舍。读者尚不知道一次登记怎样发生时，不能以“四组记录一起写完”代替过程，再让字段格式、版本号与异常码填满整节。

局部深入保留在相关步骤内；需要较长讲解时用有职责的下级标题，并在退出该层时明确当前产生的结果与下一步接手者。不存在统一的下沉层数或段落长度限制。若不断嵌套已掩盖主线，应先重组职责或拆出专题，不能仅继续增加标题。

### 4.5 内容怎样分层

| 内容 | 放置原则 |
|---|---|
| 决定主要结果的动作、关键分支与不可省前提 | 主干就地讲清；把它折叠后会形成错误模型，就不应作为可跳过补充 |
| 解释当前步骤的机制、原理与实现 | 紧邻步骤，按需要下级展开；深入结束后接回明确的结果 |
| 可选操作、独立管理入口、查询面 | 先标触发条件和与主对象的关系，再单独组织，不能冒充必经步骤 |
| 多处共用机制 | 在首个有必要的使用点给够用讲解，在主讲篇完整讲；不在业务故事开始前列全部中间件和门禁 |
| 次要异常、并发细节、设计取舍、版本演进、当前局限 | 与所解释步骤相邻，用现有稳定标签或下级标题区分；不是所有失败都必须下沉 |
| 核验过程与无助理解的实现清单 | 理解稿或 99；正文按学习目标保留必要结论 |

分类取决于本篇职责。专门解释重试的篇中，失败与恢复是主干；生命周期篇中撤销可以是主要章节；架构篇可以按职责组织。不能用“异常必须弱化”或“正文必须全部按执行顺序”覆盖这些情况。

### 4.6 标题、图和正文共同表达同一个模型

标题须概括到下一个同级标题之间的主要内容。同级标题遵循同一划分依据；改变依据时有上位分组或清楚的关系说明。优先命名业务动作、阶段、状态或机制职责，避免直接用局部结论、字段数量或实现手段充当上位主题。

“为什么”标题可以用于真实的解释问题，不实行词语禁用。表格适合比较、状态转换或数据对应；不能用参数表、接口表代替过程讲解。声明 N 步、N 层后，正文逐项对应，分支与子步骤不得抢占主序号。

检验时分别阅读目录和主要节首，观察能否恢复文章模型；再回读章节内容，检查标题承诺是否实际兑现。不能仅通过换标题、添加开场白或给旧图补图例就判定结构修复。

## 5. 讲解深度、数据与准确性

### 5.1 机制七问与流程六问

机制七问是内容完整性要求，不是正文必须照抄的七个标题：

1. 没有它，在什么具体场景会发生什么问题。
2. 它依靠什么原理起作用，解释到足够理解当前实现。
3. 本项目用了什么结构，按什么顺序执行，哪些参与者如何配合。
4. 关键判断保护什么条件，不同分支分别去哪里。
5. 校验、依赖或并发失败时，谁处理、留下什么、调用方看到什么。
6. 与更简单或常见做法相比，有什么效果和代价。
7. 在什么条件下不成立或能力受限。

核心机制的主讲篇完整回答七问；支撑机制与其他篇使用的核心机制至少回答问题、实现、失败三问，通常需要若干连贯段落。篇幅由理解需要决定；不能把旧版“两到六段”的参考值当作硬上限。确实不适用时记录原因；没查清不能写成不适用。

流程六问是：谁从何处发起；哪些校验拦什么；各环节处理什么；在哪里依据什么分叉；哪些数据或状态落到何处；谁在同一次或另一次执行中接手。主流程、关键子流程及影响结果的分支都应可按这些问题走查。原理和方案对比挂在需要它的步骤或专题中，不形成脱离项目的教材。

### 5.2 数据模型讲到能够解释行为

对决定分支、身份、权限、幂等、持久结果、跨组件交接和最终计算的数据，讲清：谁创建、保存在哪、怎样传递、谁读取或校验、如何改变、何时失效。外部数据追到责任方和当前接收点，不猜外部内部实现。

当多份记录容易混淆时，先说明它们各代表什么，再给必要的表名、关键字段与关联关系。例如“一次登录尝试”“本地员工绑定”“已建立的会话”是不同对象，不能统称“一行身份记录”。数据模型可用小表或关系图辅助，但不要求列出全库字段。

以下实现细节在影响理解时必须保留：

- 创建与使用发生在不同请求时，数据通过什么记录、令牌、消息或文件关联。
- 哪些写入在同一事务内，提交后谁能看到；失败是否回滚全部动作，哪些外部副作用不会一起回滚。
- 状态迁移的触发者、条件与结果；记录过期不等于自动删除。
- 并发时锁住什么对象、解决什么竞争；声明“唯一”“只执行一次”“立即生效”前核实其作用范围。
- 同名概念是否指不同对象，同一对象是否有多个叫法；避免“版本”“快照”“凭据”混用。

### 5.3 事实、机制解释与示意场景

理解稿区分下列内容，正文用自然语言保留会影响认知的区别，不给每句贴分类标签：

| 内容 | 可以怎样陈述 | 不可以怎样陈述 |
|---|---|---|
| 当前项目行为 | 有源码及实际调用依据，写明成立条件 | 把未接通适配器、默认关闭功能或其他路径的能力写成当前保证 |
| 通用原理／协议机制 | 明确这是理解项目所需的背景；与当前实现分别对应 | 把通用标准的完整流程补画成当前实现 |
| 效果型解释 | 从已核实行为说明效果及前提，如先拒绝无效输入会减少后续工作 | 把可能效果夸大为无条件保证 |
| 对比型解释 | 比较另一种做法的行为与成本，明确是假设比较 | 把备选方案写成项目已有功能或确定的历史选择 |
| 作者意图与历史原因 | 有注释、提交、设计资料等出处才陈述 | 从“这样有好处”推断作者经历、现场需求或历史事故 |
| 教学示例 | 使用虚构人物、编号或输入值走查已核实规则，明确“假设／示意” | 把示例值写成生产参数、把模拟运行写成真实实测 |

涉及标准协议或框架行为且不能由仓内材料确认时，后续实施者应查与所用版本对应的官方文档、标准或框架源码，依据留在理解稿。普通笔记不要求普遍增加联网步骤；未经核实的外部机制不得填补项目事实缺口。

真实系统未接通某外部能力时，仍可以解释职责和概念场景，但须在使用前说明其性质，并明确当前路径实际停在哪里。图中的模拟路径、当前实现和概念示意分别标明，不能到篇尾才补一句“实际没实现”。

### 5.4 技术材料的去向

默认不进入正文的材料：文件路径加行号、方法签名清单、测试名称及“本次是否运行”、迁移号罗列、内部来源编号、核验过程、与当前理解无关的部署未知。它们保留在理解稿或 99。篇尾代码地图只列关键文件／类及职责，通常不带行号；少数立即跳转有助理解的位置可以例外并说明理由。

不确定性若会改变读者对行为的理解，必须在相关位置说明，例如“只能确认这里向外抛出异常，最终响应还受容器处理影响”。不能为了干净，把重要未知藏入 99；也不在主文反复讲作者如何调查。

代码片段只在比自然语言更直接时使用，如关键配置、短算法或状态表达；先讲含义，去掉片段仍能读懂。沿用约 15 行／段、约 5 段／篇的可调整参考值，不贴整个类或方法。笔记与理解稿不设字数上限，也不设长度比例。

## 6. 措辞：让读者理解具体动作与因果

表达规范仍集中于一个文件，整合为少量可执行要求，不另加独立风格手册。成文和审读使用同一份规则。

### 6.1 先说对象与行为，再放名称

首次真正使用陌生概念时，说明它是什么、在当前场景做什么、与已知对象什么关系。只翻译缩写不等于解释。例如“幂等键”应说明调用方用它识别重复请求及相同键不同内容的处理，不能只写“幂等键用于幂等”。

确需对应代码时，采用“直观叫法（原始名称）”，之后优先直观叫法。源码名用于定位、区分相似对象或保留准确含义；不要求删去所有英文、字段或表名。把代码名遮掉后，读者仍应知道发生了什么。

术语表统一跨篇叫法、别名与易混淆对象；不替代就地解释，也不收录每个标识符。正文前置的小表仅放理解当前模型必需的对象，不先交给读者几十行名称与实现落点。

### 6.2 把抽象动作展开到可复述

对重要动作检查执行者、对象、条件、实际操作与结果。缺什么补什么，不要求每句话机械填满五个槽位。以下是写法示意，不是项目事实或固定句式：

| 容易遮住过程的写法 | 有效展开的方向 |
|---|---|
| “服务负责处理回执” | 谁收到回执，用什么标识找到待处理记录，校验什么，最后把状态改成什么 |
| “进行校验” | 比较哪两个值，为什么比较，不一致时由谁拒绝、是否已经写入数据 |
| “建立关联” | 哪两种记录，用哪项身份对应，关联保存在哪里，下游怎样使用 |
| “完成收口” | 谁获得什么结果，把哪条记录置为什么状态，后续能否重试 |
| “冻结上下文” | 把哪些当时的值复制到哪份记录，后续为何读取这份副本而非现值 |
| “转交 owner” | 哪个业务服务接到什么命令，负责什么业务判断和持久化 |

不是对这些词一律替换。读者已经理解的业务术语可以沿用；缺过程时不能仅换成另一个抽象词。

### 6.3 因果解释按真实需要出现

通常按“是什么／解决什么问题 → 为什么需要 → 怎样执行 → 关键实现、失败与取舍”展开。这里描述认知顺序，不要求每节都有四个固定标题，也不要求每条显然的赋值都附一段动机。

关键判断要解释它防止的具体坏结果；顺序有作用就说明作用；方案取舍写出代价。无法证明历史动机时改讲效果或比较，不通过增加【推导】标签来给猜测通行证。正文也不写“这是效果型解释，不是作者意图”这类内部分类说明，除非确实需要澄清一个读者误解。

句子压缩导致执行者切换、多个时间点和因果混在一起时，拆成连续的两三句。保持主语和对象稳定，用上一动作留下的结果接下一动作，不用“进一步实现有效闭环”这样的空转场。

### 6.4 保留准确性与教学价值

保留有帮助的小场景、具体数字、失败例子、必要前提和用户自己的有效解释。重要结论可加粗或提示，每个一级节通常不超过约三处；不要重复强调。类比必须对应实际机制，不能把“锁”“凭据”“快照”变成模糊的票据故事。

删除重复、无信息转场、装饰性词语与修改痕迹。正常最终正文不出现“修正后”“重新核验发现”“此前有误”；原处改正，过程写变更记录。错误分支彻底移除，不换一种限制说明继续保留。

表达修改不得改变数字、条件、先后、执行范围、失败行为或结论强度。不能把“尝试”“某条路径”“可能”润色成“保证”“所有”“一定”。

## 7. 图示与关系核对

保留 Mermaid 图的能力。图的选择依据它要回答的问题：架构图表达组成和依赖，时序图表达跨参与方的往返，流程图表达动作及条件分支，状态图表达生命周期。无需每篇集齐图种，也不新增固定绘图工具链。

每张图先确定层级和问题。全景图承载主要参与者、阶段、关键结果与必要分支；复杂局部另画细图。不能让一张图兼任接口目录、字段清单、运行配置和全部失败路径。

实际核对以下内容：

- 箭头到底表示执行先后、调用、数据交接、依赖、状态迁移还是阅读指引；不同含义在必要处标明。
- 异步接收与后台处理有数据依赖，不因此保证“HTTP 响应已经返回，后台才启动”。无明确时序依据不能增加先后保证。
- 独立健康检查、每请求认证、管理员操作、重试和回调，不能被画成首次建立流程必经的下一步。
- 判断节点、分支标签、执行者和结果与正文一致；图例说有菱形，图中就必须确实存在对应判断结构。
- 当前实现、模拟实现和概念示意不混为一个真实调用路径。

审读者要逐条解释关键箭头的含义，并用正文和理解稿核对。只加“图中有四类关系”的统一说明而不修改错误连线，不算通过。渲染成功只能证明语法可用；若实施环境有可用的 Mermaid 渲染器，应实际渲染修改过的图并检查可读性。无渲染能力时如实记录人工语法与关系核对，不声称已做视觉验证。

## 8. 生产流程与交接

### 8.1 开工与有效规则识别

先确认源码位置与基准（默认 HEAD）、输出位置和用户重点，已有信息直接沿用。运行依赖检查与只读勘察。多个独立项目分别建范围，不能把一个样本父目录当作单一项目。

新任务使用本次 Skill 的规则与模板副本。继续任务以当前步骤引用的归档需求包为有效规则来源；升级本机 Skill 不会自动升级已归档材料。在任务说明中记录 Skill 版本、生成来源、生成日期；在勘察结果或步骤执行说明中记下实际使用的归档 P-ID／路径与版本。只保留必要文本字段，不新增版本数据库、锁或后台同步。

遇到旧包、混合文件或无法确定版本时，列明事实。用户只是继续旧任务且未要求升级，可以继续使用该任务的既定规则，不能称为已使用 1.6。用户明确要求升级或生成 1.6 结果时，必须形成新的需求包，经 dev-skills 调整后执行；不得用新安装版本覆盖旧归档，也不得只改版本字符串。相关处理见第 10 节。

### 8.2 U-规划

保留链路候选、辅助打分、机制清单与分级、主讲篇、范围和去向、学习目标、阅读顺序、追问清单与入口去向。每篇补“组织方式及理由”，指明主要对象及容易混淆的关系，不在此提前写完整正文。

追问既覆盖机制深度，也覆盖整篇关系。除 L1–L5 外，将整体复述、关键子流程与项目特有的易误解关系设为必答题。题目问结果，不把正确阶段、对象关系或答案顺序写进题干。

00 提供最低可用模型；术语表和衔接约定记必要叫法和真实交接。阅读相邻不等于业务相邻。核心机制使用篇须明确需就地解释的内容。展示规划并取得或核对已有有效授权后，才进入交接。

### 8.3 交接编排

填好 `00-任务说明.md`、确认后的 `01-规划方案.md` 和 `02-步骤拆分要求.md`，复制对应版本规则、模板和工具。需求源在资料仓之外，不夹带敏感内容、空目录或符号链接。工程根不建 Git 仓。

以笔记仓为 dev-skills 的代码仓，初始化或调整资料仓至可接力。S001 记录笔记仓基线与源码基准，不虚构业务构建结果。每篇仍为研读、成文、审读三个新会话步骤，按确认阅读顺序安排。审读步骤完成后的动作是等待该篇确认；已有授权按范围记录。首次正常调用至交接完成即结束。

### 8.4 U-研读

按本篇范围沿源码弄懂行为，记录实际调用和跨次执行，保留完整理解稿。把相互独立的流程、生命周期操作和共同机制先分清，再决定怎样讲。

完成“讲述安排”：从已经核实的内容提炼整篇骨架、章节职责和复杂子流程；分配主干、深入、分支与核验材料的位置。建立必要术语和关键数据对应；用小场景检查状态、输入输出和失败结果能否一致走通。

继续回答机制七问／支撑三问及全部规划追问；新发现的关键问题回写规划。每个项目事实有来源，意图型解释有出处；未知保留边界。理解稿的完成条件是下一位作者无需重新探索大段源码，就能解释整体及细节，不以写满模板为准。

单元读入原始材料加产出默认不超过可用上下文的一半，可调整。容纳不下时按语义调整篇目或拆出机制专题并交编排处理，不能少读关键代码或随意拆出前半篇／后半篇。

### 8.5 U-成文

输入本篇规划条目、理解稿、必要的 00 背景、术语与衔接、讲解和表达规范及对应篇模板。不读其他篇正文；需借用机制时读其理解稿相关机制卡。00 是系统背景材料，不作为其他篇事实的替代来源。

先形成可连读的大阶段和节首，再展开对应细节；不把理解稿的机制卡目录原样搬进正文。复杂小节也执行同样判断。图与正文共同核对执行关系；变更标题时检查内容范围。

新事实定点回源码，先回写理解稿再写正文；大范围缺口退回研读。成文后仍自查 G2、G3、G5，另外按第 4 章做目录／节首及复杂小节走查，结果记在理解稿的成文自查中。自查不是独立 G1 的替代。

### 8.6 U-审读

仍为三轮，结果集中在一份 `_审读记录/NN.md`。

**第一轮：只凭正文建立模型并作答（G1）。** 使用固定正文版本，由未参与研读／成文的新会话读者完成。先看正文，作整体复述并指出看不懂的关系；再回答局部追问。此时不提供理解稿、预设答案、正确提纲、此前审读结论或源码。可以回看正文，不是背诵记忆测试。保存原始回答后，核对阶段才看理解稿与源码。

**第二轮：核实答案与事实（G4，复查 G2／G3／G5）。** 对照源码确认读者复述是否正确，有没有凭常识补出文章未提供的关系。对关键断言抽查；核对图文、术语、同一对象前后的状态和生成时机。发现共享前提错误，扩大到受影响的解释和图，不只改最初命中的一句。

**第三轮：结构与措辞校对（G6）。** 先查章节职责、标题层级、主要段落和深入部分的位置，再查句子、术语与因果。最后使用可用的“说人话”类 Skill；无该能力则如实人工检查。结构已在第一轮阻碍理解时应先记录，不能拖到最后仅润色。

表达和不改变含义的结构问题可直接改。需要新事实的小缺口先回源码并更新理解稿；大缺口退回研读并由 dev-skills 新增步骤。初次作答期间不得继续修改同一正文；修订后冻结新版本并复验受影响题目。整体骨架改变时，要重新做整体复述和受影响子流程检查；首次通过与复验通过分开保留。

### 8.7 U-收束与恢复

回填完整 00、99 和修改提示词文档，检查术语、数字、核心机制主讲与使用篇、真实交接及全仓入口去向。收束只修改 00、99 和各篇篇首篇尾衔接；正文机制问题登记并返回对应步骤，不在收束中暗改。

问题台账不得遗留未处理的 open；`needs_user_decision` 项写清影响与确认结果，不能以改状态逃避验收。阶段性产出明确已完成篇目，不因其余篇未生成而伪造最终通过。

恢复时读 dev-skills 当前步骤及其实际归档规则，再加载所需交接物。源码基准改变，列受影响篇目，先更新理解稿、术语与衔接、必要规划，再经编排重新成文和审读；不混用不同基准的事实。

## 9. 六道质量门与失败处理

### 9.1 G1：整体理解与深层追问

G1 的结果包含两种互补证据，不增加新的质量门编号。

| 检查 | 读者实际做什么 | 通过条件 |
|---|---|---|
| 整体复述 | 不给正确提纲，说明本篇解决的问题、主要参与方／对象、主要阶段或组织关系、关键结果和交接 | 重要关系完整正确；未把独立动作串成必经流程，未混同数据对象或实现边界 |
| 复杂章节／子流程复述 | 对本篇涉及多参与方、多状态或明显嵌套的关键部分，解释输入、处理、结果及其与全篇关系 | 不依靠作者答案补出必要关系；没有显著缺口。简单篇可记录无此类子流程及理由 |
| L1–L5 机制追问 | 回答是什么、怎样实现、为什么、失败怎么办、为什么不用别的 | 核心题全部答得出且正确；非核心题沿用至少 80% 的默认参考门槛 |

每个核心机制在主讲篇覆盖 L1–L5，每个支撑机制至少 L2／L4，关键判断至少 L3；跨篇使用核心机制的问题聚焦本篇必需理解的部分，不要求使用篇回答专题所有细节。用户指定问题全部纳入。一个问题可覆盖多个要求，不能为凑层次重复出题。

整体模型、关键子流程、重要前提和会改变结果的事实题标为必答。用户明确列为验收必答的问题同样如此。**必答题与核心机制题全部通过**；80% 不能抵消错误主线、错误状态、假的同步关系或未经核实的实现保证。非核心未通过项仍需说明修复或不阻塞的理由。

判定使用“答得出／部分／答不出”，正确性独立核对。答案虽正确但来自读者外部知识，正文没有对应信息，仍算文章缺口。出处仅有名词或参数、实际关系靠读者补出的，不算充分支持。

审读记录须有：正文版本、独立读者标识、实际输入范围；整体原始复述；逐题原答案、判定、正文出处与核对依据；缺口和复验。机制答案都正确但读者无法还原整体时，G1 仍不通过。

### 9.2 G2：机制完整且位置合理

逐机制对应七问或够用三问的正文位置。信息存在但散落得无法组成机制，也应记录组织问题，不靠搜索词句自动放行。不适用有理由，没查清退回研读。

### 9.3 G3：过程、数据与图文关系一致

沿流程六问正向走查，再从结果反查关键数据。按本篇组织方式区分顺序、调用、依赖、独立触发和状态迁移。核对目录、节首、主图、正文、小结描述的参与方、条件、对象和结果是否一致。

至少覆盖实际存在的跨请求／线程／事务／进程边界及容易混淆的对象。不要求技术栈中不存在的维度。记录检查对象与具体结论，不只写“主线清楚”。关系核对是语义工作，脚本不能判定。

### 9.4 G4：事实与结论强度准确

正文事实对应理解稿及源码；作者意图有出处。每个大步至少抽查一项关键断言，专题则按主要操作／机制单元抽查；数量是下限参考，关键生成时机、实际接线、事务与失败范围、跨组件交接和重要数字必须优先覆盖。发现错误扩大检查共享前提的内容。

主文、图、小结对同一事实发生冲突时不能各自通过。先修理解稿，再修全部受影响表达和追问答案。未知保留范围，不能把设计预期、协议示意或 Mock 行为写成已实现能力。

### 9.5 G5：正文服务讲解

保留现有 lint 候选与人工检查：行号、测试名、取证过程、迁移号堆列、解释标签过密、事实堆叠、一句话机制、指路代讲、补充压过主干。约四句事实堆叠、约五处标签等仍只是提醒，不是硬性扣分公式。

进一步人工检查：是否用业务词包装了内部取证过程；是否只增加定义、图例或括注却没有交代操作关系；是否删掉代码名后仍无法知道动作。无 lint 命中不能证明通过，业务审计与关联证据不按关键词一律删除。

### 9.6 G6：结构与措辞可读

结构检查：目录与内容对应、同级分类稳定、关键步骤完整、复杂小节先有过程、深入结束能接回主线、正文与补充有合理层级。措辞检查：执行者和对象明确、术语首次解释、因果具体、源码名不代替讲解、时序清楚、无无用重复和修改痕迹。

记录实际问题和修改位置，以及未修改候选的理由。不要用“已运行风格 Skill”替代 G6；风格检查不能改变事实和技术边界。

### 9.7 处理与冲突取舍

| 问题 | 处理 |
|---|---|
| P0 错误事实或虚假保证 | 回源码，修理解稿与全部相关正文／图／答案，复验；不通过不得交付 |
| P1 重要模型、主线、机制或关系缺口 | 已有事实足够则重组补讲；依据不足退回研读；整体结构调整后重新整体复述 |
| P2 局部表达问题 | 原位改写，检查原义和受影响追问 |
| 只有个人措辞偏好 | 可保留，不通过无限润色制造新事实或无关扩写 |

深度与准确冲突时先核实；确认不了讲到已确认处。理解与精简冲突时删重复而非删解释。主线与深入冲突时改变位置、层级或篇目，而非牺牲七问。跨篇重复允许够用部分。用户要求优先，偏离固定规范的事实及理由记录到修改记录。任何门失败都必须指出返工单元，不以平均分或其他门通过抵消。
