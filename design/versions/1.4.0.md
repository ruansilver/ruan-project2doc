## 1. 定位

**做什么**：读一个项目仓库的全量源码，在仓库同级目录生成一套中文笔记，并为这套笔记配一份修改提示词文档。笔记按项目的关键链路拆成多篇，每篇以一条主流程为主干，忠于源码，同时读得顺。用户读完以后，在修改提示词文档里增删要求，AI 据此修改一篇或多篇笔记。

**触发场景**（用于写 description）：
- "把这个项目整理成学习笔记 / 业务文档 / 链路文档"；
- "按主流程读懂这个仓库并写成能读下去的文档"；
- 已有本 skill 产出的笔记，用户说"按修改提示词改一下第 N 篇""我在修改提示词里加了要求"；
- 中断后说"继续生成笔记"。

**不适用**：
- 单个函数或类的解释、局部代码问答（直接回答就够了，不必建立整套笔记）；
- 建立带闸门与验收的执行流程知识库，这是 reader 的职责；
- API 参考手册、部署手册、需求文档；
- 修改业务代码；
- 没有源码只有需求的分析；
- 没有"执行链路"的仓库：纯配置或基础设施即代码仓库、纯文档仓库等（决策 D20）。skill 只在开工时识别并说明不适用，不为这类仓库设计任何降级处理，以保持 skill 简单。

### 1.1 通用性原则（决策 D19）

本 skill 面向任意项目，不面向本设计里出现过的任何具体项目。它的能力来自 skill 自身的规则和清单，不来自对某几个项目的预先了解。

| 材料 | 在本设计中的身份 | 不能用来做什么 |
|---|---|---|
| 标杆 10.4 笔记、B 文档、起步提示词、二轮深审 | 提炼写作规律和问题类型的**来源**；附录 A、B 里真实例句的出处 | 不能当作领域知识。skill 运行时不能假设目标项目里有上传、Outbox、Redis、MinIO 这些东西 |
| 三个样本项目（第 12 章） | **验证样本**：检验规则在不同形态的项目上是否成立；测试用例的取材 | 不能成为规则本身。规则中不能出现只对它们成立的条件或数字 |

由此得出三条写法要求，适用于本设计和将来的 references：
1. **规则用技术栈中立的词来写**：入口、终点、状态、跨系统交接。具体技术只放在附录 G 的映射表里，并且只作为发现线索。
2. **从样本得出的数字一律标"默认值，可后改"**，例如"约 15 步""约 60 条"，并写明它们是从哪个样本估出来的。
3. **示例分两类**：真实例句保留出处，用来说明问题长什么样；操作化定义的示例用通用场景（附录 F）。skill 运行时写进笔记的例子，必须来自目标项目自己的代码。

**目标读者**（决策 D17）：有一般软件工程基础，但不熟悉本项目的开发者。操作化定义见附录 F 的 K13。面试视角不是默认内容，用户可以在修改提示词文档里选择加上。

## 2. 与 ruan-project-reader 的关系

前提（用户已定）：有 project-map 时优先借鉴，没有时不强求。两条路径产出的笔记，质量标准和格式完全一致，区别只在取证成本。

### 2.1 project-map 能提供什么、不能提供什么

依据：reader 的 `SKILL.md`、`references/check-format.md`、`references/completion.md`、`templates/module.md`。

| 能提供（事实骨架） | 不能提供 |
|---|---|
| 入口序号 E#、汇点序号 S#（`COVERAGE.md`） | 按读者节奏切分的篇目（它的模块按执行职责划分，粒度常常比一篇笔记大） |
| 按执行职责划分的模块，以及总览里的主体流程 | 叙事：动机、"防的是什么"、由浅入深的顺序 |
| 节点级源码依据（`必要规则与源码依据` 节） | 设计原因（reader 规定没有证据的动机只能标推断） |
| 候选处置：本文已解释 / 模块引用 / 外部边界 / 琐碎 / 待核实 / 阻塞 | 源码事实正确性的保证：check 只核对记录格式与一致性（check-format.md 第 62 行） |
| `## 未决` 表：待核实 / 阻塞 / 限制 | 当前源码的时效性：map 绑定某个基准提交 |
| 源码基准提交号、扫描方法、未检查区域 | |

**不借鉴的内容**：Mermaid 执行图的形式、逐节点约 20 字短注、候选表、闸门表、验收记录。笔记的图按第 4 章另画，只画读者需要的主干，不追求节点完备。

### 2.2 检测：有没有、完不完整、过没过期

开工时按顺序做，结果写进 `笔记/_工作区/_勘察结果.md`，并报告给用户，不需要用户回答：

1. **找位置**：先找 `<仓库>/project-map/`，再找仓库的同级目录和父目录（三个样本都在 `项目目录/project-map/`，跟仓库同级）。找不到就走 2.7 的自带路径。
2. **读状态**：读 `STATE.md` 里的九项统计，读每个模块的 `状态：`、`限制：` 两行，读 `COVERAGE.md` 的"本轮发现暂时收敛 / 整体完成"。
3. **机械检查**：如有 Python 3.10+，运行 `check.py <map>`（只读）。退出码 0、1、2 原样记录，**不因为 1 就放弃借鉴**，失败项只降低相关模块的信任。
4. **比对基准**：从 `COVERAGE.md` 或 `README.md` 读出源码基准提交号，和当前 HEAD 比较。不同就记下 `git diff --stat <基准> HEAD` 涉及的路径。

样本里的真实情况（2026-11-09 实测）：

| 项目 | 模块状态 | 限制=有 | 待办/阻塞 | check | 基准与当前 HEAD |
|---|---|---|---|---|---|
| RAG | 13 本层完成 | 1 | 174 / 0 | exit 0 | 基准 `7f70c578`，当前 `3d99d88c`，**落后 61 个提交，226 个文件有变化** |
| 河南中烟 | 19 本层完成 + 1 梳理中 | 0 | 247 / 0 | exit 0 | 一致（`dd7fb644`） |
| EMG | 8 本层完成 + 总览待验收 | 9/9 | 55 / 0 | **exit 1**（06 模块有一处相对链接目标不存在） | 与自身仓库一致（`a16c0a7`）；但同一系统的 10.4 目录版本更新，它的 02 模块里还写着分片响应带 `etag` |

三份 map 都是：已证叶子 0，召回探针未做，整体完成"否"。

### 2.3 信任分级（按单条事实，不按模块状态）——决策 D4

**理由**：三份样本里"已证叶子"都是 0，"本层完成"又常带着限制，按模块状态几乎分不出高低。所以分级落到"笔记里要写的这一条事实"上。

| 事实所处位置 | 怎么用 |
|---|---|
| 基准过期，且事实涉及的文件在 diff 路径中 | 只当线索，必须回当前源码重新核对后才能写 |
| 节点或候选挂着 `待核实` | 只当线索；核对后成立就写成事实，核不了就写成待核实（第 12 章写法） |
| 挂着 `阻塞`，或所在模块"限制=有" | 先读该模块的 `## 限制说明`、`## 未决`，弄清限制范围；范围内的内容按待核实对待 |
| 所在模块"梳理中"或"待验收" | 结构可以参考，事实全部回源码核对 |
| 所在模块"本层完成"或"已证叶子"，而且没挂未决 | 可以直接用，但仍要参加 2.4 的抽查 |
| check 失败牵涉的模块 | 失败项本身（例如断链）不影响源码事实时照常分级；影响时降一级 |

### 2.4 校验：回源码的核对策略——决策 D4

check 通过不代表源码事实正确，所以借鉴来的内容仍要回源码核对：

- **必须核对**：上表前三行的事实；写进本篇主流程的关键数据来源和状态变化（B §七）；所有数字（TTL、阈值、上限、步数）。
- **抽查**：其余借鉴来的事实，主流程的每一大步至少抽 1 处。
- **抽查不一致时**：说明这个模块不能整体信任，把该模块其余借鉴事实全部改为"必须核对"。

### 2.5 冲突：map 与当前源码不一致

以当前源码为准，正文直接写现状，不写"map 原来说……"。冲突登记进 `99-复核说明` 的"与 project-map 不一致"一节（写 map 的模块、节点 ID、map 原说法、当前事实、源码位置），交付时汇总告诉用户。**不修改 project-map**，是否回写由用户在 reader 那边决定。

### 2.6 依据来源记录

每篇笔记的证据索引按"来源"分组（详见第 12 章）：`源码直取` / `借鉴 project-map <模块文件>#<节点 ID>，已核对` / `借鉴 project-map，未核对（只作结构参考）`。这样以后修改时，能追溯到某条事实来自哪里。

### 2.7 没有 project-map 时的自带路径——决策 D9

1. 开工时提示一句："先跑 ruan-project-reader 可以降低取证成本，但不是必须的"。用户选继续，就不再提。
2. 轻量发现，借用 reader 的两个方向，但不做它的覆盖登记、闸门和验收：
   - 正向：路由、控制器、消息监听、定时任务、`main`、启动钩子、Worker；
   - 反向：写库、发消息、调外部接口、写对象存储，反查它们属于哪条流程；
   - 两边对照，得到主体流程候选清单，交给第 6.A 的"拆分方案"单元。
3. 证据纪律不变：正文区分已核实 / 推断 / 待核实；每篇都有证据索引，来源写"源码直取"；核对方式由抽样改为全量自查。

### 2.8 只读

本 skill 对 project-map 只读：不改状态、不补未决、不运行任何写入命令。check.py 只用不带写入参数的形式。

## 3. 输入与开工前确认——决策 D7

开工时一次问清，之后自主推进：

| 问题 | 默认值 | 说明 |
|---|---|---|
| 仓库路径与要分析的版本或分支 | 当前 HEAD | 范围固定为全仓库，这一项就是本次范围 |
| 输出目录 | 仓库同级 `<仓库名>-笔记工程/` | 结构见 4.1 |
| 你自己的重点或已知关键流程 | 可不填 | 填了就作为拆分方案的召回检查：方案里漏掉就要说明理由 |

自行检测、只报告不问的：project-map 是否存在、状态、基准是否过期（2.2）；ruan-dev-skills 是否已安装（未安装时的处理见第 14 章 Q-6）；仓库技术栈与规模。

**必停点**只有两类（理由：这两处返工代价最大）：拆分方案出来后确认一次；每篇完成后的用户确认（决策 D11，见 6.A.6）。

## 4. 产出物规格

### 4.1 目录结构（为适配 ruan-dev-skills 重新设计，决策 D10）

```
<仓库名>-笔记工程/                  仓库同级的普通目录
  笔记/                             笔记仓：独立 Git 根，dev-skills 眼中的"代码仓"
    00-总览与主线地图.md            读者入口：系统边界、篇目清单与衔接、术语表、跨篇机制归属、事实口径
    01-<链路标题>.md ... NN-<链路标题>.md
    99-复核说明.md                  依据汇总、未确认项、与文档/project-map 的冲突、要用户决策的点
    修改已有笔记-<仓库名>.md         修改提示词文档（第 9 章）
    _工作区/                        交接物，读者不用看（6.A.3）
  需求包/                           本 skill 生成的"笔记生成需求包"，交给 dev-skills 归档
  docs/AI dev docs/                 资料仓：独立 Git 根，由 dev-skills 管理
    <版本号>/                       例如 笔记v1：步骤总览、当前状态、开发协议、接力提示词、plans/ ……
```

**为什么这样摆**：
- dev-skills 要求版本目录位于 `<项目总目录>/docs/AI dev docs/<版本号>/`，资料仓是独立 Git 根，需求源不能放在资料仓里。三者并列在一个"笔记工程"目录下，就同时满足这些要求，也不在被分析的仓库里写任何东西。
- 笔记仓与资料仓分开，读者看到的笔记目录不会混进步骤和进度文件。

**未实测**：本轮没有实际运行 dev-skills，`check-root` 对"代码仓不是被分析的源码仓、而是笔记仓"这种用法是否有额外限制，需要在实现阶段用测试用例 T5 验证（第 13.6 节）。

文件名 `NN-标题.md`，标题写"对象 + 流程"（B §四.5）。依据：标杆就是 00 + 01..09 + 99 + 修改提示词这一套（决策 D3）。

### 4.2 一个项目对应几篇

不固定。由拆分方案按"每篇的终点是一个可观测状态"（决策 D2，定义见 K02）和拆篇信号（决策 D5，定义见 K18）来定。标杆是 4 条主线拆成 9 篇正文。

### 4.3 单篇结构模板

```
# NN · 标题
> 覆盖：起点（入口）→ 终点（一个可观测状态）
> 不覆盖：……（各写去向篇号）
一句话主线：用一个具体问题说出这篇要解决什么（例：01 第 6 行）
## 一、链路全貌
   全景 Mermaid 图（只画主干与关键分支）；角色、术语与落点表
## 二..N、按执行顺序展开主流程
   编号步骤；每步先写"做了什么"，再写"防的是什么 / 为什么在这个位置"
   需要时紧跟补充块：`补充说明` `并发情况` `异常情况` `当前限制` `版本差异` `测试证据`
## 本篇终点与下一篇的接口
## 证据索引（按来源分组，见 2.6）
```

**叙事规则**（从标杆提炼，正反例见第 7 章）：
- **主干**：一级、二级标题按执行顺序排，目录读下来就是流程（B §四.6）。
- 本节用到的概念以附录 F 为准：就地展开 K09、回到主线 K10、由浅入深 K11、像小说 K12。
- **就地展开**：遇到关键环节（例如 01 第 7 步"租约"），在该步内部讲清它，最多下沉一层；讲完下一个编号回到主线。展开的内容如果在别篇有归属，只讲本篇用到的部分（00 第六节"机制归属表"）。
- **回到主线**：补充块之后的下一句必须是主流程的下一个动作，不写"回到正题"之类的转场。
- **由浅入深**：开头先给一句话主线和全景图，再讲步骤，再在补充块里讲异常与边界，最后在终点小结点明重点。

### 4.4 笔记怎么落到源码位置

- 正文用"直观叫法（原始名称）"首次建立对应，之后用直观叫法（B §三.6）。
- 主线段落的源码名只用来定位；把它删掉以后句子仍能看懂（B §三.7，即可读性标准 2）。
- 精确位置（文件、方法、迁移号）集中放在证据索引；正文只在"读者可能要跳过去看"的地方点名。

## 5. 生成工作流

本章只给总流程和每一步的判断标准，编排、方向、校对的细节分别见第 6.A、6.B、6.C 节。

| 步骤 | 做什么 | 判断标准（满足才往下走） | 详见 |
|---|---|---|---|
| 1 读仓库 | 检测 project-map、技术栈、规模；建立笔记工程目录、需求包；调用 dev-skills 初始化 | `_勘察结果.md` 写好基准与 map 状态；需求包生成；dev-skills 初始化完成，状态为"可接力" | 2.2、6.A |
| 2 识别链路 | 有 map 时从总览主体流程起；没有时走 2.7 的轻量发现 | 每条候选链路都有入口和终点状态 | 2.7、6.B |
| 3 拆分 | 定篇目、每篇的起点和终点、篇间接口、术语表初稿 | 用户确认拆分方案（必停点） | 6.B 第一阶段 |
| 4 写作 | 每篇先取证写事实摘要，再成文 | 事实摘要每条都有来源；成文符合第 4 章模板 | 6.B 第二阶段 |

## 6. 长任务编排、生成方向与逐篇校对（增补）

**问题**：一次性完成"全仓库阅读 + 链路梳理 + 撰写 + 优化"，上下文会被撑满，越往后越涣散：术语漂移、重复叙述、丢失主线、与前文矛盾。样本规模也说明一口气写不完：标杆单篇 55–65KB，三份 project-map 的模块合计 1.2–2.9MB。

### 6.0 ruan-dev-skills 研读结论

依据：本机 `ruan-dev-skills/SKILL.md`、`assets/dev-protocol.md`、`assets/relay-prompt.md`、`scripts/devdocs.py`（只看了命令定义）。

**它提供什么**
- **方法**：把"需求材料 + 当前代码"编译成多个 fresh-context 串行步骤；"一个步骤应能在一个 fresh context 内完成必要访读、实现、验证、修复和回写"；只详拆近期步骤，远端步骤只保留粗目标；需要时把步骤拆成新的 S-ID 插回原位（协议 §5）。
- **产物**：`<项目>/docs/AI dev docs/<版本>/` 下的《步骤总览》《当前状态》《开发环境》《决策记录》、步骤文件、`plans/Pxxx/` 需求快照与 `plans/索引.md`，加上原样复制的《开发协议》《开发接力提示词》。
- **进度记录**：《当前状态》保持很薄（当前步骤、代码基线、上一步 checkpoint hash、下一动作、阻塞）；"同一可变事实只维护一处"。
- **会话恢复**：开工对账（协议 §2）用代码 commit hash 作为步骤完成的强证据；"披露式读取"（当前状态 → 当前步骤 → 步骤所需资料 → 相关代码 → 按需扩展）。
- **机械脚本**：`check-root`、`archive`、`verify`、`same`，都是围绕双 Git 仓和需求归档的校验。

**它不提供什么**
- 文档写作规范、叙事、可读性校对；
- 针对"文档生成"的步骤语义：它的步骤完成以"业务代码 checkpoint"为强证据，S001 固定为"环境确认与原始基线建立"（跑构建和测试）；
- 灵活的落盘位置：版本目录必须是 `<项目总目录>/docs/AI dev docs/<版本号>/`，资料仓必须是独立 Git 根，代码仓是当前工作目录的 Git 根；
- 改写协议：两份固定资产"生成时原样复制，不按业务需求改写"。

**决策 D10：直接调用 ruan-dev-skills，不在本 skill 内另做一套编排。**
理由（用户给出）：自己再实现一套类似机制，容易跑偏；dev-skills 已经成熟。为此用户接受三点代价：
1. 重新设计笔记的目录结构，去适配 dev-skills 的目录约定（见 4.1）；
2. 笔记目录本身成为 dev-skills 眼中的"代码仓"，用 Git 管理，步骤完成以笔记仓的提交 hash 为证据；
3. 第一步 S001"环境确认与原始基线"对笔记仓没有实际意义，照常执行，不做特殊处理（它只会确认笔记仓状态并记录基线）。

**固定资产这条约束意味着什么**：dev-skills 会把《开发协议》《开发接力提示词》两份文件原样复制进版本目录，规定以后不许按业务需求改写。所以"笔记该怎么写、怎么取证、怎么校对"这些本 skill 特有的规则，**不能写进这两份文件**，只能放在 dev-skills 允许按需求生成的地方：
- **需求材料**（归档为 `plans/P001/`）：由本 skill 生成"笔记生成需求包"，里面包含写作规范、约束取舍表、拆分方案、交接物约定、校对协议、自检清单；
- **步骤文件**：dev-skills 规划时为每个步骤写的说明，要求它在每一步写明"读需求包的哪几份"。

这不影响效果：dev-skills 的协议本来就要求"需求边界不清时读 `plans/索引.md`，再按覆盖范围读 Pxxx"（协议 §3）。

**分工**
| 谁 | 做什么 |
|---|---|
| ruan-project2doc（第一次调用） | 检测 project-map、勘察仓库、做拆分方案并请用户确认；生成笔记仓骨架和笔记生成需求包；然后调用 dev-skills 初始化 |
| ruan-dev-skills | 归档需求包为 P001，规划步骤（S001 + 每篇的取证/成文/校对 + 收束），生成进度与接力文件 |
| 后续每个新会话 | 用《开发接力提示词》推进一个步骤；写笔记仓、提交、回写进度 |
| 用户后续修改 | 在修改提示词文档里追加要求 → 作为新需求材料交给 dev-skills 的"调整"模式，归档为新的 Pxxx 并规划修改步骤（第 9.2 节） |

依赖方式（硬依赖还是软依赖）见第 14 章 Q-6。

### 6.A 长任务编排

#### 6.A.1 任务单元划分

一个项目就是一个"笔记目录生成任务"。U-勘察和 U-拆分由 ruan-project2doc 在第一次调用时完成（拆分方案要用户确认，又要用到第 2 章的 project-map 规则，放在 dev-skills 之外更可控）；之后的单元由 dev-skills 规划成 S 步骤，单元类型和粒度作为需求包里的"步骤拆分要求"交给它（决策 D10、D12）。S-ID 的编号、拆分和废弃完全按 dev-skills 协议 §5 执行。

| 单元类型 | 数量 | 由谁执行 | 划分依据 |
|---|---|---|---|
| U-勘察 | 1 | ruan-project2doc 首次调用 | 检测 map、基准、技术栈，建立笔记工程目录 |
| U-拆分 | 1 | ruan-project2doc 首次调用 | 定篇目、起点和终点、篇间接口、术语表初稿；产出 00 的骨架；用户确认后生成需求包并调用 dev-skills 初始化 |
| S001 环境确认 | 1 | dev-skills 规定 | 对笔记仓只记录基线，没有构建可跑，照常通过 |
| U-取证（每篇一个） | 篇数 | dev-skills 步骤 | 为一篇笔记取证，产出事实摘要 |
| U-成文（每篇一个） | 篇数 | dev-skills 步骤 | 只读事实摘要和交接物，写成笔记 |
| U-校对（每篇一个） | 篇数 | dev-skills 步骤（天然是独立的新会话） | 可读性校对，见 6.C |
| U-收束 | 1 | dev-skills 步骤 | 回写 00 的衔接与术语，写 99，生成修改提示词文档，全局一致性检查 |

每个 dev-skills 步骤的"验证方式"写成第 11 章对应的自检清单；验证通过后在笔记仓提交，提交 hash 就是该步骤完成的证据。

粒度（决策 D12）：一篇对应"取证 + 成文 + 校对"三个单元。取证和成文分开，是因为取证要大量读源码，而成文需要的是腾出来的上下文去组织叙事；两者放在一个会话里，正是"后半段涣散"的主要来源。**超长篇的再拆**：取证阶段发现事实摘要超出预算（6.A.2），或触发拆篇信号（D5：同级步骤超过约 15 步，或跨过两个状态终点），就回到 U-拆分，把这一篇拆成两篇。拆的是篇，不是一篇里的段落；理由是拆半篇会破坏"一篇一条链路"。

#### 6.A.2 每个单元的输入、输出、完成判据和上下文预算

| 单元 | 读什么 | 明确不读 | 输出 | 完成判据 |
|---|---|---|---|---|
| U-勘察 | 目录树、构建文件、map 的 STATE/COVERAGE/模块状态行、`git log -1` | 模块正文、业务源码 | `_勘察结果.md` | 基准、map 状态、规模都写明 |
| U-拆分 | map 总览（或 2.7 的发现结果）、入口与汇点表、用户给的重点 | 下层模块的执行图与候选表 | `_拆分方案.md`、`_术语表.md` 初稿、00 骨架 | 每篇有起点、终点状态、不覆盖项与去向；用户已确认 |
| U-取证 | 本篇对应的 map 模块（只读相关节点与未决）、本篇入口到终点之间的源码、`_术语表.md` | 其他篇的源码与 map 模块 | `_事实/NN.md`（含关键步骤覆盖矩阵、附录 B 自查结果） | 每条事实有来源与核对标记；关键数据都追到来源（B §七）；矩阵每行为"已覆盖"或写明去向；B1/B2 组无未处理的 P0、P1 |
| U-成文 | `_事实/NN.md`、`_术语表.md`、`_衔接约定.md`、写作规范（第 7 章） | 源码（需要新事实时回退到 U-取证）、其他篇正文 | `NN-标题.md` | 符合第 4 章模板；正文里没有不在事实摘要中的事实；附录 A 自查已执行 |
| U-校对 | 该篇、相邻篇的事实摘要首尾、写作规范 | 源码、其他篇全文 | 修改后的该篇、`_校对记录/NN.md`（按 ID 逐条记录命中位置） | 第 6.C 停止条件满足 |
| U-收束 | 各篇的标题目录与首尾、`_术语表.md`、`_衔接约定.md`、全部事实摘要的"未确认"节 | 各篇正文全文 | 00 定稿、99、修改提示词文档 | 第 11.2 节全局项（含 F30–F32）通过 |

**预算的约定**：不写死字节数，规则是"单元读入的原始材料加产出，不超过上下文的一半"（默认值，可后改）。理由：另一半要留给推理和自检。U-取证最容易超：它读的源码量取决于链路长度，所以超出时的动作是拆篇（6.A.1），而不是"少读一点"。

#### 6.A.3 交接物（落盘在 `笔记/_工作区/`，随笔记仓一起提交）

| 交接物 | 内容 | 格式 | 何时更新 |
|---|---|---|---|
| `_勘察结果.md` | 源码基准、project-map 基准与状态、技术栈与规模 | 字段表 | U-勘察写；源码基准变化时更新 |
| 进度（不由本 skill 维护） | 当前步骤、基线、上一步笔记仓 checkpoint、下一动作 | dev-skills 的《当前状态》《步骤总览》 | 按 dev-skills 开发协议 §7，每步结束时回写 |
| `_拆分方案.md` | 篇目、每篇的起点与终点状态、不覆盖项及去向、对应 map 模块与节点 ID | 表格 | U-拆分写；拆篇时更新 |
| `_术语表.md` | 术语、本项目中指什么、首次出现在哪篇、源码名 | 表格 | U-拆分建初稿；U-取证可以追加，不可以改已有词条的含义（改含义要回 U-拆分） |
| `_衔接约定.md` | 相邻两篇的交接物（上一篇终点 = 下一篇起点的同一事物）；跨篇机制归属哪篇 | 表格 | U-拆分写；U-取证发现不一致时记一条冲突，由 U-收束处理 |
| `_事实/NN.md` | 本篇事实条目：内容、来源（2.6）、核对状态（已核实 / 推断 / 待核实）、涉及的数字 | 编号列表，一条一行 | U-取证写；U-成文只读 |
| `_校对记录/NN.md` | 每轮校对按附录 A 的 ID 记录命中位置（节号 + 原句）与处理方式、退回准确性链路的条目 | 表格：ID / 位置 / 处理 | U-校对写 |
| `_问题台账.md` | 附录 B 命中的问题：ID、优先级 P0–P2、篇、问题、代码依据、状态（open / fixed / needs_user_decision） | 表格，编号稳定（沿用二轮深审台账格式） | U-取证、U-校对登记；U-收束要求无 open |

**为什么事实摘要用"一条一行"**：上层引用下层事实时，引用的是条目编号，而不是凭记忆复述（6.B 规则 1）；修改时也能按编号追溯。

#### 6.A.4 中断与恢复

恢复完全交给 dev-skills：新会话打开版本目录里的《开发接力提示词》，按开发协议 §2 开工对账（读《当前状态》、核对笔记仓 HEAD 与基线、判断半成品），不依赖对话记忆。

本 skill 只补一件 dev-skills 不知道的事：**被分析的源码仓变了怎么办**。每个 U-取证步骤开工时，比较源码 HEAD 与 `_勘察结果.md` 的基准；变化了就列出受影响的篇目（看事实摘要里引用的路径），作为"需求调整"交给 dev-skills 新增重新取证的 S 步骤，不在当前步骤里顺手处理。这一条写进需求包，由每个取证步骤文件引用。

#### 6.A.5 退化信号与动作

| 信号 | 怎么发现 | 动作 |
|---|---|---|
| 术语漂移：同一对象换了叫法，或用了 `_术语表.md` 没有的叫法 | 成文后用术语表逐词检查 | 回读术语表，修正；同一单元内出现两次就结束单元、换会话 |
| 主线丢失：一级节读完不能用一两句话复述 | 可读性标准 1 | 交给 U-校对；如果是结构问题，退回 U-拆分 |
| 重复叙述：同一机制在本篇讲了两遍，或别篇已有归属仍完整重讲 | 对照 `_衔接约定.md` 的机制归属 | 改为引用；频繁出现说明单元过大，下次拆小 |
| 与前文矛盾：数字、状态名与事实摘要或术语表不一致 | 成文自检时逐个对照数字 | 以事实摘要为准；事实摘要本身有疑问时退回 U-取证 |
| 正文出现事实摘要里没有的事实 | 成文自检 | 删掉，或退回 U-取证补证；不在成文单元里临时查源码 |

总的原则：发现信号时优先**结束当前单元并换会话**，而不是在当前会话里继续修补，因为涣散本身就是上下文过满的结果。

#### 6.A.6 进度可见性

每个步骤结束时按 dev-skills 协议 §7 回写并提示开新会话；需求包要求额外报告一行：本步产物、未确认项数量。

**用户验收节点（决策 D11）**：拆分方案确认一次（U-拆分，必停点）；之后每篇的"取证、成文、校对"三个步骤都完成后确认一次。实现方式：在需求包里要求 dev-skills 把每篇的校对步骤的"下一动作"写成"等待用户确认第 NN 篇"，用户确认后再开下一个会话。

#### 6.A.7 没有 ruan-dev-skills 时

硬依赖（决策 D13）：开工检测到未安装，就停下并提示先安装 ruan-dev-skills，不提供降级编排。理由：降级编排等于在本 skill 里再实现一套同类机制，正是 D10 要避免的跑偏风险。

### 6.B 生成方向（准确生成链路）

#### 6.B.1 三种方案的评估

| 维度 | 自底向上（先细节和子流程，再主干，最后总览） | 自顶向下（先总览与骨架，再逐篇展开） | 混合（先定骨架与衔接约定，再逐篇自底向上取证成文，最后回顶层统一） |
|---|---|---|---|
| 准确性风险 | 低：上层只概括已落盘的事实 | 高：骨架和总览先于取证写成，后面的取证容易迁就骨架，把推断写成事实 | 低：骨架只定"范围和接口"，不写事实结论；事实全部来自取证 |
| 可读性与衔接风险 | 高：各篇各写各的，术语与切分点事后才对齐，返工量大 | 低：一开始就有全局视野 | 中低：衔接约定先定，最后一轮再统一过渡 |
| 上下文成本 | 中：每篇独立，但最后的总览要读全部摘要 | 低到中 | 中：比自顶向下多一份交接物 |
| 返工成本 | 高：篇目边界事后才确定，可能整篇改切 | 高：取证推翻骨架时要重写多篇 | 中：骨架可能被取证推翻，但只改拆分方案和受影响的两篇 |
| 与 project-map 结合 | 适合有大量叶子级事实的 map（样本里已证叶子都是 0，用不上这个优势） | 直接用 map 总览当骨架，但会继承 map 的过期内容 | map 总览只作拆分候选（D2），模块与节点作取证线索 |
| 适用规模与类型 | 小项目、单链路 | 结构已经很清楚、主要是改写的场景 | 中大项目、多条链路，三个样本都属这一类 |

**对候选假设的评估**："准确性要下层事实先落地，可读性要先有全局视野，所以先定顶层骨架与衔接约定，再自底向上取证成文，最后回顶层统一过渡"。我认为**成立，但要加一个限定**：第一阶段的骨架只能包含"范围、起点和终点状态、接口、术语初稿"，**不包含任何事实结论**（例如"某机制保证了什么"）。否则它就退化成自顶向下，后面的取证会去迁就骨架。标杆的 `00` 本身也是最后才定稿的：它的第四节"一句话结论"引用了各篇的事实，属于"先写骨架、最后回填"的产物。

**采用混合方案**（决策 D11，用户在混合与纯自底向上之间选定混合）。三个阶段（第 1 阶段由 ruan-project2doc 首次调用完成，第 2、3 阶段是 dev-skills 的步骤）：
1. **骨架**（U-拆分）：篇目、起点与终点状态、接口、术语初稿、机制归属。00 只写边界和清单，"一句话结论"一节先空着，交付时再填。
2. **逐篇自底向上**（U-取证 → U-成文 → U-校对）：篇内先取证落盘，再成文。篇与篇之间按衔接顺序进行，让后一篇能读到前一篇的终点摘要。
3. **回顶层统一**（U-收束）：用各篇事实摘要回填 00 的一句话结论和衔接段，统一术语和过渡，写 99。

**失败模式与预防**

| 失败模式 | 预防 |
|---|---|
| 骨架里夹带事实结论，取证迁就骨架 | U-拆分的产物只允许范围、状态名、接口；U-收束才写结论 |
| 取证推翻了切分点（例如终点状态并不存在） | 退回 U-拆分，只改受影响的相邻篇，记入 `_拆分方案.md` |
| 逐篇推进时前后篇术语不一致 | `_术语表.md` 只能追加，改含义必须回 U-拆分 |
| 收束阶段"顺手"改写各篇事实 | U-收束只能改 00、99 和各篇的过渡句，不改正文事实 |

#### 6.B.2 上层引用下层事实的规则

1. 00、99、篇首的一句话主线、篇尾的接口段，引用的事实**只能来自已落盘的 `_事实/NN.md`**，注明条目编号（编号只记在工作区，不进正文），不凭记忆复述。
2. 概括可以降低细节，但**不能提高结论强度**：下层是"推断"，上层不能写成确定事实。

#### 6.B.3 跨篇一致性

- 术语：以 `_术语表.md` 为唯一来源（00 的术语表从它生成）；
- 数字：同一数字只有一个事实条目，其他篇引用该条目；
- 流程名和状态名：在 `_衔接约定.md` 里固定，篇首篇尾的接口必须使用同一个名字。

#### 6.B.4 下层与上层冲突时的回修

优先级：**当前源码 > 事实摘要 > 衔接约定和术语表 > 拆分方案 > 00 和过渡句**。

发现冲突时，按优先级找到第一个有错的层修正，再向下游传递：改了事实摘要，就重新成文受影响的段落；改了衔接约定，就更新相邻两篇的接口段；改了拆分方案，就重做受影响篇目的取证。每次回修按 dev-skills 协议 §3"范围外问题新增 S-ID"处理，不改已完成步骤的记录。

### 6.C 逐篇可读性校对与优化

#### 6.C.1 定位

校对是独立于撰写的环节。输入只有：该篇全文、相邻篇的事实摘要首尾（检查接口）、写作规范（第 7 章）和约束取舍表（第 8 章）。**不读整个仓库**。

#### 6.C.2 校对维度（从标杆提炼）

下面七个维度是总纲，**实际执行按附录 A 的 R 编号逐条进行**，结果写入 `_校对记录/NN.md`。两轮分工（默认值，可后改）：第 1 轮查结构与层级（A2、A3、A4、A5），第 2 轮查句子与术语（A1）；理由是结构调整会改写句子，先调结构再抠句子可以避免返工。

1. **主干是否清晰**：只看标题能否还原流程（B §四.6）；每个一级节能否用一两句话复述（D5 标准 1）。
2. **就地展开后是否回到主线**：补充块是否紧跟所补充的步骤；下一句是否回到主流程（B §二）。
3. **是否由浅入深**：有没有一句话主线和全景图；异常是否下沉到补充块，没有和正常流程同级。
4. **过渡是否自然**：有没有模板化转场（B §三.9）；相邻两步之间是否"一句推一句"。
5. **重点是否点明**：关键结论是否用加粗或提示块，而不是靠标题或换句式重复（B §四.5）。
6. **代码名密度**：主线段落去掉源码名后是否仍能看懂（D5 标准 2）。
7. **动机**：每个主流程步骤是否写了"防的是什么"（D5 标准 3）。

#### 6.C.3 权限边界

| 可以改 | 不可以改 |
|---|---|
| 表达、句子顺序、段落顺序、过渡、详略、标题措辞、补充块的层级 | 事实、数字、源码依据、结论强度（已核实 / 推断 / 待核实的标记） |

需要改事实时，在 `_校对记录/NN.md` 里记一条"退回准确性链路"，由新的 U-取证单元处理。理由：校对单元不读源码，在这里改事实只能凭记忆，正是准确性最容易出错的地方。

#### 6.C.4 执行者与轮数（决策 D12）

- 由**独立会话或独立子 agent** 执行，不让作者自评。在 dev-skills 编排下，校对是单独的 S 步骤，天然在新会话里进行。理由：作者会把自己知道但没写出来的上下文自动补上，看不出悬空句和跳步。
- **最多 2 轮**。停止条件：第 6.C.2 节七个维度都没有新问题；或者第二轮只剩措辞偏好，没有结构性问题。超过 2 轮仍有结构性问题，说明是拆分或取证的问题，退回对应单元，不继续润色。
- 收尾时用"说人话"类 skill 做一次表达自检（B §八最后一段），如果本机可用。

#### 6.C.5 与修改提示词文档的关系

**结论：复用同一套流程，入口不同。**
- 生成期校对：输入是写作规范和取舍表；
- 用户后续修改：输入是同样的规范，加上修改提示词文档里用户追加区的新要求。

两者都遵守同一个权限边界（6.C.3）：涉及事实的要求走准确性链路（U-取证），只涉及表达的走校对流程。理由：B 本身就是"修改已有笔记"的要求文档，标杆的生成和后续修改用的是同一套标准；拆成两套会让规范分叉。

### 9.2 使用协议：AI 如何选择并修改一篇或多篇

2. **定目标篇**：
   - 填了目标篇：只改这些篇。
   - 没填：按要求涉及的术语、机制、流程名，查 `_术语表.md` 的首次出现篇和 `_衔接约定.md` 的机制归属，列出受影响篇目和理由，**等用户确认后再改**（理由：防止 AI 自行扩大范围，B §一）。
3. **定类型**：
   - 只涉及表达或结构：走 6.C 校对流程，输入是该篇加这条要求；
   - 涉及事实：先走 U-取证核对源码，更新 `_事实/NN.md`，再改正文。
4. **改**：直接改在原位置，正文不留痕迹（C14）。
5. **改完自检**：第 10 章的单篇清单；如果改动影响了篇首篇尾接口或术语，同步检查相邻篇。
6. **留痕**：在「四、变更记录」追加一行，把对应要求的状态改为"已处理"。

**与 ruan-dev-skills 的衔接**：修改不是在当前会话里直接动手，而是走 dev-skills 的"需求调整"模式：
- 把修改提示词文档作为新的需求材料交给 dev-skills，归档为新的 Pxxx，`plans/索引.md` 标明本次只覆盖"用户追加区"里状态为"待处理"的行；
- 第 2 步"列受影响篇目并等用户确认"在调整前由 ruan-project2doc 完成，确认后的篇目清单一起写进需求材料；
- dev-skills 为每篇规划修改步骤（涉及事实的先规划取证步骤），之后按接力提示词逐步执行；
- 小改动（只改一篇的表达）也走这条路，代价是多一次规划；好处是所有修改都有提交 hash 可追溯。例外（决策 D14）：只改一篇、只涉及表达的修改可以在当前会话直接改，按 6.C 的权限边界执行，改完仍在笔记仓提交并写变更记录；涉及事实或多篇时必须走 dev-skills。

用户要求与固定规范冲突时（例如要求"每个类名都保留"），以用户要求为准，并在变更记录里注明偏离了哪条规范。理由：修改提示词文档允许用户随时增删要求，是用户意图的最高来源。

## 10. 准确性保障与对不确定内容的处理

### 10.1 事实分层

沿用标杆 00 第七节的分层，不允许互相升格：已确认事实 / 可复现实证（测试与留档，写明覆盖范围）/ 历史实现证据 / 目标设计 / 合理推导 / 未确认。

### 10.2 不确定内容怎么写才不破坏阅读流

- 正文只用短标签：`【推导】` `【未确认】`，放在句末；
- 详细的"为什么没法确认、缺什么证据"放进 99 的未确认项表；
- 如果不确定点会改变主流程的走向，就在正文就地写一个 `当前限制` 补充块，而不是只放 99。

### 10.3 借鉴 project-map 时的核对与溯源

见第 2.3–2.6 节。每篇证据索引按来源分组，事实摘要里每条都带来源和核对状态。

## 12. 泛化性推演

以下推演基于结构勘察和 project-map 状态，没有读业务源码；篇数是估计值。

**定位说明**（D19）：这三个项目是验证样本，用来检验第 2 章和第 6 章的规则在不同形态、不同 map 状态下是否成立，不是本 skill 的服务对象。三者都以 Java 为主，覆盖面有限，非 Java 和非服务端项目的验证见 13.6 的 T9、T10。

### 12.1 企业知识库 RAG 系统（有 project-map 路径）

- **形态**：Java 服务端 + Python AI 服务 + Web 前端（`apps/server`、`apps/ai`、`apps/web`），三端源文件约 1525 个。
- **拆分**：map 总览有 9 个执行分区（在线问答、文档入库发布、源同步、Agent 与审批、事件与权限版本、会话派生与记忆、评估与在线判官、治理控制台、定时与运维）。按"终点是可观测状态"，较重的"在线问答"大概拆成 受理与编排 / 混合检索与精排 / 交付三篇；"文档入库发布"拆成两篇。预计正文 12–14 篇。
- **单元数**：勘察 1 + 拆分 1 + 每篇 3 个 × 约 13 篇 + 收束 1 ≈ 42 个单元。
- **会遇到的问题**：
  - **基准过期是最大风险**：map 落后 61 个提交、226 个文件。2.2 第 4 步会把 diff 路径涉及的模块全部列为"必须核对"，取证成本接近无 map 路径。这正是检验 2.3 分级的真实用例。
  - 跨语言链路（Java 调 Python）：一篇笔记要横跨两个服务，U-取证读入的源码面更宽。
  - 11-前端模块"限制=有"，按 2.3 读限制说明后再定范围。

### 12.2 河南中烟卷包车间后端重构（有 project-map 路径；也用于"状态不全"推演）

- **形态**：Maven 多模块 Java 后端（`apps`、`modules`、`database`），约 1615 个 Java 文件；map 有 77 个入口、20 个模块。
- **拆分**：map 模块已经按业务域切得比较细（MES 入站、DAS 批次、出站对账、工单执行、物料台账、质量问题……），很多模块可以 1 对 1 成篇，少数（例如"五域聚合运行与发布"）可能拆成两篇。预计正文 18–22 篇。
- **单元数**：约 60–70 个，**单元数最多**。
- **会遇到的问题**：
  - **规模**：map 模块合计约 2.9MB，是三者中最大的；单个模块文件很大，U-取证"只读相关节点与未决"的规则在这里最关键。
  - **状态不全**：`19-物料质量关联查询` 是"梳理中"，按 2.3 全部回源码核对；待办 247 条，大部分是待核实，取证时会频繁遇到"线索不能直接用"。
  - 后端重构类项目的"关键链路"更多由入站消息和定时任务驱动，不是用户操作驱动；"终点是可观测状态"的切分规则依然适用（终点多是表状态或出站回执）。

### 12.3 EMG 多端训练标注数据平台（有 project-map 路径）

- **形态**：Java 后端 + Vue 前端 + Android 客户端，两个独立 Git 仓库，约 1046 个源文件；与标杆是同一个系统的不同版本。
- **拆分**：map 有 8 个模块，其中"分片上传会话"一个模块就有 117 个展示节点，对应标杆的 01+02 两篇。预计正文与标杆相近，9–11 篇（多出 Android 端和认证权限）。
- **单元数**：约 30–35 个。
- **会遇到的问题**：
  - **9 个模块全部"限制=有"，check exit 1**：按 2.3，所有借鉴事实先读限制说明；断链只影响 06 模块的导航，不影响源码事实，所以 06 照常分级。
  - **两个 Git 仓库**：基准比对要分别对两个仓库做；跨端链路（Android Worker → 后端）在一篇里要读两个仓库。
  - 可以用标杆做对照验收：生成的上传篇与标杆 01/02 比较结构和覆盖面。

### 12.4 无 project-map 路径推演（假设 EMG 没有 map）

- U-勘察：发现 Spring 控制器、RocketMQ 监听、`@Scheduled`、Android Worker 等入口；反向扫 `INSERT`、MinIO PUT、MQ 发送。
- U-拆分：主体流程候选靠入口和汇点对照得出，大致会得到"上传 → 入库 → 回放 → 同步"几条主线，与标杆生成提示词里人工给出的四条主线相近。
- 风险：没有 map 的未决表，**隐藏链路**（例如 DLQ 清扫、孤儿检查这类后台任务）更容易漏掉。预防：U-拆分必须列出所有 `@Scheduled` 和监听器的去向（归入某篇，或在 00 标为不覆盖并写原因）。
- 成本：U-取证全量核对，单篇的取证单元更容易超预算，拆篇会更频繁。

### 12.5 哪个项目最容易撑爆上下文

**河南中烟**：单元最多、map 最大、模块文件最大。应对：
1. U-取证只读相关节点与未决，不读整份模块文件；
2. 事实摘要严格按 C20 控制篇幅；
3. U-收束不读正文全文，只读标题目录、首尾和事实摘要的未确认节。

RAG 的风险性质不同：主要是基准过期导致取证成本高，而不是上下文大。

`单篇笔记.md`、`00-总览.md`、`99-复核说明.md`、`修改已有笔记.md`（含固定规范区全文），以及交接物模板 `_拆分方案.md`、`_术语表.md`、`_衔接约定.md`、`_事实.md`、`_校对记录.md`。

### 13.4 是否需要脚本

建议一个只读的小脚本（Python 标准库），做三件机械的事：
1. 检测 project-map、读状态行与 STATE 统计、比对基准提交号与 HEAD；
2. 检查笔记仓实际文件与《步骤总览》中已完成步骤的产物是否对得上；
3. 检查笔记里使用的术语是否都在 `_术语表.md` 中，篇首篇尾接口名是否与 `_衔接约定.md` 一致。

理由：这三件事人工做容易漏，而且不需要理解语义。可读性判断不脚本化。

### 13.5 与 ruan-dev-skills 的关系

- **调用方式**：ruan-project2doc 在首次调用末尾，以"需求材料 = `<笔记工程>/需求包/`，版本目录 = `<笔记工程>/docs/AI dev docs/<版本号>/`"调用 dev-skills 初始化；修改时以修改提示词文档调用 dev-skills 调整模式。代码仓是 `<笔记工程>/笔记/`（会话工作目录）。
- **需求包**（`需求包/`，作为 P001 归档）至少包含：
  1. `00-任务说明.md`：目标、被分析仓库路径与基准、产出位置、"这里的'代码仓'是笔记仓，S001 只记录基线"；
  2. `01-拆分方案.md`：用户确认过的篇目、起点与终点、篇间接口；
  3. `02-步骤拆分要求.md`：6.A.1 的单元类型、粒度、每类单元的输入/不读/输出/完成判据（6.A.2），每篇校对步骤后等待用户确认；
  4. 写作规范、约束取舍表、校对协议、自检清单、project-map 借鉴规则（从本 skill 的 references 复制）；
  5. 交接物模板。
  这样每个 dev-skills 步骤文件都能用 `P001 + 文件名 + 标题` 的格式引用具体规则。
- **SKILL.md 声明依赖**（D13）：在 frontmatter 的 compatibility 写明需要 ruan-dev-skills 2.0 与 Git，开工检测，缺失即停止。
- **Git 提交**（D15）：笔记仓默认 Git 管理，允许自动提交；只提交笔记仓，从不推送。
- **交接物模板**：放在本 skill 的 `templates/`，首次调用时复制进 `笔记/_工作区/` 和需求包。
- **为什么写作规则放需求包而不放协议**：dev-skills 的《开发协议》《开发接力提示词》按其规定原样复制、不得改写（6.0）。

## 附录 A　可读性与写作问题清单（具象化）

**为什么要有这份清单**：第 7 章和 11.1 只写了原则。"可读""连贯"太抽象，AI 自检时很容易逐条打勾，实际什么也没查。这份清单把用户长期积累的 AI 写作毛病逐条落成可以执行的检查：每条有稳定 ID、一个判定问题、反例和正例。

**来源**：
- B（`10.4笔记\修改已有笔记-数据管理平台.md`）；
- `10.2笔记\00-起步提示词.md`（下文简称"起步"），具体是其中的 43 条 grok 检查项、"陌生用语"段、codex 检查项、"理清逻辑链"段和"思维导图"段；
- 标杆 10.4 笔记。

**例句标注**：反例和正例凡是原文摘录的，都标了出处；标"示意"的是按原文描述改写的。

**例句来源说明**（D19、D22）：本附录的真实例句集中在同一个业务领域（上传、消息、缓存），只用来说明问题的形态。实现 `references/问题清单.md` 时，保留这些真实原句，并为每一类再补一个其他领域的改写示例（如订单、支付、导入任务），统一标"示例，非领域知识"。skill 运行时检查和改写，都以目标项目自己的句子为准。

**用法**（6.C 与第 11 章引用本附录）：
- U-成文结束时自查 A 组；U-校对逐条执行 A 组全部条目。
- 结果写进 `_校对记录/NN.md`，格式为"ID → 命中位置（节号 + 原句）/ 无"。**不允许只写"已检查"**。
- 命中项按 6.C.3 的权限边界处理。

## 附录 E　问题清单的维护（防止跑偏）

- **运行时只引用 ID**：步骤文件、校对记录、问题台账都用 R、F、M 编号指代问题，不让 AI 每次凭自己的理解去复述"可读性"是什么。
- **项目级扩展**：用户在修改提示词文档里追加的要求，如果同一类出现了第二次，AI 就在项目口径区的"项目特有问题"表里登记一个项目级 ID（如 `P-R01`），格式与附录 A 相同：毛病、检验、反例与正例、出处。
- **回流到 skill**：项目级条目只在本项目内生效。如果多个项目反复出现同一个问题，由用户决定是否把它并入 skill 的 references。AI 不在运行时修改 skill 本身。

## 附录 F　抽象概念的操作化定义

**为什么要有这份附录**：附录 A 解决的是"可读性"太抽象的问题。本设计里还有一批同样抽象的词，例如"关键链路""可观测状态""防的是什么""就地展开""像小说"。只给这些词、不给判定方法，skill 落地时会各自理解，结果跑偏。所以这里每个词都写成四项：**定义 / 判定方法或产物 / 合格与不合格示例**。正文中凡出现这些词，都以本附录为准。

示例统一使用与样本项目无关的通用场景（订单、支付、导入任务），不代表任何项目的领域知识（决策 D19）。

|---|---|---|---|---|
| K01 | 入口 | 外部能触发本项目代码开始执行的位置。各技术栈的具体形态见附录 G | U-勘察产出入口清单，每个入口注明类型和源码位置 | ✓"`POST /orders`（`src/order/api.py#create`）" ✗"订单模块" |

## 附录 G　各技术栈的入口、终点与关键步骤映射

**为什么要有这份附录**：附录 B 和 K01、K02、K05 的原始素材来自 Java 后端项目，里面的 Controller、Consumer、Redis、MinIO 等都是具体技术。skill 面向任意项目，所以把这些概念抽象成"入口 / 终点 / 状态"，再按项目类型给出对应物。下表只是**发现线索**，最终以目标项目的实际代码为准。识别不出类型时，退回两条通用定义：入口是外部能触发执行的地方（K01），终点是留下可独立检查结果的地方（K02）。

| 项目类型 | 典型入口 | 典型可观测终点 | "状态"主要指什么 | 发现线索（检索模式只是起点） |
|---|---|---|---|---|
| HTTP / RPC 服务端 | 路由与处理函数、过滤器或中间件、RPC 方法、启动钩子 | 数据库记录与状态字段、发出的消息、对象存储、HTTP 响应 | 持久化的行、缓存键、会话或令牌、事务边界 | 各框架的路由注解或注册表；反查写库、发消息、外部调用 |
| 消息 / 任务驱动服务 | 消费者、定时任务、工作线程、批处理入口 | 处理后写入的记录、下游消息、死信、任务状态 | 偏移量或确认、重试计数、幂等记录 | 订阅、监听、调度注册；反查确认与重投 |
| 前端单页应用 | 路由页面、用户操作处理函数、应用初始化、后台轮询 | 发出的请求、本地存储、界面上的稳定状态 | 全局状态仓库、本地缓存、表单状态 | 路由表、状态仓库定义、请求封装层 |
| 移动客户端 | 页面或导航入口、后台任务、推送回调、应用启动 | 本地数据库、发出的请求、通知、界面状态 | 本地持久化、同步游标、令牌 | 清单文件中的组件注册、导航图、后台任务注册 |
| 数据 / 机器学习管道 | 管道或作业入口、调度定义、触发器 | 输出的表、文件或模型产物、指标记录 | 中间产物、检查点、分区或水位 | 作业定义、调度配置、读写数据集的调用 |
| 命令行工具 | 命令与子命令的注册点、主函数 | 写出的文件、标准输出与退出码、外部调用 | 配置文件、本地缓存、进程退出状态 | 参数解析器的注册点 |
| 库 / SDK | 对外公开的 API（导出的函数、类、方法） | 返回值、抛出的错误、回调、对传入对象的修改 | 实例内部状态、全局注册表 | 导出清单、公开接口文档、测试中的调用方式 |
| 多端或单仓多项目 | 各子项目各自的入口 | 跨端交接点（接口契约、共享存储、消息） | 跨端约定的状态与契约 | 按子项目分别套用上面各行，再找跨端交接 |

**附录 B 的具体技术词换成通用说法**：F03 的"MySQL、Redis、MinIO、MQ"读作"任意两个以上的独立存储或系统"；F30 的"Controller、Consumer……Sentinel Resource"读作"本表第二列列出的全部入口类型，加上第三列列出的全部终点类型"；F08 的"Android 与后端"读作"任意两端之间的契约"。附录 A、B 中来自 10.4 或 10.2 的原句保留原样，作为真实例证，但它们**只说明问题的形态**，不说明目标项目会有这些组件。
