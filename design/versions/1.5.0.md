## 0. 为什么重做

### 0.1 1.4 的实际效果

1.4 产出的 `01-登录会话` 篇，读起来是一份技术取证报告，不是一份学习笔记。典型症状：

| 症状 | 1.4 原文（节选） | 读者读完的状态 |
|---|---|---|
| 机制一句话带过 | “用户资料缓存的本机一级配置为 60 秒、Redis 二级为 30 分钟、空值为 30 秒，默认有效期抖动系数为 0.1……主动失效与跨实例处理见第 07 篇” | 记住了四个数字，不知道两级缓存怎么读、怎么写、为什么要两级、Redis 挂了怎样 |
| 只说存在，不讲背景 | “按令牌中的用户编号，从数据库或用户资料缓存装载当前用户” | 不知道为什么每个请求都要重新装载用户、为什么不直接信任令牌里的角色、为什么这里需要缓存 |
| 限流只给参数 | “登录的 IP 门是 60 次 / 60 秒……限流规则和预热机制由第 15 篇展开” | 不知道“IP 门”怎么计数、怎么判断超限、超限后谁返回什么 |
| 取证材料占据正文 | 七个“测试证据”块（“本次均未运行”）、迁移号 V1/V11/V13/V14/V16/V19 的列举、三个【未确认】、二十余处【推导】、带行号的证据索引 | 注意力被“证据是否充分”占据，主线和原理反而退到背景里 |
| 补充多于正文 | 第四节正文 3 段，补充块 6 个 | 分不清什么是要理解的核心，什么是边角 |

用户的判断标准：如果面试官顺着笔记继续追问实现细节（这个二级缓存具体怎么工作？限流怎么判断超限？），读过这份笔记的人答不上来。**笔记经不起追问。**

### 0.2 根因：不是规则少了，是目标和机制偏了

| # | 根因 | 在 1.4 里的具体位置 | 造成的结果 |
|---|---|---|---|
| 1 | **定位里没有“让读者理解”这一目标** | 核心价值写成“忠于源码 + 读得顺”；目标读者 K13 规定“通用概念不讲定义，只讲本项目怎么用” | 讲清 Redis 滑动窗口、两级缓存原理，按定义就在范围之外 |
| 2 | **标杆选偏** | 主要从 10.4 笔记和 B 提炼规则。10.4 是按“事实优先”提示词生成的，本身已偏取证；B 是一份**纠正 AI 过度展开**的修改要求，规则几乎全是“收”（精简、少代码名、不重复） | Skill 学会了克制，没学到 8.1、10.2 笔记里“讲透一个机制”的手法 |
| 3 | **生产管线里没有任何一步产出“理解”** | U-取证产出事实摘要：一行一条，“不写叙事、不写动机推演”，约为成文的 1/4；U-成文“只读事实摘要”，“不在成文单元里临时查源码”，正文出现摘要里没有的事实就删掉 | 从源码到笔记之间只流过孤立的事实碎片，成文只能拼接事实。原理、配合方式、设计原因在管线里无处产生 |
| 4 | **按链路拆篇 + 机制只归属一篇** | “同一机制只在归属篇讲完整，其他篇只讲本篇用到的部分加一句指引” | 两级缓存归 07、限流归 15，01 篇遇到它们只能写一串参数加“见第 NN 篇”。17 篇链路把每个机制都切碎了 |
| 5 | **质量判据只量准确、覆盖和形式** | 附录 A/B/D/F 共 100 多个检查 ID，没有一项检查“读者能否回答追问”；F 组要求每个分支、失败、配置差异都有去向；事实分层要求不确定性在正文可见 | 覆盖压力把正文推向“事实密度”，严谨压力把【推导】、测试证据、行号推进正文，变成审计报告 |

这五条互相加强：定位不要求理解（1）→ 标杆只提供克制（2）→ 管线无处产生理解（3）→ 拆分把机制推走（4）→ 质量门只奖励准确和覆盖（5）。在任何一处加几条“要讲透”的规则，都会被其余四处抵消。

### 0.3 重做原则

1. **从目标反推**：先定义“读完一篇笔记读者应该能做到什么”（第 1 章），再定义“讲清一个机制、一条流程”具体指什么（第 3 章），然后才设计篇目组织（第 4 章）、生产流程（第 5 章）和质量门（第 6 章）。
2. **准确是底线，不再是目标本身**。1.4 把准确当成最高目标，准确性的各种外显（证据、标签、未确认）挤占了讲解。1.5 中准确性仍不可违反，但它的证明材料默认留在工作区和 99，不进正文。
3. **1.4 的资产逐项过筛**（第 9 章）。与目标无冲突的基础设施（只读约束、dev-skills 编排、修改提示词文档、表达规范）保留；造成偏差的机制（事实摘要管线、机制单一归属、百余条检查 ID、正文证据外显）删除或重做。
4. **实现时重写，不在旧文件上改**。在 1.4 的 `写作规范.md`、`问题清单.md` 上增加“要讲透”的条目，正好就是“东坡肉（去掉蛋炒饭）”：旧规则的克制倾向仍在，新条目只是贴在上面。

## 1. 定位

### 1.1 一句话

**把一个项目讲懂给初学者**：读一个项目仓库的全部源码，写成一套中文系统学习笔记。读者读完，能说清系统的数据从哪里来、经过哪些处理、流向哪里，能讲清关键机制怎样实现、为什么这样设计，并经得起两三层追问。

### 1.2 目标读者（替代 1.4 的 K13）

| 读者已经具备 | 读者还不具备（笔记要补上） |
|---|---|
| 会写一般的业务代码；知道 HTTP、数据库、事务、Redis、消息队列、JWT 这些名词大概是什么 | 这些技术在真实系统里怎样组合使用；它们内部大致怎样工作，以至于能解释“为什么这样用” |
| 能读懂代码 | 本项目的业务、架构、数据流和设计取舍 |

所以：**通用技术的原理，讲到“足以理解本项目为什么这样用、和备选做法差在哪”为止**（用户确认，见 3.6）。不解释“什么是数据库”，但要解释“Redis 有序集合为什么能做滑动窗口”“本地缓存和 Redis 缓存各自解决什么问题”。

### 1.3 读完一篇后读者能做到什么（成功标准）

1. **讲流程**：不看笔记，能复述这条流程的主要步骤；能说出关键数据从哪里来、在哪些环节被校验或改变、最后落到哪里、交给谁。
2. **讲机制**：对篇中的核心机制，能讲出它解决什么问题、靠什么原理起作用、本项目具体怎样实现（结构、步骤、组件怎样配合）、失败时怎样兜底、为什么选这种做法而不是别的。
3. **经得起追问**：面对“为什么要这个判断”“这一步失败了会怎样”“为什么不用 X”这类两三层追问，能凭笔记内容回答。

这三条是 1.5 所有设计的出发点，也是第 6 章质量门 G1（追问测试）检验的对象。

### 1.4 学习笔记是什么、不是什么

| | 学习笔记（1.5 要的） | 源码取证报告（1.4 的结果） | 源码导读 / API 文档 |
|---|---|---|---|
| 回答的问题 | 这个系统怎样工作、为什么这样设计 | 代码里有哪些事实、证据是否充分 | 某个类或接口怎么用 |
| 组织方式 | 问题 → 原理 → 实现 → 取舍，嵌在业务流程里 | 按执行顺序列事实，附证据 | 按代码结构 |
| 主要内容 | 背景、机制原理、处理流程、判断原因、失败兜底、设计取舍 | 配置值、分支条件、异常码、版本迁移、测试覆盖、未确认项 | 签名、参数、返回值 |
| 证据的位置 | 留在工作区和 99；正文只在会改变理解时说明不确定性 | 正文 | — |

### 1.5 价值排序

**准确是底线，理解是目标，可读是手段，覆盖服从理解。**

- 准确：写进正文的每个事实都经源码核实；没有依据的设计意图不写成事实（3.7）。这条不可违反，但它的证明材料不进正文（3.8）。
- 理解：用 1.3 的三条衡量。冲突时，宁可少写一个次要分支，也要把核心机制讲透。
- 可读：B 提炼的表达规范（6.6）服务于理解，不反过来限制讲解深度。
- 覆盖：全仓库每个入口仍要有去向（见 4.5 的 99），但正文不追求穷举分支和配置。

### 1.6 触发与不适用（沿用 1.4，措辞更新）

触发：“把这个项目整理成学习笔记 / 系统学习笔记”“按主流程读懂这个仓库并写成笔记”“按修改提示词改一下第 N 篇”“我在修改提示词里加了要求”“继续生成笔记”。

不适用：单个函数或局部代码问答；建 project-map（那是 ruan-project-reader）；API 或部署手册、需求文档；修改业务代码；没有执行链路的纯配置或纯文档仓库。识别后说明原因并停止，不做降级处理。

### 1.7 通用性原则（沿用 1.4 D19）

Skill 面向任意项目。8.1、10.2 笔记和 EMG 仓库只是标杆和验证样本，不是领域知识：Skill 运行时不能假设目标项目里有 Redis、两级缓存或消息队列。规则用技术栈中立的词写（入口、终点、状态、机制、交接）；写进笔记的例子必须来自目标项目自己的代码；从样本估出的数字一律标“默认值，可后改”。

## 2. 标杆与反例

### 2.1 从 8.1、10.2 笔记提炼的讲解手法

这是 1.4 缺失的部分，也是 1.5 讲解规范（第 3 章）的来源。

| 手法 | 标杆中的样子 | 起什么作用 |
|---|---|---|
| 从问题起步 | 10.2：“这一篇解决的是‘用户登录后，系统怎样持续确认他是谁，并在过期、登出、改密……时收回令牌’的问题”；8.1 限流篇开头“问题的起点” | 读者先知道这个机制要对付什么，后面每个设计都有了着落 |
| 前置原理就近讲，够用即止 | 8.1 限流篇在讲项目实现前，先讲“Sentinel 是什么”“QPS 限流到底怎么‘限’”“熔断器三态转换” | 读者有了理解实现所需的最小原理 |
| 朴素方案 → 缺陷 → 改进 | 8.1 缓存篇讲防击穿：全局一把锁会让不同 key 互相排队 → 所以每个 key 一把锁 → 用并发 Map 按 key 取同一个锁对象 | 读者理解的是“为什么必须这样”，而不只是“代码是这样” |
| 方案对比 | 8.1 限流篇：固定窗口 / 每请求独立 key / 有序集合 + Lua 三种滑动窗口实现的对比表 | 回答“为什么不用别的”，这是面试最常追问的一层 |
| 写清读写顺序 | 8.1 缓存篇：“读：L1 → L2（命中回填 L1）→ DB；写：先删 L2 → 写 L1 → 写 L2 → 广播” | 读者能在脑中跑一遍机制 |
| 具体数字的小场景 | “100 个并发未命中 → 1 个查数据库”；“第五次失败只负责落锁，第六次才返回 423” | 把抽象规则变成能检验的结论 |
| 故障与兜底成套讲 | 8.1 缓存篇“Redis 故障全局对比——fail-open vs fail-closed 全景”；10.2“登录路径上 Redis 基本 fail-open：Redis 挂了仍可能登录成功，只是……” | 读者知道依赖出问题时系统的真实表现和代价 |
| 设计取舍讲代价 | 10.2：“非轮换设计让客户端简单……代价是原文一旦泄漏，攻击者可在七天有效期内重复刷新” | 不把设计讲成完美方案 |
| 收束全景 | 8.1 缓存篇“并发控制手段全景”；10.2“当前设计的优点、限制与优化方向” | 把分散在流程里的机制连成整体模型 |
| 澄清常见误解 | 10.2：“`STATELESS` 只表示不创建服务端 Session，不代表服务器完全不存会话相关数据” | 提前拆掉读者凭直觉会建立的错误模型 |

## 3. 什么是一份好的学习笔记（核心章节）

本章定义 1.5 的“东坡肉”。第 4–6 章都为实现本章服务。

### 3.1 两种讲解单元

一篇笔记由两种讲解单元交织而成：

- **流程讲解**：一件事从开始到结束经过哪些环节，数据怎样流动、状态怎样变化；
- **机制讲解**：流程中某个环节依赖的一套做法（如两级缓存、滑动窗口限流、双令牌、事务性 outbox、幂等去重），它怎样工作、为什么这样设计。

1.4 只有流程（而且退化成事实序列），没有机制讲解。1.5 中，流程是骨架，机制讲解嵌在它被用到的那一步里。

### 3.2 机制讲解：七问

讲清一个机制，要回答下面七个问题。“核心机制”七问都要答；“支撑机制”至少答 ①③⑤（分级见 3.4）。

| # | 问题 | 合格的样子 | 不合格的样子 |
|---|---|---|---|
| ① | **它解决什么问题**：没有它，在什么具体情形下出现什么坏结果 | “如果每个请求都直接查数据库取用户资料，所有受保护接口都要多一次数据库查询；用户量上来后，这个查询会成为全站最热的读” | “为了提高性能” |
| ② | **它靠什么原理起作用**（够用即止，见 3.6） | “Redis 有序集合按分数排序，可以一次删掉某个时间点之前的所有成员，所以能用时间戳当分数，删掉窗口外的旧记录后，剩下的个数就是窗口内的请求数” | 直接写“使用 ZSET 滑动窗口” |
| ③ | **本项目怎样实现**：用了什么结构（键、表、字段、数据结构），关键步骤按什么顺序执行，哪些组件怎样配合 | 写出读顺序、写顺序、键的格式、谁调用谁；一张小图或一个具体数字的走查 | 只写组件名和参数值 |
| ④ | **关键判断与分支**：每个判断为什么存在，不同结果走向哪里 | “拿到锁后再查一次缓存：排队期间前一个线程可能已经把数据写回了，这次查到就直接返回，查不到才由自己查库” | “加锁后进行双重检查” |
| ⑤ | **失败与兜底**：依赖出错、校验不过、并发冲突时系统怎样处理，代价是什么 | “Redis 读失败按未命中处理，请求继续查 MySQL，不会因为缓存故障而失败；代价是 Redis 故障期间数据库压力上升” | 不写，或只写“有异常处理” |
| ⑥ | **为什么这样设计**：与更简单或常见的备选做法比，差在哪、选它付出了什么代价 | “只用本地缓存：多实例各存一份，管理员改了角色，其他实例不知道；只用 Redis：每个请求多一次网络往返。两级结合……代价是需要跨实例通知” | 不写，或写成无依据的意图断言（见 3.7） |
| ⑦ | **局限**：在什么情况下它不起作用或会出错（简要） | “跨实例通知如果丢失，别的实例的本地旧值最多再活一个本地有效期” | 把所有理论风险都列一遍 |

③ 是 1.4 最缺的一问。**“本项目怎样实现”必须具体到读者能在脑中跑一遍**：给出顺序、给出结构、给出一个小例子，而不是列出参数。

### 3.3 流程讲解：数据的来龙去脉

讲清一条流程，要让读者能回答：

1. **起点**：谁、在什么场景下发起，带着什么数据来；
2. **校验**：经过哪些校验，每项校验拦的是什么情况，为什么放在这个位置（顺序本身常常有理由）；
3. **处理**：经过哪些环节，每个环节做什么、产生什么、交给下一步什么；
4. **判断**：在哪里分叉，依据什么数据判断，各分支走向哪里；
5. **状态与落点**：哪些状态被改变，数据最终写到哪里（库、缓存、文件、消息、响应）；
6. **接手**：谁接着处理，是同一次执行还是另一次（另一个请求、另一条线程、另一笔事务、另一个进程）。

关键数据（决定分支、用于身份或权限或幂等、写入持久存储、跨进程传递、参与最终结果的数据）要追到它真实的来源：谁产生 → 怎样传到这里 → 被谁使用或校验 → 何时失效。这一条沿用 1.4 的 K06 和 B 第七节，它本身是“讲清来龙去脉”的一部分，不是取证要求。

### 3.4 机制分级：讲多深由级别决定

不是每个机制都讲七问，否则篇幅失控、主线被淹没。U-规划阶段给每个机制定级，用户确认篇目时一并确认：

| 级别 | 判据（满足任一） | 讲解要求 |
|---|---|---|
| 核心机制 | 承担系统的关键质量目标（安全、一致性、可靠性、性能）；被两条以上主流程依赖；读者凭直觉容易误解；用户开工时点名 | 在主讲篇中完整回答七问；在其他用到它的篇中给“够用讲解”（3.5） |
| 支撑机制 | 主流程中有独立作用，但只服务一两处 | 在用到的地方回答 ①③⑤，通常两三段 |
| 细节 | 不改变读者对流程或机制的理解（日志字段、截断长度、兼容分支、迁移历史） | 一句带过或不写；去向记在研读稿 |

判据里的“两条以上”是默认值，可后改。

### 3.5 够用原则：跨篇使用机制时讲到哪里

1.4 的“机制只归属一篇，其他篇只加一句指引”是 01 篇只剩参数的直接原因。1.5 改为：

> **读者不翻其他篇，也能理解当前流程为什么这样走。**

具体要求：链路篇用到一个核心机制时，在用到的那一步给一段“够用讲解”，回答 ①（在这条流程里它解决什么）、③（在这条流程里它怎样工作，至少讲清读写或判断顺序）、⑤（在这条流程里失败会怎样），通常两到六段；然后一句话指向主讲篇，说明那里还会讲什么（原理、全部使用点、方案对比）。

**禁止**：只给名称、参数或数字，再写“见第 NN 篇”。

允许重复：同一机制在多篇里的够用讲解会有重叠，这是为单篇可读付出的合理代价。重叠控制在“够用”，完整讲解只在主讲篇。

### 3.6 通用原理讲到哪里

用户确认的深度：**讲到足以理解本项目为什么这样用、和备选做法差在哪为止。**

- 讲：理解本项目实现所必需的那部分原理。例：讲滑动窗口限流，要讲有序集合按分数删除和计数的能力、为什么要用 Lua 脚本把“删旧 → 计数 → 判断 → 写入”合成一次原子操作；讲两级缓存，要讲本地缓存和共享缓存各自的长处和短处。
- 不讲：技术的历史、完整 API、与本项目无关的特性、教科书式的全面介绍。
- 检验：把这段原理删掉，读者是否还能理解后面的项目实现和设计取舍？能理解，说明这段原理多余；不能，说明它必要。

### 3.7 “为什么这样设计”怎么写才不编造

用户要求讲“为什么这么实现”，而代码很少写明设计意图。1.4 的应对是给每个解释加【推导】，结果全篇二十多处标签。1.5 区分三种“为什么”：

| 类型 | 例子 | 写法 |
|---|---|---|
| **效果型**：这样做带来什么效果、避免了什么问题 | “先检查锁再比对密码，已被锁定的来源不会再消耗一次密码哈希计算” | 直接陈述。它是可以从代码行为验证的因果，不是对作者意图的猜测，不加标签 |
| **对比型**：换成备选做法会怎样 | “如果只用本地缓存，多个实例各存一份，改了角色其他实例不知道” | 直接陈述。这是对备选方案的分析 |
| **意图型**：作者当初为什么选它、在什么背景下引入 | “这个窗口是在校园网 NAT 下出现撞库后加上的” | 有出处（代码注释、提交记录、项目文档、设计记录）才写，正文可以说明出处类型；没有出处就不写意图，改写成效果型或对比型 |

这样，绝大多数“为什么”都能以效果型或对比型准确写出，不需要标签。【推导】只留给少数确实需要猜测意图、又对理解有帮助的地方。

### 3.8 什么不进正文

以下内容默认**不进正文**，留在工作区（研读稿）或 99：

| 内容 | 去处 | 例外：什么时候可以进正文 |
|---|---|---|
| 文件路径加行号、方法签名清单 | 研读稿；篇尾“代码地图”只列关键文件或类，不写行号 | 读者很可能要立刻跳过去看的一两处 |
| 测试证据（哪个测试断言了什么、本次是否运行） | 研读稿、99 | 测试本身是理解某个行为的最好例子时（如“连续 6 次错误密码的测试过程”），作为例子讲，不作为证据清单 |
| 数据库迁移号、版本号列举 | 研读稿 | 版本演进本身能解释当前设计时，进“版本演进”补充块，讲“旧做法 → 问题 → 新做法”，不列迁移号 |
| 【未确认】项 | 99 | 不确定点会改变读者对主流程的理解时，正文用一句话说明 |
| 部署覆盖值未知、注解数字不等于实际吞吐等取证式限定 | 研读稿、99 | 读者不知道就会形成错误模型时，用一句话说明 |
| 证据索引 | 不设；源码位置留研读稿，篇尾只留代码地图 | — |

准确性没有降低：这些材料都还在，只是不再以正文为载体。

### 3.9 代码片段

用户要求“不要大量堆砌代码块”，同时 8.1、10.2 标杆中短小的代码片段确实帮助理解。规则：

- 代码片段只在**它本身就是最直接的讲解载体**时使用：关键配置、注解组合、几行核心算法（如 Lua 脚本的步骤）、状态转换表；
- 片段之前必须先用自然语言讲清它在做什么；删掉片段，正文仍能读懂；
- 单个片段一般不超过约 15 行，每篇一般不超过约 5 个（默认值，可后改）；能用伪步骤或表格说清的，优先用伪步骤或表格；
- 不贴整个方法、整个类；不用代码代替叙述。

### 3.10 篇幅

用户不在意篇幅。1.5 **不设篇幅上限，也不设“约为成文 1/4”之类的比例**。检验只有一条：**每一段都要服务于理解**。

- 删去：重复（同一篇里第二次完整讲同一件事）、空话、模板化转场、与理解无关的取证细节；
- 不删：理解所需的背景、原理、实现过程、例子、取舍分析。不能以“精简”为由删它们。

### 3.11 示范：受保护请求装载当前用户（用户资料两级缓存）

用 EMG 仓库同一处内容，对照 1.4 与 1.5 的写法。下面 1.5 的段落是**写法示范**，数字取自 1.4 研读结果，事实以实测时的研读为准。

**1.4 写法**（`01` 篇第四节，节选）：

> 它解析 JWT、查询令牌标识是否已吊销，再按令牌中的用户编号，从数据库或用户资料缓存装载当前用户……
> > **补充说明**：用户资料缓存的本机一级配置为 60 秒、Redis 二级为 30 分钟、空值为 30 秒，默认有效期抖动系数为 0.1……主动失效与跨实例处理见第 07 篇，账号变更操作见第 03 篇。

**1.5 写法**（链路篇中的“够用讲解”，节选）：

> **为什么每个请求都要重新装载用户。** 访问令牌里虽然写着用户编号和角色，但令牌签发后最多有效 30 分钟，这期间管理员可能已经把这个用户降了角色或停用。如果过滤器直接相信令牌里的角色，这 30 分钟里旧角色仍然有效。所以过滤器只从令牌里取用户编号，再去取这个用户**当前**的资料，用当前的角色和启用状态做授权。
>
> **为什么这里需要缓存，而且是两级。** 每个受保护请求都要取一次用户资料，这是全站最频繁的一次读。每次都查 MySQL，数据库要为所有接口多承担一次查询。项目在这里放了两级缓存：一级是每个后端进程自己内存里的本地缓存（Caffeine），命中时不走网络；二级是所有实例共享的 Redis。只用本地缓存，多个实例各存一份，管理员在一个实例上改了角色，其他实例并不知道；只用 Redis，每个请求仍要多一次网络往返。两级结合，大部分请求在本地命中，本地没有时再从 Redis 取。
>
> **一次读取怎样走。** 先查本地；没有就查 Redis，查到了顺手放进本地再返回；两边都没有，才执行真正的查询方法去查数据库，再把结果写回缓存。
>
> > **并发情况**：两级缓存组件自己带有“同一个键只放一个线程去查库”的加载方式：第一个未命中的线程拿到这个键专属的锁，其他线程排队，排到后先再查一次缓存。但用户资料缓存是通过普通的缓存注解接入的，没有打开同步加载（`sync`），Spring 走的是“先读缓存、未命中就执行方法、再写回”的路径，不经过这把锁。所以某个用户的缓存恰好过期时，同时到达的几个请求会各自查一次数据库。对用户资料这种按用户分散、单条很小的读，这个代价不大。
>
> **写回和失效怎样走。** 查库得到结果后，按“先删 Redis 旧值 → 写本地 → 写 Redis → 广播通知其他实例删掉各自的本地旧值”的顺序写回。管理员改角色、停用账号时，同样删除本地和 Redis 中这个用户的条目并广播。本地条目只活 60 秒，Redis 条目活 30 分钟并上下浮动 10%，避免一批条目在同一时刻集中过期；查不到用户时也缓存一个空值 30 秒，防止有人反复用不存在的编号打到数据库。
>
> **Redis 出问题时。** 读写 Redis 都经过熔断保护，失败一律按“未命中”处理：请求继续查 MySQL，不会因为缓存故障而被拒绝。代价是 Redis 故障期间，数据库要承担本该由缓存挡住的读。
>
> 两级缓存的完整设计（为什么本地 60 秒而 Redis 30 分钟、广播丢失时的后果、项目里另外两处使用）在第 NN 篇讲。

示范与 1.4 的差别：同样的四个数字都在，但每个数字都挂在它的作用上；读者读完能回答“为什么要两级”“一次读怎么走”“同时过期时会不会一起打库”“Redis 挂了怎样”。这就是 G1 追问测试（6.1）要检验的东西。

**标杆的事实也要回源码核实。** 起草这段示范时，最初照 8.1 缓存篇写成“即使同时来了 100 个请求，也只有 1 个真正查库”。回源码核对才发现，按键加锁只在同步加载路径上生效，而用户资料缓存没有走这条路径。标杆提供的是**讲解手法和深度**，不是可以直接搬用的事实；任何写进正文的结论都要在本项目当前源码上研读确认（G4）。讲得越深，越容易在细节上出错，所以 1.5 把准确性放在底线位置，而不是放松它。

## 4. 篇目组织：链路篇 + 机制专题篇

用户确认采用“链路篇 + 机制专题篇”的混合组织。

### 4.1 两类篇的职责

| | 链路篇 | 机制专题篇 |
|---|---|---|
| 回答 | 一件业务从发起到结束怎样走完，数据从哪来、到哪去 | 一个核心机制怎样工作、为什么这样设计、在项目哪些地方使用 |
| 主干 | 按执行顺序 | 问题 → 原理 → 本项目实现 → 判断、失败与兜底 → 方案取舍 → 使用点 |
| 机制讲解 | 用到的支撑机制在原处讲 ①③⑤；用到的核心机制给够用讲解（3.5） | 对本篇主题机制完整回答七问 |
| 对应标杆 | 10.2 的认证篇、10.4 的上传篇（结构） | 8.1 的缓存全解析、流量控制与熔断 |

### 4.2 识别机制专题

满足下面任一条的核心机制，单独成为机制专题篇：

1. 被两条以上链路使用，且每处只讲够用部分会让读者始终看不到全貌；
2. 有较多需要独立讲解的原理或方案对比，嵌在任何一条链路里都会长时间打断主线；
3. 用户开工时点名。

只被一条链路使用的核心机制，在该链路篇里就地完整讲解，不单独成篇。多个小机制共享同一主题时可以合成一篇（如“限流与熔断”）。

### 4.3 识别链路篇

沿用 1.4 的入口、可观测终点、链路定义和 K04 六项打分（改变持久状态、跨系统交接、有失败处理、用户可见结果、被其他链路依赖、用户点名），以及附录 G 的技术栈映射。改动两处：

- 打分只作候选筛选的辅助，不再是成篇的唯一依据。规划时还要看“这条链路有没有值得讲的东西”：一条只做增删改查、没有机制可讲的链路，即使分数够，也可以并入相邻篇或在 00 中简述；
- 篇数不追求多。链路之间差别只在少量分支时，合成一篇按主题讲（10.2 的组织方式），比拆成多篇更利于理解。

### 4.4 篇间关系与阅读顺序

- 每个核心机制有且只有一个**主讲篇**（专题篇，或唯一使用它的链路篇），其他篇给够用讲解；
- 00 给出推荐阅读顺序。一般先读一条最能代表系统的主链路，再读它依赖的机制专题，然后读其他链路；顺序由 U-规划提出、用户确认；
- 篇与篇之间的交接（上一篇的终点 = 下一篇的起点）沿用 1.4 的衔接约定，但交接写在篇尾小结里，用一两句话说清，不再用“去哪查 / 查什么 / 看到什么算到达”的三列表格（那是取证验收的格式）。

### 4.5 00 总览与 99 复核说明

**00 · 系统总览与阅读路线**：面向第一次接触这个项目的读者，回答：

1. 系统是做什么的，谁在用，解决什么问题；
2. 系统由哪几部分组成（服务、前端、存储、外部系统），一张架构图；
3. 一两条数据主线：数据从哪里进入系统、经过哪些环节、最后到哪里，一张主线图；
4. 核心机制一览：每个核心机制一两句话说清它解决什么问题，写明主讲篇；
5. 推荐阅读路线和篇目清单；
6. 术语表（只收读者会混淆的词）。

入口清单、不覆盖表这类取证性质的内容移到 99。

**99 · 复核说明**：承接所有不进正文的准确性材料：源码基准、入口去向全表（保证全仓库覆盖）、不覆盖项及原因、未确认项及所缺证据、与 project-map 的不一致、测试覆盖情况概览。读者不读 99 也不影响理解。

### 5.2 U-规划

产出 `_规划方案.md`，包括：

1. **链路候选**：入口、终点、打分与理由（沿用 1.4 K04）；
2. **机制清单**：每个机制的名称、在哪些链路中出现、级别（核心 / 支撑 / 细节）及理由、主讲篇；
3. **篇目表**：类型（链路 / 专题）、标题、范围、不覆盖项及去向、阅读顺序；
4. **每篇的学习目标**：3–5 个“本篇回答”的问题；
5. **每篇的追问清单初稿**：按 6.1 的五个层次，覆盖本篇的核心机制和关键判断点；用户开工时给出的重点也转写成追问；
6. 全仓库入口去向（供 99 使用）。

用户确认时重点看：篇目和阅读顺序、机制级别、追问清单是否覆盖自己关心的问题。用户在这里补充的问题直接进入追问清单。

### 5.3 U-研读：理解稿替代事实摘要

**这是 1.5 管线改动的核心。** 1.4 的事实摘要把源码拆成孤立事实，禁止写“为什么”；1.5 的理解稿要求研读者先把这一篇要讲的东西真正弄懂，把理解写下来，供成文使用。

`_研读/NN.md` 的结构：

1. **流程走查**：按执行顺序，每一步写做什么、输入从哪来、输出到哪去、关键判断、失败去向、同一次还是不同次执行；附源码位置；
2. **机制卡**：每个核心机制、支撑机制一张，按七问（支撑机制按 ①③⑤）写成段落，不是一行一条。②⑥ 中需要的通用原理和备选方案分析写在这里；
3. **关键数据去向**：来源 → 传递 → 使用或校验 → 失效；
4. **追问清单与答案草稿**：对 `_规划方案.md` 中本篇的每个追问写出答案，并补充研读中发现的新追问；
5. **设计意图的出处**：意图型解释（3.7）的出处（注释、提交、文档）；
6. **取证材料**：测试覆盖、配置差异、版本迁移、未确认项、与 project-map 的不一致。这些不进正文，供 99 和审读使用；
7. **细节去向**：被定为“细节”、正文不写的内容，记一行去向，保证可追溯。

理解稿里每个事实仍要有源码位置，“为什么”的部分按 3.7 分类标明是效果型、对比型还是有出处的意图型。理解稿的篇幅不设比例，以“成文者不重读大段源码也能写出合格讲解”为准。

**上下文预算**：单元读入的源码加产出不超过上下文的一半（沿用 1.4 默认值，可后改）。超出时拆篇或把某个机制拆成专题篇，而不是少读。

### 5.4 U-成文

- 输入：本篇理解稿、`_规划方案.md` 中本篇条目、术语表、衔接约定、讲解规范和表达规范；
- **可以定点回读源码**：为了核实或补足某个机制的实现细节，回读理解稿里给出的源码位置。成文时新发现的事实，先补进理解稿（写明来源），再写进正文；
- 不读其他篇正文；需要引用其他篇时，读其理解稿的机制卡；
- 写完自查 G2、G3、G5（第 6 章）。

1.4 中“成文不得查源码”的规则是为了防止上下文涣散和凭记忆写事实。1.5 用“只读理解稿给出的位置”和“新事实先回写理解稿”实现同样的目的，同时不再切断理解的来源。

### 5.5 U-审读

新会话执行，分三轮，顺序固定：

1. **理解度（G1 追问测试）**：审读者**只读笔记正文**，逐题回答本篇追问清单，判定“答得出 / 部分 / 答不出”。然后对照理解稿检查答案是否正确。答不出或答错的问题，就是笔记的讲解缺口；
2. **准确性抽查（G4）**：对机制讲解中的关键断言（顺序、条件、失败行为、数字）回源码抽查；
3. **表达校对（G6）**：按表达规范校对，最后用“说人话”类 Skill 自检一次。

处理规则：

- 表达问题，审读者直接改；
- 讲解缺口，审读者可以补讲，但补讲涉及的事实必须先回源码核实并补进理解稿；
- 缺口大到需要重新研读（例如某个机制根本没弄懂），登记问题台账，交 dev-skills 新增研读步骤，不在审读里硬补；
- 审读不得为了顺口改变事实或结论强度（沿用 1.4 C17 的精神）。

### 5.6 U-收束

回填 00（系统总览、核心机制一览、阅读路线、术语表）；用各篇理解稿的取证材料写 99；检查跨篇一致性（术语、数字、机制主讲篇与够用讲解是否矛盾）；生成修改提示词文档。收束只改 00、99 和各篇的篇首篇尾衔接，不改各篇的机制讲解。

### 5.7 与 ruan-dev-skills、project-map 的关系（沿用）

- 长任务编排、进度、恢复全部交给 ruan-dev-skills（硬依赖，沿用 1.4 D13）；本 Skill 不另建进度机制；
- project-map 是研读的加速器：可以借鉴它的流程结构和已核实节点，但写进理解稿的事实要按 1.4 的信任分级回源码核对（沿用 1.4 第 2 章，内容缩写进 references）；
- 被分析的仓库和 project-map 只读；只提交笔记仓，不推送（沿用）；
- 源码基准变化时的处理沿用 1.4：列出受影响篇目，交 dev-skills 新增重新研读步骤。

## 6. 质量门

1.4 有 R01–R52、F01–F32、M01–M08、K01–K19 等一百多个检查 ID，全部衡量准确、覆盖和形式。1.5 换成六道质量门，**第一道是理解**。每道门写明何时执行、怎样判定、记在哪里、不通过怎么办。

### 6.1 G1 追问测试（理解）

**追问的五个层次**（来自用户提出的追问维度：校验、判断、异常兜底、具体实现、缓存、限流）：

| 层 | 问什么 | 例（通用场景） |
|---|---|---|
| L1 是什么 | 这个环节或机制做什么 | “请求进入后要经过哪几道校验？” |
| L2 怎么实现 | 具体结构、步骤、组件配合 | “限流怎样判断一个 IP 是否超过 60 秒 60 次？” |
| L3 为什么 | 为什么需要它、为什么放在这个位置、为什么要这个判断 | “为什么先查锁再比对密码？” |
| L4 出问题怎么办 | 校验失败、依赖故障、并发冲突时怎样处理，有没有兜底 | “Redis 挂了，登录还能用吗？代价是什么？” |
| L5 为什么不用别的 | 备选方案和代价 | “为什么不直接用 JWT 里的角色做授权？” |

**清单要求**：每个核心机制 L1–L5 各至少一题；每个支撑机制至少 L2、L4 各一题；流程中每个关键判断点至少一个 L3。用户在规划阶段提出的问题全部列入。

**判定**：U-审读中，审读者只读正文作答。核心机制的题目必须全部“答得出”且答案正确；其余题目“答得出”的比例不低于 80%（默认值，可后改）。

**记录**：`_审读记录/NN.md` 中逐题记录判定和正文出处。

**不通过**：按 5.5 的处理规则补讲或退回研读。

### 6.2 G2 机制讲解完整

核心机制在主讲篇中逐一对照七问，支撑机制对照 ①③⑤，链路篇中的核心机制对照够用讲解的 ①③⑤。缺失的要补，或写明为什么不适用（例如“这个机制没有备选方案可比”）。成文自查、审读复查。

### 6.3 G3 流程与数据去向

对照 3.3 的六问检查主流程；从篇尾的结果反向追，每个影响结果的关键数据都能找到来源；每个分支有去向；“同一次执行”与“不同次执行”有明确说明。成文自查、审读复查。

### 6.4 G4 准确

正文的事实都能在理解稿中找到带源码位置的条目；意图型解释有出处（3.7）；审读时对关键断言回源码抽查（每个大步至少一处，默认值，可后改）。不通过的事实退回理解稿修正后再改正文。

### 6.5 G5 不写成取证报告

可以检查的信号（脚本出候选，人判断）：

| 信号 | 判定 |
|---|---|
| 正文出现“文件路径:行号”，或测试类、测试方法名清单 | 命中（例外见 3.8） |
| 正文出现“本次未运行”“尚无真实容器证据”这类取证过程说明 | 命中 |
| 迁移号、版本号的列举不在“版本演进”补充块里，或补充块只列号不讲变化原因 | 命中 |
| 【推导】【未确认】每篇正文合计超过约 5 处 | 提示：检查是否能改写成效果型解释，或移入 99 |
| **事实堆叠**：连续约 4 句以上只陈述配置、数字、名称、分支条件，没有一句说明作用或原因 | 命中 |
| **一句话机制**：核心或支撑机制只以名称、参数出现，没有讲工作方式 | 命中 |
| **指路代讲**：写了“见第 NN 篇”，但本篇没有给出够用讲解 | 命中 |
| 某一节的补充块字数多于正文 | 提示：检查主次是否倒置 |

数字均为默认值，可后改。成文自查、审读复查。

### 6.6 G6 表达

从 B 和 1.4 写作规范中保留下面这些（实现时重写成一份不超过约 20 条的清单，不再按 R 编号拆成五十多条）：

1. 句子完整：谁对什么做了什么，结果是什么；
2. 流程中的时间、位置、执行者、对象、结果明确；
3. 用简单直接的表达，少用 AI 味词（钉死、拓扑、抓手、闭环等）和模板化转场；
4. 先说实际发生了什么，源码名放后面；首次用“直观叫法（原始名称）”，之后用直观叫法；删掉代码名后句子仍能读懂；
5. 术语首次出现时就近解释；同一对象有多个叫法时先说明它们是同一个东西；
6. 标题概括它到下一个同级标题之间的全部内容；标题不推销观点；目录能看出全文结构；
7. 主线与补充分层：补充块用稳定标签、紧跟所补充的内容，格式体现从属关系；
8. 声明了 N 步、N 层，正文逐项对应；
9. 异常、调用、数据流转写出去向：谁发出 → 谁承接 → 结果；
10. 时序区分“同一次”和“不同次”；
11. “等价、对应、就是”两侧同粒度；类比和命名描述机制实质；
12. 重要结论用加粗或提示块，每个一级节不超过约 3 处；
13. 例子优先保留；
14. 不留修改痕迹；
15. 必要的限定放进补充块，不用一连串“但是、注意、严格来说”打断正文。

审读第三轮执行，最后用“说人话”类 Skill 自检。

### 6.7 价值冲突时怎么取舍（替代 1.4 的 C1–C23）

| 冲突 | 取舍 |
|---|---|
| 讲透 vs 准确 | 讲到哪一步不确定，就回源码确认；确认不了，讲到确认为止，缺口登记 99，不编造 |
| 理解 vs 覆盖 | 次要分支可以一句带过或不写（去向记在理解稿）；核心机制的七问不能省 |
| 理解 vs 精简 | 精简只针对重复、空话、与理解无关的取证细节；不以篇幅为由删背景、原理、实现过程和例子 |
| 主线 vs 深入 | 深入讲解放在它所属的步骤里，用小标题或补充块分层，讲完回到主线；层级在格式上体现，不限制下沉层数 |
| 单篇可读 vs 不重复 | 按够用原则（3.5）：允许多篇重复够用讲解，完整讲解只在主讲篇 |
| 用户要求 vs 本设计 | 用户要求优先，在修改记录里写明偏离了哪条 |

### 10.2 实测（决定能否发布）

在 EMG 仓库上用 1.5 重新执行。实测在开发会话内完成，不经 ruan-dev-skills 初始化：按 Skill 的单元依次执行 scaffold、survey、U-规划、U-研读、U-成文、U-审读，产出放在 1.4 产出目录之外的新笔记工程（Q-6）；规划方案的“用户确认”由开发会话按本节标准自行核对并记录。dev-skills 编排路径只做结构核对（需求包、步骤拆分要求与第 8 章一致）。

1. **U-规划**：产出规划方案。检查两级缓存、限流（Redis 滑动窗口与 Sentinel）、令牌吊销等是否被识别为核心机制并有主讲篇；
2. **生成两篇**：`登录会话` 链路篇，加一篇机制专题（默认“缓存”，见 Q-5）；
3. **追问测试**：以用户在本次需求中提出的问题为必答题，例如：
   - 二级缓存具体怎样工作？一次读、一次写、一次失效分别怎样走？Redis 故障时怎样？
   - 为什么要从缓存装载当前用户，而不直接用令牌里的信息？
   - 登录请求经过哪些校验？各拦什么？为什么是这个顺序？
   - 登录失败计数与锁定怎样实现？第几次失败返回什么？
   - Redis 限流怎样计数、怎样判断超限、超限后谁返回什么？
   - 刷新令牌为什么不轮换？代价是什么？
4. **发布门槛**：上面的必答题全部“答得出”且回源码核对正确，两篇的 G1–G6 全部通过，才可以构建 `install/` 并发布。任何一项不通过，修改 Skill 后重测；仍不通过就停止发布并报告。
5. **发布后的用户验收**：把新旧两版 `01` 篇交给用户对照阅读。**用户的阅读判断是最终验收**；发现的问题作为 1.5.x 或下一版的输入，不回改已发布的 1.5.0 设计。
