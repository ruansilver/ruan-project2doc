**第 1–11 章描述的是 1.6 应有的最终状态**，不区分哪条规则原来就有、哪条是这一版才有。"相对现有文件要改什么"只出现在第 12 章的实施表和附录 C。

## 1. 定位与目标

### 1.1 交付什么

读一个软件项目的全仓库源码，写成一套中文系统学习笔记，并配一份修改提示词文档：

- **00 系统总览与阅读路线**：第一次接触这个项目的人先读它，建立系统地图；
- **链路篇与机制专题篇**：按阅读顺序逐篇讲清一条业务流程，或一个被多处使用的核心机制；
- **99 复核说明**：承接分析范围、入口去向、未确认项等核对材料，读者不读它也不影响理解；
- **修改已有笔记-<仓库名>.md**：用户读完后在里面追加要求，AI 据此修改一篇或多篇。

### 1.2 写给谁

| 读者已经具备 | 读者还不具备（笔记要补上） |
|---|---|
| 会写一般业务代码，能读懂源码 | 本项目的业务、架构、数据流和设计取舍 |
| 知道 HTTP、数据库、事务、缓存、消息队列、令牌这些名词大概是什么 | 这些技术在真实系统里怎样配合；它们内部大致怎样工作，以至于能解释"为什么这样用" |

所以笔记不解释"什么是数据库"，但要解释"这里为什么需要两级缓存""这次登录为什么要跳到另一个系统再回来"。读者不认识项目里的类名、表名、错误码，也不应该被要求先认识它们才能读懂。

### 1.3 读完一篇，读者能做到什么

1. **讲整体**：不看笔记，能说出这件事解决什么问题、有哪些参与方和核心对象、整个过程分哪几个阶段、每个阶段留下什么。
2. **讲流程**：能复述主要步骤，说清关键数据从哪里来、在哪里被校验或改变、最后交给谁；能分清哪些动作属于同一次执行，哪些是另一次。
3. **讲机制**：对核心机制，能讲出它解决什么问题、靠什么原理、本项目怎样实现、失败时怎样处理、为什么选这种做法。
4. **经得起追问**：面对"为什么要这个判断""这一步失败会怎样""为什么不用另一种做法"，能凭笔记内容再回答两三层。

这四条是全部设计的出发点，也是第 8 章质量门 G1 直接检验的对象。

### 1.4 价值排序

**准确是底线，理解是目标，可读是手段，覆盖服从理解。**

- **准确**：写进正文的每个项目事实都经当前源码核实；没有依据的设计意图不写成事实。证明材料留在理解稿和 99，不占正文。
- **理解**：用 1.3 的四条衡量。先让读者建立整体，再沿流程展开细节；冲突时宁可少写一个次要分支，也要把主线和核心机制讲透。
- **可读**：组织和措辞为理解服务。通俗化是把技术信息讲明白，不是删掉技术信息。
- **覆盖**：全仓库每个入口都有去向（成篇、简述或不展开的原因）；正文不追求穷举分支和配置。

### 1.5 触发与不适用

触发："把这个项目整理成学习笔记／业务文档／链路文档""按主流程读懂这个仓库并写成能读下去的文档""继续生成笔记""按修改提示词改一下第 N 篇""我在修改提示词里加了要求"。用户没有点名本 Skill 也适用。

不适用：单个函数或局部代码问答；建立 project-map 执行流程知识库（那是 ruan-project-reader）；API 或部署手册；需求分析；修改业务代码；没有执行链路的纯配置或纯文档仓库。识别后说明原因并停止，不降级生成一套不相符的笔记。库和 SDK 适用：公开调用、返回值、错误、回调与实例状态同样构成可讲解的执行关系。

### 1.6 通用性原则

Skill 面向任意技术栈。规则用技术栈中立的词书写（入口、终点、状态、机制、交接）；规则文件中的正反例只说明写法，不代表目标项目有这些组件；从样本估出的数字一律标"默认值，可后改"。运行时不修改 Skill 本身，项目特有要求写进该项目的修改提示词文档。

### 1.7 本版的设计依据

本版依据一次实际调查：通读了 1.4、1.5 设计与 1.5 全部规则、模板、脚本和测试；检查了用户笔记工程中 nanyang（21 篇）、ruan-rag（10 篇）、EMG（1 篇）的实际产出；阅读了按 1.5 规则实测生成的两篇笔记及其审读记录；复核了用户历次修改要求。方法、样本与统计见附录 A。下面五条结论决定了本设计的重点。

**结论一：用户正在阅读的三套笔记，执行的是 1.4 规则。** 三个工程的需求包（规则 10 份、模板 11 份、工具脚本）与 1.4 发布内容逐文件一致，工作区也是 1.4 的交接物。这些工程在 1.5 发布前建成，长任务此后一直按归档的需求包执行，本机升级到 1.5 并没有改变它们。两点含义：其一，这批笔记里的证据索引、测试证据块、推导标签、入口编号等取证格式，是 1.4 规则要求的产物，1.5 已经不再要求——1.6 要做的是守住这一点，而不是重新修复；其二，用户和执行者都需要一眼看出"这个工程按哪一版规则生成"，所以需要一个轻量的规则版本标识（§9.6）。

**结论二：按 1.5 规则实测生成的笔记，机制深度已经达标，结构和措辞问题仍在。** 实测样本里已没有取证格式，机制有因果、有走查、有失败行为。但仍然：全貌很薄，一张图把四次独立请求画成一条链；进入流程第一步后立刻展开几十行限流细节，读者还没看到这件事整体长什么样；二级标题多是论点句；全文十几处"不能据此断言……"式的否定句；罕见的边界细节与主干同权。

**结论三：结构问题的第一根源，是生产过程里没有任何一步把"理解"组织成"讲述"。** 研读产出流程走查、机制卡等素材，却没有整篇的讲述设计。成文时，文章结构实际沿用了素材的排列顺序，也就是阅读源码的顺序，而不是读者建立认知的顺序。

**结论四：结构问题的第二根源，是质量检查测不到它。**
- 追问清单全部是机制级的题，没有一道要求读者复述整体；其中大量是"为什么不能……""是否等于……"这种审稿人视角的题。由于通过条件是"只凭正文答得出"，正文就被写成每道题都有一句现成答案——那些"不能把 X 当成 Y"的否定句正是这样来的。
- 承担"独立读者"的是 AI。AI 在再密的文本里也能检索出答案，实测第一轮全部题目都被判为"答得出"。这道检查实际测的是"答案在不在"，不是"读者读不读得懂"。
- 结构要求（目录能还原结构、每节能复述、由浅入深）被压缩成表达规范里的几条，放在最后一轮校对，且由作者一方逐条自判。实际记录里，命中"目录不能当内容地图"后以"与前两篇保持一致"为由保留不改；检查"是否有具体例子"时，把几个数字的存在当成了有场景例子。

**结论五：措辞问题有四个来源。** ① 旧规则要求的取证格式残留；② 上面说的应试效应；③ 没有任何对名称密度和句子压缩的检查——最难读的两篇，正文每 10 行约 9 个内部名称，较易读的几篇约 2 个；④ 修改时用文字补丁冒充修复——17 篇笔记的图后被批量补上同一段"读图时分清四类关系"，其中 7 篇声称"菱形是条件分支"，而图里根本没有判断节点。

**归因。** 上述问题不全是规则的责任：

| 来源 | 具体表现 |
|---|---|
| 规则缺陷 | 没有讲述设计这一产物；质量门只测局部机制；结构规则没有可操作的检查；缺少图、密度、压缩句方面的要求 |
| 执行偏差 | 研读、成文、审读被合并在同一会话连续执行，独立读者名存实亡；审读期间正文仍在变化；把每篇的教训不断追加到接力状态里，而不是回到规则 |
| 项目复杂性 | 多入口、多套状态机、未接通的外部适配、默认关闭的能力；个别篇的范围过大，读者负荷超载 |

复杂性不是删细节的理由；本设计的做法是让细节有层次、有位置。

### 1.8 范围与非目标

范围：定义完整的 1.6 Skill。重点是三件事——在研读与成文之间加入讲述设计；给出全篇、章节、小节三层的组织规则与措辞规则；让质量门能够测到整体理解、组织和表达。

非目标：不改变编排方式（长任务仍交给 ruan-dev-skills）；不增加生产单元和质量门的数目；不设逐条检查编号体系；不按项目定制规则；不以字数、标题数、图节点数或禁词数量判定质量；不强制所有主题写成线性流程；不自动迁移已有笔记工程。

## 2. 工程结构与边界

### 2.1 笔记工程目录

```text
<仓库名>-笔记工程/               普通目录，不执行 git init
  笔记/                          独立 Git 根（只提交，不推送）
    00-系统总览与阅读路线.md
    NN-标题.md                   链路篇或机制专题篇
    99-复核说明.md
    修改已有笔记-<仓库名>.md
    _工作区/
      _勘察结果.md
      _规划方案.md
      _术语表.md
      _衔接约定.md
      _问题台账.md
      _研读/NN.md                理解稿
      _审读记录/NN.md
  需求包/                        交给 ruan-dev-skills 的需求源
    00-任务说明.md
    01-规划方案.md
    02-步骤拆分要求.md
    规则/                        本版 references 副本
    模板/                        本版 templates 副本
    工具/project2doc.py
  docs/AI dev docs/              ruan-dev-skills 管理的独立资料仓
```

笔记仓充当 ruan-dev-skills 所说的"代码仓"；需求包位于资料仓之外，不含空目录、符号链接和敏感信息。目录名和文件名都是默认值，可后改。

### 2.2 每类文件承担什么信息

| 位置 | 应保存的内容 |
|---|---|
| 00 | 系统解决什么问题、由什么组成、一两条代表性主线、核心机制一览、阅读路线、易混淆术语 |
| 单篇正文 | 全貌、按组织方式展开的过程与机制、影响理解的条件与失败、必要数据结构、例子、小结、代码地图 |
| 规划方案 | 链路候选、机制分级与主讲篇、篇目与组织方式预判、学习目标、阅读顺序、追问清单、入口去向、确认记录 |
| 理解稿 | 已理解并核实的过程与机制、事实来源、追问答案草稿、核对材料、未展开内容，以及**讲述方案** |
| 审读记录 | 独立读者的原始复述与答案、初读障碍、核真结果、修改位置与复验、六道门结论 |
| 99 | 源码基准、入口全表、未展开原因、未确认项、与 project-map 的差异、测试与运行核对范围、审读概览 |
| 修改提示词文档 | 固定规范、项目口径、用户追加的要求、变更记录 |

### 2.3 硬边界

1. 源码仓与 project-map 只读：不改代码、状态或未决，不在其中运行写入命令；所有产出写入独立的笔记工程。
2. 只提交笔记仓，不推送；资料仓由 ruan-dev-skills 管理。长任务的步骤、进度和恢复全部交给它，本 Skill 不另建同类机制。
3. 不为表达顺畅改变事实、条件或结论强度。新事实先核实并写入理解稿，再进入正文。
4. 不在运行时修改本 Skill。
5. 对不适用场景说明原因后停止。
6. 两个确认点由用户做出：规划确认、每篇审读通过后的确认。已有明确授权时按授权范围执行并记录依据；生成文件或脚本成功不等于用户确认。

### 2.4 依赖与缺失处理

| 依赖 | 用途 | 缺失时 |
|---|---|---|
| Git | 笔记仓提交、源码基准核对 | 停止并说明 |
| ruan-dev-skills 2.0 | 长任务编排 | 停止并说明，不自建替代 |
| Python 3.8+（仅标准库） | 辅助脚本 | 如实记录脚本未执行，人工完成相应检查 |
| project-map（可选） | 研读导航 | 提示一次后按入口与终点发现继续，不降低要求 |
| "说人话"类 Skill（可选） | 表达自检 | 人工按表达规范检查并如实记录 |

### 2.5 调用类型与开工确认

| 类型 | 识别与动作 |
|---|---|
| 首次生成 | 尚无已确认规划：勘察 → 规划 → 用户确认 → 交接编排。已有材料先核对后继续，不覆盖 |
| 继续生成 | 已有 dev-skills 接力提示词：读取它，按当前步骤恢复，只推进该步骤 |
| 执行编排步骤 | 以步骤文件和归档需求包为准，读本单元指定的规则与交接物 |
| 修改已有笔记 | 按第 9 章处理修改文档中待处理的要求 |

开工时核对仓库路径与分析基准（默认 HEAD）、输出目录（默认仓库同级）、用户重点；用户已提供的直接沿用，只补问影响工作的缺项。分析范围固定为全仓库。

## 3. 讲解：一篇笔记必须讲清什么

### 3.1 两种讲解单元

一篇笔记由两种讲解交织而成：

- **流程讲解**：一件事从开始到结束经过哪些环节，数据怎样流动、状态怎样变化；
- **机制讲解**：流程中某个环节依赖的一套做法怎样工作、为什么这样设计。

流程是骨架，机制讲解放在它被用到的那一步里。

### 3.2 流程六问

| 问题 | 必须讲清什么 |
|---|---|
| 起点 | 谁、在什么场景下发起，带着什么数据来 |
| 校验 | 经过哪些校验，每项拦什么情况，为什么放在这个位置 |
| 处理 | 经过哪些环节，每个环节做什么、产生什么、交给下一步什么 |
| 判断 | 在哪里分叉，依据什么数据判断，各分支去哪里 |
| 状态与落点 | 哪些状态被改变，数据最终写到哪里 |
| 接手 | 谁接着处理；是同一次执行，还是另一次（另一个请求、线程、事务或进程） |

### 3.3 机制七问

| # | 问题 | 合格的样子 | 不合格的样子 |
|---|---|---|---|
| ① | 它解决什么问题 | 说出没有它时，在什么具体情形下出现什么坏结果 | "为了提高性能" |
| ② | 靠什么原理起作用 | 讲到足以理解当前实现的最小原理 | 只写组件或算法的名字 |
| ③ | 本项目怎样实现 | 结构、关键步骤的顺序、参与者怎样配合；给一个能在脑中跑一遍的小场景 | 只列组件名和参数值 |
| ④ | 关键判断与分支 | 每个判断保护什么条件，不同结果各去哪里 | "加锁后进行双重检查" |
| ⑤ | 失败时怎样处理 | 校验不过、依赖出错、并发冲突时，谁处理、留下什么、调用方看到什么、代价是什么 | 不写，或只写"有异常处理" |
| ⑥ | 为什么这样设计 | 与更简单或常见的做法相比，效果和代价各是什么 | 不写，或写成没有依据的意图 |
| ⑦ | 有什么局限 | 在什么条件下不起作用或会出错 | 把所有理论风险列一遍 |

七问是内容要求，不是七个固定标题。确实不适用的写明原因；没查清不能写成不适用。**组件有某种能力，不等于当前使用点走了这条路径**：读、写、失效这类操作，要沿真实调用点分别确认配置、注册、调用分支、事务与异常捕获范围。

### 3.4 关键数据

决定分支、用于身份或权限或去重、写入持久存储、跨组件传递、参与最终结果的数据，都要讲清：谁创建 → 保存在哪 → 怎样传到这里 → 谁读取或校验 → 何时改变或失效。外部提供的数据追到责任方与当前接收点即可，不猜外部实现。写完流程后从结果向前倒查一遍。

多份记录容易混淆时，先说明它们各代表什么，再给必要的表名、关键字段与关联关系。例如"一次登录尝试""本地员工绑定""已建立的会话"是三样不同的东西，不能统称"一行身份记录"。

下面这些实现细节在影响理解时必须保留：创建与使用发生在不同请求时，数据靠什么关联；哪些写入在同一事务内，失败时哪些会回滚、哪些外部副作用不会；状态迁移由谁在什么条件下触发；并发时锁住什么对象、解决什么竞争；同名概念是否指不同对象。

### 3.5 机制分级与跨篇够用讲解

| 级别 | 判据（满足任一） | 讲解要求 |
|---|---|---|
| 核心 | 承担安全、一致性、可靠性或性能等关键质量目标；被两条以上主流程依赖；容易被直觉误解；用户点名 | 在主讲篇完整回答七问；在其他用到它的篇给够用讲解 |
| 支撑 | 在流程中有独立作用，但主要服务一两处 | 在用到的地方至少回答①③⑤ |
| 细节 | 不改变读者对流程或机制的理解 | 一句带过或不写，去向记在理解稿 |

**够用讲解**：读者不翻其他篇，也应理解当前流程为什么这样走。链路篇用到别篇主讲的核心机制时，在用到的那一步回答①（在这条流程里它解决什么）、③（在这条流程里它怎样工作）、⑤（在这条流程里失败会怎样），再用一句话指向主讲篇，说明那里还会讲什么。不允许只给名称、参数或数字再写"见第 NN 篇"。不同篇的够用讲解可以重叠；完整讲解只在主讲篇。

"两条以上"是默认值，可后改。不得为省篇幅把用户关心的机制降级。

### 3.6 通用原理讲到哪里

讲到足以理解本项目为什么这样用、和备选做法差在哪为止。检验方法：把这段原理删掉，读者是否还能理解后面的实现与取舍？能，说明多余；不能，说明必要。技术历史、完整接口手册、与当前用途无关的特性不讲。

### 3.7 "为什么"的三种写法

| 类型 | 例子 | 写法 |
|---|---|---|
| 效果型：这样做带来什么效果、避免什么问题 | "先检查锁再比对密码，已被锁定的来源不会再消耗一次密码计算" | 直接陈述。它是可以从行为验证的因果 |
| 对比型：换成另一种做法会怎样 | "只用本机缓存，多个实例各存一份，一个实例改了角色，其他实例不知道" | 直接陈述 |
| 意图型：作者当初为什么选它、在什么背景下引入 | "这个限制是某次事故后加上的" | 有注释、提交记录或项目文档作出处才写；没有出处就改写成效果型或对比型 |

理解稿记录每个解释属于哪一类及其依据；正文不贴分类标签，也不写"这是效果型解释，不代表作者意图"这类说明。

### 3.8 事实、原理与示例要分清

正文里有三种性质不同的陈述，读者必须分得出来：

| 陈述对象 | 可以怎样写 | 不可以怎样写 |
|---|---|---|
| 当前项目的行为 | 有源码和实际调用依据，写明成立条件 | 把未接通的适配器、默认关闭的功能、其他路径的能力写成当前保证 |
| 通用原理或协议的标准做法 | 明确这是理解项目所需的背景，再与当前实现分别对应 | 把标准的完整流程补画成当前实现 |
| 教学示例 | 用虚构的人物、编号、数值走查已核实的规则，标明"假设""示意" | 把示例值写成生产参数，把模拟运行写成真实实测 |

**教学示例是被鼓励的。** 用"张三登录车间系统"这样的假设场景帮助读者建立认知，比回避举例更好。项目没有接通某项外部能力时，仍然可以用概念场景解释它的职责，只需先说明这是示例，并明确指出当前实现实际停在哪里。不能到篇尾才补一句"实际没实现"。

涉及标准协议或框架行为、而仓内材料不能确认时，查阅与所用版本对应的官方资料，依据记在理解稿。不用未经核实的外部知识填补项目事实的缺口。

### 3.9 讲解手法

| 手法 | 起什么作用 |
|---|---|
| 从问题起步 | 读者先知道这个机制要对付什么，后面每个设计都有着落 |
| 原理紧挨实现 | 读者知道这种结构为什么适合这个问题 |
| 朴素方案 → 缺陷 → 改进 | 读者理解的是"为什么必须这样"，不只是"代码是这样" |
| 写出结构和顺序 | 读者能在脑中执行一次 |
| 用小场景和具体数字检验规则 | 把抽象规则变成可检验的结论 |
| 故障与代价一起讲 | 读者知道依赖出问题时系统的真实表现 |
| 收成全景并说明局限 | 把分散的机制连成整体，不把方案讲成完美 |
| 提前拆掉常见误解 | 防止读者凭直觉建立错误模型 |

这些手法只借讲法；写进笔记的事实一律回目标项目的当前源码确认。

### 3.10 什么不进正文

| 内容 | 去处 | 什么时候可以进正文 |
|---|---|---|
| 文件路径加行号、方法签名清单 | 理解稿；篇尾代码地图只列关键文件或类及其职责，不写行号 | 读者很可能要立刻跳过去看的一两处 |
| 测试覆盖与运行情况 | 理解稿、99 | 测试过程本身是解释某个行为的最好例子时，讲成例子，不列测试名 |
| 迁移号、版本号罗列 | 理解稿 | 版本演进能解释当前设计时，讲"旧做法 → 问题 → 新做法" |
| 未确认项、与其他资料的冲突 | 理解稿、99 | 不说明就会让读者建立错误模型时，用一句话交代 |
| 核验过程、来源编号、入口编号 | 理解稿、99 | 不进正文 |

准确性没有降低：这些材料都在，只是不以正文为载体。

### 3.11 代码片段与篇幅

代码片段只在它比叙述更直接时使用（关键配置、几行核心算法、状态转换）。先用自然语言讲清，再给片段；删掉片段正文仍能读懂。单段一般不超过约 15 行，每篇一般不超过约 5 段，均为默认值。

笔记与理解稿都不设篇幅上限或比例。每一段都应服务理解：删重复、空话和无关的核验细节；保留必要的背景、原理、过程、例子和取舍。

## 4. 组织：怎样安排一篇笔记

总原则：**先流程，后重点；先骨架，后细节；先建立因果关系，再解释实现机制。**

### 4.1 三个层次各自的职责

| 层次 | 读者在这里得到什么 | 要求 |
|---|---|---|
| 全篇 | 这件事是干什么的、谁和什么参与、整体怎么走、文章按什么顺序展开 | 先建立可复述的整体模型，再进入细节 |
| 章节 | 现在处于整个过程的哪一步，这一步要产生什么 | 每个主要章节承担一个明确的问题或阶段；标题概括其全部内容 |
| 小节 | 这一步内部的具体过程，以及其中机制怎样运转 | 先走通过程，再展开细节；细节讲完接回主线 |

三个层次执行同一顺序：**先让读者知道"在做什么、结果是什么"，再回答"怎么做、为什么这样做"。** 术语和背景在读者第一次需要它的位置给出，不提前堆放。

### 4.2 篇首与全貌

正文开始处，要让第一次接触本项目的读者建立一个可以复述的模型。固定包含：

1. **一句话主线**：用具体场景或问题开头，说清这件事为谁解决什么问题。不写"本篇介绍某某模块"。
2. **本篇回答的问题**：三到五个具体问题，篇尾小结逐一回答。
3. **前置与关联**：建议先读哪篇；本篇用到的核心机制由哪篇主讲。
4. **全貌一节**（正文第一个一级章节），依次包含：
   - 业务背景：谁、在什么场景下、要得到什么结果，两三段以内；
   - 参与方与核心对象：系统内外有哪些参与者，哪些对象把各环节连起来；容易混淆的对象在这里区分开；
   - **全流程走查**：用一段连续的文字把这件事从发起到结果走完——谁先做什么、留下什么、下一步谁接手。可以先粗后细，但必须真实、连贯，读者据此就能复述；
   - 一张或一组全景图（规则见 §4.7）；
   - 术语与落点表：只收理解本篇模型必需的叫法，说明"在本文指什么"，源码名单独一列；
   - 一个贯穿全篇的示例：具体的人或对象、编号、时刻、数字（规则见 §3.8）。

**先建立整体，不等于画一张塞满细节的大图。** 全貌必须能被直接复述；完整的失败清单、全部配置项、全部字段不放在这里。但如果一条与默认配置有关的结论会改变读者对"这条流程能否走通"的判断（例如"默认配置下这条链会停在失败"），它必须出现在全貌或一个标题能找到的小节里，不能只藏在后文的补充块中。

### 4.3 组织方式按主题选择

不强制所有内容写成线性流程。

| 一篇的主题 | 主要组织方式 | 必须讲清的关系 |
|---|---|---|
| 一次业务或一次数据处理 | 按执行流程的大阶段 | 每阶段的输入、执行者、结果与交接；请求、线程、事务或进程在哪里改变 |
| 一个对象的建立、使用、变更、终止 | 按生命周期 | 谁在什么条件下触发；哪些操作可选、可重复、可互相替代；不是每次都依次发生 |
| 一组部件或职责的协作 | 按职责与边界 | 谁调用谁、交换什么、状态由谁管理；依赖关系不等于时间顺序 |
| 一个横切机制（专题篇） | 问题 → 原理 → 实现 → 失败 → 取舍 → 使用点 | 哪些能力由机制提供、哪些由使用方决定；适用与失败的范围 |

一篇有一个主组织方式。局部换一种方式时，在切换处用一句话说明关系，例如"下面是凭据已经建立之后，两种各自独立触发的处理"。**不能只因为代码属于同一模块、接口前缀相同，就把管理动作、查询接口、初始化和异常恢复与业务步骤编成同一串步骤。**

### 4.4 内容类别决定位置

| 内容 | 位置与层级 | 不允许 |
|---|---|---|
| 主流程的必经步骤 | 主要章节的主干，按真实顺序 | — |
| 条件分支与判断 | 所属步骤内部，和主路径同样清楚，各分支的去向写明 | 省略；或升格成与阶段并列的章节（除非分支本身就是主题） |
| 被多处共用的横切机制 | 在第一个需要它的使用点给够用讲解；完整讲解放主讲篇 | 在流程开始之前集中罗列全部机制和门禁 |
| 独立触发的操作（重发、轮换、撤销、重放、人工恢复等） | 集中成独立章节，先说明触发条件，以及它和主流程对象的关系 | 伪装成主链的下一步；与必经步骤混编成一条编号链 |
| 旁路与辅助面（只读查询、配置管理、其他入口） | 独立章节，放在主线之后；开头一句说明它和主线的关系 | 插在主线中段打断阅读（除非理解当前步骤确实需要它） |
| 异常与失败出口 | 影响当前步骤理解的就地讲；完整的失败清单放在该步骤之后 | 在正常流程之前集中展开；整篇零散分布 |
| 默认配置与当前限制 | 改变全篇结论的，进全貌或独立小节；局部的，紧邻相关步骤 | 只出现在补充块或 99 里 |
| 实现细节（字段、格式、算法内部） | 读者需要它才能理解当前动作时，放在该步骤的下级 | 以细节开篇；与主线同权 |
| 测试证据、版本演进、核验过程、源码位置 | 理解稿与 99；正文只保留影响理解的结论 | 作为正文内容 |

### 4.5 章节与标题

**核心标准：读者通过标题能看懂整体脉络，通过正文能理解执行过程，通过逐层展开能深入掌握具体实现。** 所有篇目的每个章节都必须满足。

**每个章节先建立清晰、完整的逻辑主干，再围绕主干逐层展开技术实现细节。** 主干负责讲清执行流程、步骤之间的关系和因果逻辑；实现细节负责解释每一步怎样实现、为什么这样设计。主干、子流程、技术实现和补充说明不能全部平铺在同一层级，要按它们真实的逻辑从属关系组织。

章节规则：

1. **同级同依据**：同级章节使用同一种划分依据（阶段、对象、职责或机制）；换依据时要有上位分组或一句清楚的说明。
2. **节首交代位置**：每个主要章节开头用一两句话说明读者现在在哪、已经拿到了什么、这一节要产生什么。纯结构主题说明本节解释哪类职责或关系。写成自然的句子，不机械套用"输入／处理／输出"标签。
3. **多层级递进拆解**：一个章节可以拆成 3.1、3.2；其中某一步内容复杂，再拆成 3.1.1、3.1.2；必要时继续细化。不预设固定的层级深度，层级跟着内容的逻辑从属关系走——子流程从属于它所在的步骤，技术实现从属于它所解释的动作，补充说明从属于它所补充的内容。
4. **层级由内容决定，不为排版强行拆分**：有独立逻辑关系的内容（一个子流程、一个机制的内部、一类独立的处理）使用子标题；同一逻辑下的简单并列细节用列表或段落表达，不为了显得有层次而拆出只有一两句话的小节。
5. **细节放在它所解释的步骤下面**：实现细节紧跟它解释的那一步，在该步骤之下按需要逐层展开。不为了简化结构删减必要的实现细节，也不把全部细节集中堆放在章节末尾。
6. **深入内容出现的时机**：锁、哈希、事务、并发、异常这类内容，放在读者已经知道这一步的正常过程之后；讲完说明此时的结果，以及下一步由谁接手。
7. **复杂子流程单独建骨架**。满足任一条件即算复杂：跨两个以上参与方或执行体；含三步以上有先后依赖的动作；涉及多份记录的状态变化；它的产物是后续章节的输入。做法：先用一小段把子流程走完（谁 → 做什么 → 产生什么 → 交给谁），再分点展开校验、写入、并发与失败；结束处说明留下的状态和接手者。
8. 层级不断加深以致掩盖主线时，重组章节职责或拆出专题，而不是继续加标题。

标题规则：

1. **每一级标题承载逻辑职责**：准确说明这一部分在整体执行流程或技术机制中的作用，概括从它到下一个同级标题之间的全部主要内容。不随意摘取其中一个技术细节充当标题。
2. 一节包含多个并列内容时，用它们共同的上位概念命名，不挑其中一个局部结论代替整节。
3. 大标题范围大，小标题逐级收窄；小标题同样概括自己下面的全部内容，不退化成一句正文结论。
4. 优先用"对象 + 行为／流程／状态／机制"命名；不用具体实现手段充当上位主题；不用数量充当标题的主体（"五个状态、四个动作"）。
5. 慎用"必须""真正""关键是"这类推销式句式；重要结论放在正文里加粗或用提示块。
6. **目录检验**：只读一至三级标题，应能恢复文章的整体结构和执行过程（或主题结构）。如果目录读起来像一串知识点、结论或数量，就重新调整标题体系。
7. 先看正文实际包含什么，再命名标题；不先想好标题再让正文迁就。

### 4.6 小节内部：三层内容

| 层 | 是什么 | 怎样呈现 |
|---|---|---|
| 主干 | 执行流程、步骤之间的关系与因果逻辑：决定主要结果的动作、关键分支、不可省的前提 | 正文段落，单独读就是完整的过程 |
| 深入 | 每一步怎样实现、为什么这样设计：结构、顺序、机制内部 | 紧跟所解释的步骤，用下级标题或引导段展开，可以多层递进，讲完接回结果 |
| 边界 | 次要的失败与并发细节、设计取舍的补充、版本演进、当前局限的细节 | 紧跟相关步骤的补充块，使用稳定标签：异常情况、并发情况、设计取舍、版本演进、当前局限 |

纪律：

1. **折叠检验**：把深入小节和边界补充块遮住，剩下的文字必须仍然是完整、连贯、正确的过程描述。不满足，就把必要内容提回主干，或补一句承接。
2. **补充块只放可以跳过的内容**。任何会改变"这条流程能否走通、结果是什么"的事实——默认配置下的停点、未接通的外部依赖、失败时整笔回滚——属于主干或独立小节。
3. 深入内容是讲解的主体：有独立逻辑关系的用下级标题承载，同一逻辑下的简单并列细节用列表或段落；都不放进补充块，也不集中堆到章节末尾。
4. 补充块紧跟它所补充的步骤；块里出现的名词，紧邻正文已经解释过，否则在块内就地补一句。
5. 正常流程与极端情况的分量通过层级体现：并发竞态、依赖故障、部分失败可以写得详细，但在结构上不与正常流程平起平坐。
6. 密度提示（默认值）：补充块平均每 20 行超过一个，或某一节补充块的字数多于主干时，检查主线是否被切碎、主次是否倒置。
7. 同一结论不反复强调；多轮补充之后重新检查能否精简。

**按内容的性质选择 Markdown 表达形式**，让执行步骤、技术细节、约束条件和补充说明一眼可辨：

| 内容 | 适合的形式 |
|---|---|
| 逻辑主干、子流程、机制内部 | 多级标题；标题层级表示逻辑从属关系 |
| 有先后顺序的执行步骤 | 有序列表 |
| 同一逻辑下的并列细节、条件、字段 | 无序列表；项目多或需要逐项对照时用表格 |
| 对照、状态转换、数据对应关系 | 表格，并在表外用一句话说明怎样读 |
| 约束条件与补充说明 | 引用块加稳定标签 |
| 关键结论 | 加粗或提示块 |
| 很长但可以跳过的清单 | 必要时使用 HTML 标签（如折叠块） |

形式服务于辨认，不为排版堆砌：同一种性质的内容全篇用同一种形式；不用表格或列表代替对过程的讲解。

### 4.7 图

按要回答的问题选图：架构图表达组成与依赖，流程图表达动作与条件分支，时序图表达跨参与方的往返，状态图表达生命周期。不要求每篇集齐图种。

1. **全景图画什么**：主要参与者或执行体、主要阶段、关键结果、必要分支。不放字段值、错误码、配置键、SQL、表名清单。承载语义的关键数字可以保留（如"5 分钟内有效"）。复杂的局部另画细图，不让一张图同时充当接口目录、字段清单和失败清单。
2. **关系类型与画法一致**：同一次执行内的先后、条件分支、并行或独立触发的活动、独立检查，各用可以区分的画法。同一张图不用同一种边同时表示执行先后、调用、数据交接和依赖；必要处在图上注明边的含义。
3. **另一次执行要标出来**："之后的每个请求""对端随时发来的回执""回调""人工重放""定时任务"不属于当前这次执行，要在图上标明，不能让读者读成主链的下一步。跨参与方有多次往返时，优先用带参与方的时序图。
4. **图例与图一致**：图里没有判断节点，就不说"菱形是条件分支"；没有虚线，就不说"虚线是失败出口"。
5. **修图优先于补说明**：如果必须靠一段文字才能说清"图上相接的两步其实不是先后""这一格其实是另一次执行"，说明图需要改——调整布局、拆图，或在图上加注记。不允许在图后附一段通用的读图说明来代替改图。
6. 当前实现、模拟实现与概念示意不画成同一条真实调用路径。
7. 有可用渲染器时实际渲染修改过的图并检查可读性；没有时如实记录人工做了哪些语法与关系核对。

### 4.8 00 总览

00 是读者在读各篇之前和之间使用的系统地图，内容为：

1. 系统解决什么问题：谁在用、处理什么业务对象、解决什么实际问题；
2. 系统由什么组成：一张架构图，说明应用、存储、外部系统之间的关系；
3. 一件事怎样流过系统：一两条代表性主线，说明数据从哪里进入、怎样变化、最后交给谁；
4. 核心机制一览：每个机制一两句话说明解决什么问题，注明主讲篇；
5. 推荐阅读路线与篇目表；
6. 易混淆术语。

要求：

- **规划阶段就要达到最低可用**：第 1、2、5 项，以及第 3 项至少一条主线的文字走查（图可以后补），随规划一起交用户确认。第 4、6 项随各篇补充。
- 每篇成文完成时，把本篇已核实、属于 00 的内容（主线简述、机制一览、易混术语）补进 00，只动与本篇有关的部分。
- 不留空节、"以后回填"的占位说明或未兑现的承诺。尚未核实的内容明确写"待研读后补充"，或暂不设该节。
- 三种关系不混在一张图里：组成与依赖用架构图；数据或状态怎样走用主线图；先读哪篇用篇目表说明。用篇号作图时，先声明箭头表示阅读接续还是依赖。
- 入口清点、配置穷举、核对口径不放在 00，归 99。

### 4.9 两类篇的骨架

骨架可以按内容调整，不是填空表。

**链路篇**

```text
# NN · <对象与过程>

> 本篇回答：<3–5 个具体问题，篇尾逐一回答>
> 前置与关联：<建议先读哪篇；本篇用到的核心机制由哪篇主讲>

<一句话主线>

## 一、全貌
   业务背景；参与方与核心对象；全流程走查；全景图；术语与落点；贯穿示例
## 二…N、<主体章节，按讲述方案确定的组织方式>
   节首：现在在哪、已拿到什么、这一节产生什么
   主干 → 深入（下级标题，可按内容继续拆成 N.1、N.1.1）→ 边界（补充块）
## <独立触发的操作、旁路与辅助面>（需要时，各自成章）
## 设计取舍与局限（可选：把分散的取舍连成整体）
## 本篇小结      逐一回答篇首问题；说明留下什么结果、谁接着处理
## 代码地图      关键文件或类及其职责，不写行号
```

**机制专题篇**

```text
# NN · <机制名>：<它解决的问题>

> 本篇回答：<3–5 个具体问题>
> 使用它的流程：<相关链路篇>

## 一、问题起点      没有它会怎样；哪些流程共同需要它
## 二、需要先知道的原理（够用即止）
## 三、本项目怎样实现  先给结构或交互图和一次完整走查，再按关键操作分节
## 四、关键判断、失败与兜底
## 五、为什么这样设计  备选做法与代价
## 六、在项目中的使用点
## 本篇小结
## 代码地图
```

### 4.10 讲述方案

**讲述方案是研读交给成文的结构设计**，写在理解稿里（§7.4），只在这一处维护。成文以它为骨架，审读对照它检查组织。

```markdown
## 讲述方案

组织方式与理由：<按执行流程 / 按生命周期 / 按职责与边界 / 按机制；一句话说明为什么>
读者先要建立的模型：<参与方、核心对象、它们的关系>
全流程走查：<用一段话把这件事从发起到结果讲完，成文时用于全貌一节>
贯穿示例：<贯穿全篇的人、对象、编号与关键数字；或说明本篇不需要>
哪些内容不是同一次执行：<独立请求、回调、定时任务、管理操作、后续流程，各是什么>

| 章节（暂定标题） | 本节回答什么 | 读者进入本节时已经知道什么 | 本节产物，与前后节的关系 | 深入与边界内容放在哪里 |
|---|---|---|---|---|
| …… | …… | 上一步的产物 / 独立触发 / 共同依赖 | …… | 主干就地讲 / 下级小节 / 补充块 / 留给主讲篇或 99 |

复杂子流程：<只为确有多参与方、多状态或明显嵌套的部分，列出内部步骤和出口；没有就写"无">
```

要求：

- 它把已经核实的内容**组织给读者**，不复制机制卡，不逐条抄事实。
- 章节的划分与顺序，以"读者先建立什么、再理解什么"为准，不以素材在理解稿里的排列顺序为准。
- "全流程走查"写不出来，说明研读还没有完成。
- 成文时可以按实际内容调整标题、合并或拆分章节，但要同步更新讲述方案，并在成文自查里记录调整了什么。

## 5. 措辞：怎样把话说明白

总原则：**先说对象和行为，再放名称；先讲是什么、解决什么问题，再讲怎样实现；把抽象动作展开到读者可以复述。** 通俗化不删技术细节，只改变呈现方式。

### 5.1 三个检验

1. **去名检验**：删掉一段话里的源码名、字段名、错误码，这段话仍应能读懂"发生了什么"。
2. **复述检验**：读完一个章节，读者能用一两句话说出"这部分在做什么、核心过程是什么、主要对象之间是什么关系"。说不出，是这一节的骨架有问题，应先修结构，而不是换词。
3. **首用检验**：每个陌生的概念、缩写、内部名称，在第一次真正用到的地方说明了"它是什么、在这里做什么"。

### 5.2 术语与名称

- **首次解释**：类、方法、组件、字段、状态名、配置键、错误码、缩写，第一次真正使用时说明含义或职责。只翻译缩写不算解释——"幂等键用于幂等"不合格，要说明"调用方用它标识同一次请求，服务端据此识别重复提交；键相同而内容不同时拒绝"。
- **直观叫法（原始名称）**：确实需要对应代码时，首次用这个格式，之后优先用直观叫法。有自然、准确的中文说法就用中文；已经普遍使用、翻译后反而难懂的术语不硬翻。
- **保留源码名的四种情形**：帮助读者回到代码定位；区分多个相似对象；名称本身就是接口或数据结构的一部分；翻译会丢失准确含义。其余情形，删掉不影响理解就不保留。
- **同一对象有多个叫法**时，先说明它们指同一个什么东西；跨篇叫法由术语表统一。
- **错误码**：首次出现时说明"什么情况下出现、调用方看到什么"。只在一处出现、对理解没有帮助的错误码，直接描述行为，不写名称。
- **配置键**：只在"这个开关影响读者对流程的判断"时出现，并说明默认值的作用。成串的配置键放表格或留在理解稿。
- **状态值**：属于读者要建立的模型时，集中成状态表或状态图，并把每个状态翻译成后果（例如"还能不能自动往下走"），不在句子里零散出现。
- **数量声明配清单**：写了"共 N 项""七条规则""十一个引用"，就给出逐项清单或表格，且数目与清单一致。不能只报数量让读者自己数。
- **密度参考值**（默认值，可后改）：一个自然段里的内部名称一般不超过约 5 个；全篇正文平均不超过约每 10 行 4 个（表格、代码块、代码地图不计）。超过时改用表格、括注，或先解释再命名。

### 5.3 把抽象动作展开

重要动作检查五项：**执行者、对象、条件、实际操作、结果**。缺什么补什么，不要求每句话都填满。

| 遮住过程的写法 | 应当展开的方向 |
|---|---|
| "服务负责处理回执" | 谁收到回执，用什么标识找到待处理的记录，校验什么，最后把状态改成什么 |
| "进行校验" | 比较哪两个值，为什么比较，不一致时由谁拒绝，这时是否已经写入数据 |
| "建立关联" | 哪两种记录，用哪项身份对应，关联保存在哪里，下游怎样使用 |
| "完成收口" | 谁得到什么结果，把哪条记录置为什么状态，之后还能不能重试 |
| "冻结上下文" | 把当时的哪些值复制到哪份记录，后续为什么读这份副本而不读现值 |

判断标准是读者能否复述出"谁对什么做了什么、结果是什么"，不是见到这些词就替换。读者已经理解的业务术语可以沿用；缺过程时，换成另一个抽象词不算修复。

描述异常传播、调用和数据流转时写完整：谁发出 → 谁承接 → 承接后发生什么。不用"冒泡、落到、交给"就停下。

### 5.4 因果与背景

- 通常的顺序是：是什么、解决什么问题 → 为什么需要 → 怎样执行 → 关键实现、失败与取舍。这是认知顺序，不是每节都要有的四个固定标题。
- 关键判断解释它防止的具体坏结果；顺序有作用就说明作用；取舍写出代价。不要求每条显然的赋值都附一段动机。
- 写"为什么"按 §3.7；举例按 §3.8。
- 贯穿示例在一篇内保持一致；跨篇复用同一个示例时，名称、数值和含义保持一致。

### 5.5 限定与否定的写法

- **正面表述优先**：直接写出正确的模型（"读共享缓存失败时按未命中继续；写入、删除、通知失败时，已完成的动作各自保留"），不用一串"不能把 A 当成 B"来代替。
- 确实需要澄清一个读者会自然产生的误解时，用一句"是 X，不是 Y"说清，同一条界限全篇只说一次。
- 写给读者的区分保留，写给审稿人的防御删去。判断方法：这句话是在告诉读者系统怎样运行，还是在声明"作者没有过度概括"？后者改写为对现状的直接陈述，或移入理解稿。
- 必要的限定放在对应的补充块或一句清楚的说明里，不在一个结论后面连续追加"但是、注意、严格来说"。
- 会改变读者对行为理解的未知，在相关位置用一句话说明（例如"这里只能确认向外抛出了异常，最终响应还取决于容器的处理"）；不为了干净把重要的未知藏进 99，也不反复讲调查过程。
- 提示（默认值）：全篇"不能……断言／认为／当作／等同／概括／套用"式的句子超过约 6 处时，逐句判断属于上面哪一种。

### 5.6 句子

- 一句话里塞进多个条件、多个动作或多个时间点时，拆成连续的两三句。保持主语和对象稳定，用上一个动作留下的结果接下一个动作。
- 四项以上并列的条件或字段，改成列表或表格，并在表外用一句话说明怎样读。
- 区分同一次执行和不同次执行：重试、重放、异步交接、事务提交后的动作都明确交代。用表格表示时序时，给出次数、时刻或阶段这样的显式维度，不靠行的先后暗示。
- 声明了 N 步、N 层，正文逐项对应；子话题用下级编号，不占用同级编号。
- "等价、对应、就是"的两侧保持同一粒度。命名和类比要说出机制的实质；类比不贴切就改成对象之间的普通关系描述。
- 删去没有信息的转场（"上一节已经……""明确……之后，本节继续……"）和装饰性词语；能直接进入内容就直接进入。相邻环节之间带信息的衔接（上一步的产物就是这一步的输入）要保留。
- 重要结论可以加粗或用提示块，每个一级章节通常不超过约 3 处（默认值）。
- 保留有帮助的小场景、具体数字、失败例子，以及用户自己写的有效解释。
- 不留修改痕迹："修正后""重新核验发现""此前有误"不出现在正文；被否定的内容彻底移除，不换一种限制说明继续留着。
- **表达修改不改变数字、条件、先后、执行范围、失败行为或结论强度。** 不能把"尝试""某条路径""可能"润色成"保证""所有""一定"。

## 6. 篇目规划

### 6.1 入口、终点与链路

- **入口**：外部能触发本项目代码开始执行的位置，例如一次用户操作、公开函数调用、消息到达、定时触发。写实际触发点，不只写模块名。
- **终点**：这次执行留下的、可以独立检查的结果，例如响应、返回值、持久记录、文件、下游消息、稳定的界面状态。写具体结果，不只写"处理完成"。
- **链路**：从一个或多个入口出发，沿真实的调用和交接关系，走到这样一个终点的执行路径。

先正向找入口，再从返回、写入和外部交接反向找终点，两边对照补漏。后台清理、订阅回调、定时任务、工作线程也是入口，都要登记去向。规则文件中保留按项目形态整理的入口与终点线索表（HTTP 或 RPC 服务、消息或任务服务、前端应用、移动客户端、数据或模型管道、命令行工具、库或 SDK、多端或单仓多项目）；它只是发现线索，最终以目标项目的代码为准。

### 6.2 分数辅助筛选

每条候选链路按六项各记 0 或 1 并写理由：改变持久状态；跨进程或跨系统交接；有失败处理、重试或补偿；产生用户可见结果；终点被其他链路依赖；用户点名。

默认参考：3 分及以上是独立成篇的候选；1–2 分优先并入相关篇或在 00 简述；0 分登记为不展开并写原因。分数只辅助筛选：分数够但只有简单增删改查的链路可以合并；分数低但能解释重要机制的链路可以独立成篇；差别只在少量分支的链路按主题合并。所有入口的最终去向进 99。

### 6.3 机制定级与主讲篇

按 §3.5 给每个机制定级，级别依据写进机制清单。每个核心机制有且只有一个主讲篇。

满足任一条件的核心机制单独成为机制专题篇：被多条链路使用，每处只讲够用部分会让读者始终看不到全貌；有较多需要独立讲解的原理或方案比较，放进任何一条链路都会长时间打断主线；用户点名。只被一条链路使用的核心机制，在该链路篇里就地完整讲。多个小机制属于同一主题时可以合成一篇。

### 6.4 组织方式预判与读者负荷

- 为每篇预判组织方式（§4.3）和主要对象，写进篇目表；研读后可以修正，理由记在规划里。
- **读者负荷**：一篇的主体宜为"一条主线"或"一个对象的生命周期"。如果一篇要读者同时记住两套以上的状态机、三条以上互不依赖的流程，或清点大量并列的入口和命令，优先拆篇、拆出专题，或把其中一部分降为简述加去向。这是判断而不是硬限制，取舍写进规划。
- 篇数不追求多，也不为凑整齐而合并。

### 6.5 阅读顺序与学习目标

阅读顺序通常是：先读一条最能代表系统的主链路，再读它依赖的机制专题，然后读其他链路。按读者需要调整，不按源码目录排序。每篇写三到五个"本篇回答"的具体问题。

### 6.6 追问清单的设计

追问清单在规划时写成，研读时写答案草稿，审读时由独立读者作答。

**每篇必须包含：**

1. **一道整体复述题（必答）**："不看笔记，说明这件事解决什么问题、由谁发起、按什么顺序经过哪些阶段、每个阶段留下什么、最后交给谁。"
2. **关键子流程复述题（必答，复杂篇一到两道）**："把〈某个过程〉从开始到结束讲一遍，说清每一步谁对什么做了什么、结果是什么、失败由谁处理。"
3. **机制追问**，按五个层次：

| 层 | 问什么 | 通用例子 |
|---|---|---|
| L1 是什么 | 这个环节或机制做什么 | 这几步分别拦住什么情况？ |
| L2 怎样实现 | 结构、步骤、组件配合 | 一条记录怎样写入、读取、更新和失效？ |
| L3 为什么 | 判断、顺序和条件的作用 | 为什么先检查状态，再执行昂贵的操作？ |
| L4 出问题怎么办 | 校验、依赖、并发失败后的结果与代价 | 依赖不可用时，谁继续、谁拒绝、什么能力减弱？ |
| L5 为什么不用别的 | 备选做法与代价 | 只保留一层，或把两步合并，会有什么差别？ |

   每个核心机制 L1–L5 各至少一题；每个支撑机制至少 L2、L4 各一题；流程中每个关键判断至少一题 L3。跨篇使用的核心机制，题目只问本篇读者必须理解的部分。

4. **用户提出的问题**全部纳入。

**出题纪律：**

- 从读者要建立的理解出发，问结果和关系。题干不把正确的阶段名、对象关系或答案的结构写进去。
- "为什么不能……""是否等于……"这类界限题，只用于读者确实容易混淆的地方，每篇一般不超过约 3 道（默认值），不用来凑层次覆盖。
- 一道题可以覆盖多个要求，不为凑数重复出题。

### 6.7 规划的产物与确认

`_规划方案.md` 记录：链路候选及打分理由；机制清单、级别与主讲篇；篇目表（类型、标题、范围、组织方式预判与主要对象、不覆盖项及去向、阅读顺序）；每篇学习目标；追问清单；全仓库入口去向；确认记录。同时产出规划期的 00（§4.8）、术语表初稿和衔接约定。

规划内容可以包含待研读核实的候选，但不能把候选写成已经确认的机制保证。

向用户展示篇目与阅读顺序、机制级别与主讲篇、组织方式预判、学习目标、追问清单、规划期的 00，以及用户重点落在哪里。**得到用户确认后**，记录日期和调整内容，才进入交接。研读发现范围或关键认识变化时，先更新规划；涉及篇目或用户重点的实质调整，按授权范围确认后交 ruan-dev-skills 调整后续步骤。旧规划不能反过来限制源码结论。

## 7. 生产流程与交接物

### 7.1 总表

| 单元 | 做什么 | 主要产物 | 满足这一条才往下走 |

每篇的研读、成文、审读是三个步骤，按确认的阅读顺序推进，各在新的会话中执行。任何步骤都不把"文件存在"当作质量门通过，不把脚本退出码当作用户确认。

单元读入的原始材料加产出，默认不超过可用上下文的一半（可后改）。装不下时调整篇目或拆出机制专题，交编排处理；不以少读关键源码换取完成。

### 7.2 U-勘察与 project-map

U-勘察只读目录树、构建信息、基准提交和 map 状态，不在这里装入全部业务源码。结果写入 `_勘察结果.md`，其中记录本工程使用的规则版本（§9.6）。

project-map 是导航材料，可以提供流程候选、入口与终点、节点的源码位置；它不决定笔记篇目，不能代替理解机制。使用规则：

| map 内容的情况 | 怎样使用 |
|---|---|
| 基准过期，且相关文件已变化 | 只作线索，回当前源码重新核实 |
| 节点或候选标为待核实、阻塞，或所在模块有限制 | 先读限制与未决；受限制的内容按待核实处理 |
| 模块仍在梳理或待验收 | 结构可以参考，事实回源码核实 |
| 模块已完成且相关内容没有未决 | 可作理解稿的来源线索和起草基础，仍参加抽查 |

必须回源码核对的：上表前三类内容；关键数据的来源、状态变化和全部数字。其余借鉴的事实，每个主流程大步至少抽查一处（默认值）；抽查不一致，该模块其余借鉴事实全部改为必须核对。当前源码优先，冲突写进理解稿并汇总到 99，不回改 map。map 的图、候选表、状态表不搬进正文。

### 7.3 U-规划与交接编排

规划按第 6 章执行。用户确认后按第 10 章准备需求包并初始化编排。正常的首次调用到编排"可接力"为止，不继续进入研读。

### 7.4 U-研读：先自己弄懂，再设计怎么讲

按本篇范围沿真实执行关系读源码，写成理解稿 `_工作区/_研读/NN.md`：

1. **流程走查**：按执行顺序，每一步做什么、输入从哪来、输出到哪去、关键判断、失败去向、是否换了一次执行；附源码位置。
2. **机制卡**：每个核心机制按七问、每个支撑机制按①③⑤写成可以连读的段落，含必要的原理、备选分析和走查例子；区分组件能力与业务实际走的路径。
3. **关键数据去向**：来源 → 传递 → 使用或校验 → 更新与失效。
4. **追问与答案草稿**：逐题回答规划中的问题，含整体复述题与子流程复述题；研读中发现的必要追问回写规划。
5. **设计意图出处**：每个"为什么"属于效果型、对比型还是有出处的意图型，后者记录注释、提交或文档位置。
6. **核对材料**：测试覆盖与运行情况、配置差异、版本演进、未确认项、与 project-map 的差异。
7. **细节去向**：不进正文的细节及其去向。
8. **讲述方案**：按 §4.10。
9. **成文中的补充研读与成文自查**：成文阶段填写。

每个事实有源码位置，因果分析写明前提。理解稿的完成标准：**下一位作者只读这份理解稿，不必重读大段源码，就能写出合格的文章骨架并讲清机制。** 不写成孤立的一行一条，不限制与正文的篇幅比例。

### 7.5 U-成文：按讲述方案写

输入：本篇理解稿（含讲述方案）、规划条目、00 的相关背景、术语表、衔接约定、规则文件和对应篇型模板。不读其他篇的正文；需要讲别篇主讲的机制时，只读那一篇理解稿里的相关机制卡。

步骤：

1. **先写骨架**：按讲述方案写出各级标题、全貌一节，以及每个章节的节首段。检查两件事：只看目录能否还原过程或主题结构；把各节首段连起来读，能否讲成一条连续的线。骨架和讲述方案不一致时，先决定改哪一个，再让两者一致。
2. **再展开**：逐节补入主干、深入和边界内容，执行第 3–5 章的规则。不按理解稿的条目顺序搬运。
3. **回读与新事实**：可以定点回读理解稿标明的源码位置。成文中新发现的事实，先补进理解稿并注明来源，再写进正文。需要大范围重新探索，说明理解稿没有完成，退回研读。
4. **回填 00**：把本篇已核实、属于 00 的内容补进 00（§4.8）。
5. **成文自查**，结果写在理解稿末尾：
   - G2、G3、G5（第 8 章）；
   - 运行 `skeleton` 查看自己的骨架视图，做目录检验和节首检验；
   - 对全篇最复杂的两三处做折叠检验（默认值）；
   - 运行 `lint`，逐条处理候选或写明保留理由。

自查不能代替审读中独立读者的结论。

### 7.6 U-审读：三轮

**读者与正文版本。** 独立读者必须是没有接触过本篇理解稿、源码和成文过程的会话或 agent。如果当前会话做过本篇的研读或成文，就另起一个独立 agent 承担读者，并且只给它规定的输入。审读开始前冻结正文版本（提交号或内容哈希），第一轮期间不修改正文。读者的设定是 §1.2 的目标读者：不用源码、理解稿、其他篇或一般常识补答案，正文没讲清的地方如实标出。

**第一轮：独立读者，只接触正文。** 分三个阶段，每个阶段先保存原答再进入下一阶段：

| 阶段 | 读者拿到什么 | 读者做什么 |
|---|---|---|
| A 骨架复述 | 只有骨架视图：篇首块、全貌一节全文、其余各级标题及每个标题下的第一段 | ① 讲出这件事的全貌：解决什么问题、参与方与核心对象、过程分哪几个阶段、每个阶段留下什么、谁接手；② 逐章说出这一章讲什么、处在整个过程的什么位置；③ 指出哪些内容不是同一次执行；④ 列出凭骨架判断不了的关系 |
| B 通读复述与初读障碍 | 正文全文 | ① 用自己的话完整复述；② 按阅读顺序写出初读障碍清单 |
| C 逐题作答 | 追问题面（没有答案） | 逐题回答，标"答得出／部分／答不出"，给出正文出处 |

初读障碍清单记录读者在第一次顺序阅读时卡住的地方，约 20 条以内，优先记最影响理解的：

- 没有解释就使用的术语、缩写、内部名称；
- 读完说不出"谁对什么做了什么、结果怎样"的句子；
- 断掉的关系：前面提到而后面没有交代，或突然出现的对象；
- 读到这里才发现缺的前置信息；
- 条件或数字过密、需要反复回读的句子。

读者可以回看正文，这不是记忆测试。

**第二轮：核对者，可以读理解稿和源码。**

1. 对照理解稿和源码判定阶段 A、B 的复述与阶段 C 的答案是否正确（G1）。答案正确但来自读者的外部知识、正文没有对应内容的，算文章缺口。
2. 回源码抽查关键断言（G4），复查 G2、G3、G5。
3. **修复顺序：先结构，再事实，最后表达。** 骨架或复述暴露的组织问题先处理：更新讲述方案，重组章节，再改正文。

**第三轮：表达校对（G6）。** 在结构稳定的正文上进行：先处理初读障碍清单里还没解决的条目，再按第 5 章逐节校对，最后用可用的"说人话"类 Skill 自检；没有该能力时人工检查并如实记录。

**修改权限与复验：**

- 表达问题，以及不改变含义的结构调整，审读中直接改。
- 需要新事实的小缺口：先回源码核实并补入理解稿，再补讲。
- 大缺口（机制没弄懂、讲述方案需要重做）：登记 `_问题台账.md`，交 ruan-dev-skills 新增研读或成文步骤，不在审读里凭记忆硬补。
- 复验规则：章节增删、顺序调整、全貌重写、标题体系变化之后，冻结新版本，**换一位新的独立读者**重跑阶段 A；全文组织变化时同时重跑阶段 B 的复述。局部补讲或改写，复验受影响的追问和障碍条目。首次结果与复验结果分开保留，不把原判定直接改成通过。
- 没有可用的独立读者时，G1 不能记为通过：如实标为"待独立读者验证"并告知用户。用户本人的阅读结论可以作为读者证据。

三轮结果集中记在 `_审读记录/NN.md`。

### 7.7 U-收束

- 补全 00，使六项内容完整、与各篇一致。
- 用各篇理解稿的核对材料写 99：源码基准与检查范围、全仓库入口去向、未展开的内容及原因、未确认项、与 project-map 的差异、测试与运行核对概览、各篇审读结果。
- 跨篇检查：术语、数字；核心机制的主讲篇与使用篇是否矛盾；篇与篇之间的真实交接；跨篇共用示例的名称、数值、含义是否一致；同一事实在不同篇的说法是否一致。
- 运行 `consistency --final`，生成修改提示词文档。

收束只改 00、99 和各篇的篇首篇尾衔接。发现正文的事实或讲解问题，登记后返回对应步骤，不在收束里改。问题台账不得留有未处理项；需要用户决定的项写清影响与确认结果。阶段性产出如实说明已完成哪些篇，不写成全仓笔记已经完成。

### 7.8 恢复、源码变化与执行方式

- 中断后按 ruan-dev-skills 的接力提示词和当前步骤恢复，再读该单元需要的交接物。`progress` 只辅助核对产物与提交。
- 源码基准变化时，列出受影响的篇目，交编排新增重新研读步骤；先更新理解稿、术语与衔接、必要的规划，再重新成文和审读。不把不同基准的事实混进一篇。
- 用户要求在同一会话连续推进多个步骤时，可以照办，但要如实记录这一偏离；质量门的判据不因此改变，独立读者仍由受限输入的独立 agent 承担。
- 每篇写作中得到的教训，属于本项目的写进修改提示词文档的项目口径区（§9.5）；接力状态只记编排状态，不积累写作规则。

| `_问题台账.md` | 编号、质量门、优先级（P0 错误事实、P1 结构或理解缺口、P2 局部表达）、篇、问题、源码依据、状态（open、fixed、needs_user_decision）、处理说明 |
| `_研读/NN.md` | §7.4 |
| `_审读记录/NN.md` | 正文冻结版本、规则版本、独立读者标识与每阶段输入；阶段 A、B、C 的原答；判定与核对依据；G4 抽查表；G6 的问题与修改位置；六道门汇总；问题处理与复验；用户确认 |
| 99 | §7.7 所列各项 |

## 8. 质量门

六道门检查同一个结果：笔记准确，读者能讲清整体、流程和机制。成文自查 G2、G3、G5；审读按 §7.6 的三轮执行 G1–G6。各门全部通过后才进入该篇的用户确认。

### 8.1 G1：读者能否讲清整体并回答追问

| 证据 | 通过条件 |
|---|---|
| 阶段 A 骨架复述 | 全貌、各章职责和"哪些不是同一次执行"没有重要错误。不把独立触发的操作说成必经步骤，不把跨参与方的多次往返说成一次请求，主要阶段与产物正确 |
| 阶段 B 通读复述 | 完整复述没有重要错误：阶段顺序、对象关系、执行边界、关键结果正确 |
| 初读障碍清单 | 逐条处理：修改正文，或写明保留理由；同一类障碍成批处理 |
| 阶段 C 逐题作答 | 必答题（整体复述题、子流程复述题、用户指定的问题）与核心机制的题全部答得出且正确；其余题答得出且正确的比例不低于 80%（默认值） |

**骨架复述或通读复述不通过时，机制题全部答对也不能通过。** 80% 的比例不能抵消错误的主线、错误的状态关系或未经核实的保证。

记录：正文冻结版本、读者标识与输入范围、三个阶段的原答、逐题判定与正文出处、核对依据、缺口与复验。

### 8.2 G2：机制讲解完整

核心机制在主讲篇逐一对照七问；支撑机制，以及链路篇用到的别篇主讲的核心机制，对照①③⑤。逐个机制记录正文位置。内容都在但零散得拼不成一个机制，也算不通过。确实不适用的写原因；没查清退回研读。

### 8.3 G3：组织与流程

**组织检查**，逐项记录结论和依据：

1. 实际组织方式与讲述方案一致；各类内容的位置符合 §4.4（独立操作、旁路、横切机制没有被排成主链步骤）。
2. 标题职责与目录检验：每一级标题说明该部分在流程或机制中的作用、概括其全部内容；只读一至三级标题能还原执行过程或主题结构；同级同依据。
3. 多层级递进与内容一致：主干、子流程、技术实现和补充说明出现在各自应有的层级上；子标题由独立逻辑关系产生，同一逻辑下的并列细节用列表或段落，没有为排版强行拆分。
4. 节首检验：每个主要章节开头交代了位置和产出。
5. 细节位置与表达形式：实现细节紧跟它所解释的步骤，没有集中堆放在章节末尾；正文形式（标题、列表、表格、引用块）与内容性质匹配，执行步骤、技术细节、约束条件和补充说明一眼可辨。
6. 折叠检验：抽查最复杂的两三处，遮住深入与边界内容后，主干仍完整可读。
7. 复杂子流程有自己的骨架，结束后接回主线。
8. 会改变全篇结论的事实不只出现在补充块里。
9. 图：图例与实际图形一致；关系类型画法正确；另一次执行已标出；图、正文、小结对同一件事的描述一致。
10. 声明的数量与清单一致。

**流程与数据去向检查：** 沿六问正向走查，再从结果反向追关键数据；每个影响结果的数据有真实来源，每个分支有承接者和结果；同一次执行与不同次执行分清；覆盖本篇实际存在的跨请求、线程、事务、进程边界，以及容易混淆的对象。

组织检查靠阅读完成；`skeleton` 和 `lint` 只帮助定位。

### 8.4 G4：事实与结论强度准确

正文事实能在理解稿里找到带源码位置的解释；意图型解释有出处。每个大步至少抽查一处关键断言（默认值），优先核对生成时机、实际接线、事务与失败范围、跨组件交接和重要数字。发现错误时，先修理解稿，再改正文，并扩大检查到共享同一前提的断言、图和追问答案。主文、图、小结对同一事实冲突时，不能各自通过。教学示例抽查两点：示例遵循已核实的规则；示意性质已标明。未知的范围如实保留，不把设计预期、协议示意或模拟行为写成已实现的能力。

### 8.5 G5：正文承担讲解

运行 `lint` 取得候选，再人工判断；脚本没有命中不代表通过。

| 信号 | 怎样判断和处理 |
|---|---|
| 路径加行号、测试类或方法名清单 | 移到理解稿；少数立即跳转有助理解的位置可以保留并记录理由 |
| "本次未运行"之类的核验过程说明、入口编号、来源编号 | 移到理解稿和 99 |
| 迁移号、版本号堆列 | 移到理解稿；确需讲版本演进时，讲旧做法、问题与变化原因 |
| 解释性标签合计超过约 5 处 | 检查能否改写成经核实的效果型解释，或把不影响理解的未知移到 99 |
| 连续约 4 句只写配置、数字、名称或条件 | 把事实组织成机制：补作用、原因和步骤，不只是删数字 |
| 机制只有名称和参数 | 补足问题、工作方式与失败行为 |
| 写了"见第 NN 篇"而本篇没有够用讲解 | 在使用处先补①③⑤，再指向主讲篇 |
| 某一节补充块多于主干，或补充块过密 | 检查主次是否倒置、主线是否被切碎 |
| 数量声明没有清单 | 补清单，或去掉数量声明 |

数值都是默认值。正文中属于业务概念的"证据""冻结""快照"等词不按关键词删除。

### 8.6 G6：表达

在结构稳定的正文上，按第 5 章逐节检查：过程是否说完整；术语是否在首次使用处解释；名称密度；因果是否具体；限定与否定的写法；句子是否过度压缩；有无模板转场和修改痕迹。记录实际问题与修改位置，以及保留候选的理由。结构问题归 G3，不在这一门处理。表达修改不改变事实和结论强度。"已运行风格检查 Skill"不能代替逐节检查。

### 8.7 问题分级与处理

| 问题 | 处理 |
|---|---|
| P0 错误事实或虚假保证 | 回源码，修理解稿和全部相关的正文、图、答案，复验；不通过不得交付 |
| P1 结构或理解缺口（复述不通过、主线错误、机制缺口） | 已有事实足够时，先更新讲述方案再重组；依据不足时退回研读；整体结构变化后重跑骨架复述 |
| P2 局部表达问题 | 原位改写，检查原义和受影响的追问 |
| 仅为个人措辞偏好 | 可以保留，不做无限润色 |

任何一道门不通过，都要指明是规则执行问题、理解缺口还是资料不足，并登记需要返工的单元；不用平均分或其他门的通过来抵消。

### 8.8 冲突取舍

| 冲突 | 取舍 |
|---|---|
| 深度与准确 | 不确定就回源码；确认不了就讲到已确认处，缺口记 99，不编造 |
| 理解与覆盖 | 次要分支可以简述或留在理解稿；核心机制的七问不能省 |
| 理解与精简 | 删重复、空话和无关的核验细节；保留背景、原理、过程和例子 |
| 主线与深入 | 改变位置、层级或篇目来安放深入内容，而不是删掉它 |
| 结构与表达 | 先把结构改对，再润色句子 |
| 示例与事实 | 以事实为准；示例调整或移除 |
| 单篇可读与跨篇重复 | 使用篇保留够用讲解，完整讲解由主讲篇承担 |
| 用户要求与固定规范 | 按用户要求执行，在变更记录里写明偏离了哪条规范 |

## 9. 修改已有笔记与既有工程

### 9.1 修改提示词文档

`笔记/修改已有笔记-<仓库名>.md` 分四区：固定规范区（本版的讲解、组织与措辞要点）、项目口径区、用户追加区、变更记录。

只处理用户追加区里状态为"待处理"的行。填了目标篇就只改这些篇；没有填时，根据术语表、规划中的主讲篇和衔接约定列出受影响的篇及理由，取得用户确认后再改。已有明确的范围授权直接沿用。

### 9.2 先判断缺口在哪一层

收到阅读反馈时，先把它转成一个可以回答的问题，并判断缺口在哪一层。不预设"看不懂"只是措辞问题。

| 缺口层级 | 典型反馈 | 处理 |
|---|---|---|
| 整体模型与组织 | "不知道整体怎么走""章节混乱""标题看不出顺序" | 更新讲述方案，重组全貌和章节（§9.3 的结构修改路径） |
| 章节职责或子流程 | "这一节读不下去""看不懂这个过程" | 更新讲述方案的相关条目，重组该节；给子流程补骨架 |
| 机制讲解 | "讲不清它怎么工作" | 判断缺的是背景、原理、实现、判断、失败还是取舍；必要时补研读，再在原位置补讲 |
| 术语或句子 | "这个词不懂""这句读不通" | 就地补解释或改写 |
| 事实 | "这里和代码不一致" | 回源码核实，先修理解稿，再改正文 |

用户指出的那一处要改；同一个缺口是否在本篇其他位置也存在，一并检查。补充要服务当前问题，不借机扩展成无关主题。

### 9.3 修改路径与复验

| 修改范围 | 执行方式 |
|---|---|
| 一篇之内，纯表达，或不改变含义的结构调整 | 当前会话处理，复验后写变更记录并提交笔记仓 |
| 涉及事实、讲解依据，或涉及多篇 | 交 ruan-dev-skills 调整模式：在资料仓之外新建需求材料目录（修改提示词副本、修改说明），由它归档并安排步骤；涉及事实的先安排研读 |

修改规则：

- 直接在原位置修正或补讲；原处确实容不下，才在附近另起层次。
- 错误的内容彻底删掉，不把它改写成新的限制或提醒继续保留。
- 保留用户为了理解而写的解释和例子；只要没有错误和明显重复，优先在原有表达上优化。
- 修改既做加法也做减法。正文不留修改过程的痕迹。

复验：

- 结构类修改完成后，按 §7.6 的复验规则重跑阶段 A（必要时连同阶段 B 的复述）。
- 其他修改：复验受影响的追问（G1），核对 G2、G3；涉及事实时执行 G4；再检查 G5、G6。
- 结果记入对应的审读记录，不只写"已修改"。

### 9.4 修改必须落在实处

- **每一处"已处理"，都要能指到实际改动的文字。** 只增加一段解释性说明（例如在图后补一段通用的读图说明）、只声明"已有背景，未再改动"、只改标题不改内容，都不算完成。
- 结构问题按结构修：图的关系画错了就改图；章节职责混乱就重组章节；标题不能概括内容就调整标题体系。补一段文字说明"其实不是这个顺序"，不能代替把它改对。
- 批量处理多篇时逐篇记录：改了哪些节、结构是否变化、复验了什么。没有改动的篇如实写"未改动"和理由，由用户决定是否接受。
- 变更记录写明：日期、对应的用户要求、目标篇与位置、缺口层级、改动类型、复验结果、理解稿是否更新、偏离的规范（如有）、笔记仓提交。完成后把该行状态改为"已处理"。

### 9.5 项目口径、用户选择与回流

- 项目口径区记录本项目的篇目与阅读路线、源码位置与基准、术语索引、未确认项索引，以及项目特有的约定（问题、适用范围、正反例、生效日期）。
- 用户可以在项目口径区打开默认关闭的内容：每篇的"面试怎么讲与高频追问"章节（内容取自已经验证的追问，不编造经历）、版本演进叙述、更深的原理展开。
- 用户要求优先于固定规范；偏离之处在变更记录里用普通文字说明。
- 反复出现的项目特有问题只在本项目生效；是否并入 Skill 由用户决定。不另建检查编号体系，不在运行时修改 Skill。

### 9.6 既有工程与规则版本

- **一个笔记工程从建立起，一直使用它归档的那一版规则。** 本机安装新版本不改变已经归档的任务。
- 新建工程时，`00-任务说明.md` 和 `_勘察结果.md` 写入"规则版本"（如 `ruan-project2doc 1.6.0`）。审读记录也记下实际使用的规则版本。
- 继续一个已有工程时，先读它归档的规则版本，与当前安装的版本对照。不同就在开工时用一句话告诉用户："这个工程按 X 版规则继续；要使用 Y 版规则，需要另建工程。"不混用两版规则，不把旧规则的产出称为新版的结果。没有版本字段的工程报告为"未标注（早于 1.6）"，不自行推定是哪一版。
- 要用新版规则重做已有的笔记：另建新的笔记工程。旧工程的笔记和工作区材料只作线索，用法同 project-map（§7.2）——可以借它定位和导航，写进正文的事实回当前源码核实。不移动、改名或覆盖旧工程的文件。

## 10. 需求包与编排交接

### 10.1 建工程

```bash
python "<SKILL>/scripts/project2doc.py" scaffold --project "<工程>" --repo-name "<仓库名>"
```

`scaffold` 初始化笔记仓，放入 00、99 和工作区的共用交接物，创建空的 `_研读/`、`_审读记录/` 目录；在需求包里复制本版的规则、模板和工具，放入任务说明与步骤拆分要求模板，并写入规则版本。已有文件不覆盖。按篇的文件在相应单元从模板复制。

### 10.2 确认规划后的需求包

| 文件 | 内容 |
|---|---|
| `00-任务说明.md` | 学习目标与读者；只读源码仓与基准；project-map 状态；输出位置；用户重点；规则版本；说明代码仓是笔记仓、初始步骤只记基线；源码变化后的重新研读安排 |
| `01-规划方案.md` | 用户确认后的 `_规划方案.md` 完整副本 |
| `02-步骤拆分要求.md` | 每篇研读、成文、审读三个步骤及各自的输入、读取边界、输出、完成判据；审读步骤的下一动作是"等待用户确认第 NN 篇"；最后是收束 |
| `规则/`、`模板/`、`工具/` | 本版 references、templates 与辅助脚本的副本 |

步骤文件用"需求包编号 + 归档内相对路径 + 标题"引用规则，以 ruan-dev-skills 实际返回的归档结构为准。每个步骤写明本次要读的规则，不要求通读全部副本。写作规则放在需求包里，不写进 dev-skills 的固定协议和接力提示词。

步骤拆分中各单元的读取边界：

| 单元 | 输入 | 读取边界 |
|---|---|---|
| U-研读 | 本篇规划、相关源码、相关 map 节点、术语与衔接、规则 | 围绕本篇的流程和机制读源码，不整仓重读 |
| U-成文 | 理解稿（含讲述方案）、本篇规划、00 相关背景、术语、衔接、规则、篇型模板 | 可定点回读理解稿标明的源码；不读其他篇正文 |
| U-审读 | 第一轮：骨架视图 → 正文 → 题面；之后：理解稿、相关源码、规则 | 独立读者不得提前接触理解稿、源码和答案 |
| U-收束 | 各篇首尾、理解稿的核对材料、术语、衔接、台账 | 只改 00、99 和各篇首尾衔接 |

### 10.3 初始化编排

前提：规划已确认，三份需求文件已填好，笔记仓已有骨架提交。以 `<工程>/笔记/` 为工作目录，加载已安装的 ruan-dev-skills，用初始化模式提供需求材料目录和版本目录；由它初始化资料仓、归档需求、规划步骤，直到状态为"可接力"。第一个步骤只记录笔记仓基线、源码基准和依赖检查结果，不虚构业务构建结果。在 Windows 上运行它的脚本时使用 `python -X utf8`；具体参数以当前安装的 dev-skills 说明为准。

### 10.4 最终汇报

生成时报告：工程位置、源码基准、map 状态、规则版本、已确认的规划与实际完成的篇目、各篇质量门结果与未决项、编排目录与下一动作。阶段性产出不写成全仓笔记已经完成。

修改时报告：改动的篇与位置、缺口层级、补足了什么、复验结果、理解稿是否更新、笔记仓提交；走编排时说明新需求包与步骤。

## 11. 辅助脚本

`<SKILL>/scripts/project2doc.py`：只用标准库，支持 `--json`，在 Windows 中文路径下可用，需求包内的副本可以独立执行。**脚本只检查结构、给出候选，不能证明读者理解、事实正确或表达合格。** 脚本出错、语义不通过、用户确认是三种不同的状态，不能互相替代。

| 命令 | 作用 |
|---|---|
| `deps` | 只读检查 Git、ruan-dev-skills 和表达检查能力 |
| `survey --repo R [--map M]` | 只读检查源码基准、map 状态、技术栈和规模 |
| `scaffold --project P --repo-name N` | 创建笔记仓、骨架和需求包副本，写入规则版本；不覆盖已有文件 |
| `progress --notes N --version-dir V` | 只读对账编排步骤、笔记提交与产物；不管理进度 |
| `consistency --notes N [--final]` | 只读检查交接物结构 |
| `lint --file F [--words W ...]` | 只读列出 G3、G5、G6 的候选 |
| `skeleton --file F [--out O]` | 只读输出骨架视图 |
| `render-revise --notes N --repo-name R` | 新建四区修改提示词文档；已存在则拒绝覆盖 |

**`skeleton`**：输出篇首块（标题、本篇回答的问题、前置与关联、一句话主线）、第一个一级章节的全文、其余每个一至三级标题及其下的第一个自然段；不含其余正文和代码地图。供审读阶段 A 和成文自查使用。`--json` 另给出标题列表和图的位置。

**`lint` 的信号**（全部是候选，带行号和原文片段；阈值是默认值）：

| 信号 | 判定 |
|---|---|
| G5-行号引用、G5-测试名称、G5-取证过程 | 路径加行号；测试类或方法名；"本次未运行"等过程说明、入口编号 |
| G5-迁移版本列举、G5-标签密集 | 版本号堆列且没有原因说明；解释性标签合计超过约 5 处 |
| G5-指路代讲 | "见第 NN 篇"附近缺少作用、工作顺序、失败行为的词语信号 |
| G5-补充块过密 | 补充块的数量与间距；平均每 20 行超过一个时提示 |
| G5-数量声明 | 标题和正文里"共 N 项、N 条、N 步"这类声明，列出来供人工核对清单 |
| G3-图例不符 | 图后文字提到"菱形"而图里没有判断节点；提到"虚线"而图里没有虚线边 |
| G6-名称密集 | 一个自然段里反引号标识符超过约 5 个；同时报告全篇正文密度（参考线约每 10 行 4 个） |
| G6-否定限定 | "不能……断言／认为／当作／等同／概括／套用""不应理解为"等句式的位置与总数；超过约 6 处时提示 |
| G6-长并列句 | 单句超过约 120 字且含 3 个以上分号或顿号并列 |
| G6-用词、G6-模板转场、G6-修改痕迹、G6-推销式标题、G6-补充标签 | 装饰性词语（可用 `--words` 追加项目词表）；模板化转场；修改过程用语；推销式标题；不在稳定集合内的补充标签 |

表格、代码块、代码地图不参与名称密度统计。

**`consistency` 检查**：规划的篇目表与实际文件；核心机制有唯一主讲篇；已有正文的篇有对应的理解稿和审读记录；理解稿含非空的"讲述方案"；审读记录含阶段 A、B、C 三个区块、逐题记录和六道门结论，核心题的判定与通过条件一致；术语与衔接约定；问题台账有无未处理项；需求包的规则版本字段（缺失时报告"未标注"，按警告处理）。`--final` 在全部篇目完成后要求全套交付物齐全。它检查的是结构是否齐备，复述是否"通过"只能由阅读判定。
