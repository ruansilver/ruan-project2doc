# 写作规范

**何时读本文件**：U-成文、U-校对、修改时。

本文件只列原则和最有代表性的正反例；可执行的逐条检查在 `问题清单.md`（R、F、M 编号）。

**例句说明**：标“真实例句”的句子摘自一套真实笔记及其修改要求，只用来说明问题长什么样，不代表目标项目里有上传、消息队列、缓存这些组件。标“示例，非领域知识”的是通用场景改写。写进笔记的例子，必须来自目标项目自己的代码。

## 1. 单篇结构

文件名 `NN-标题.md`，标题写“对象 + 流程”，例如“订单支付：从回调到已支付”。模板见 `templates/单篇笔记.md`：

```
# NN · 标题
> 覆盖：起点（入口）→ 终点（一个可观测状态）
> 不覆盖：……（各写去向篇号）
一句话主线：用一个具体问题说出这篇要解决什么
## 一、链路全貌
   全景 Mermaid 图（只画主干与关键分支）；角色、术语与落点表
## 二..N、按执行顺序展开主流程
   编号步骤；每步先写“做了什么”，再写“防的是什么 / 为什么在这个位置”
   需要时紧跟补充块：补充说明 / 并发情况 / 异常情况 / 当前限制 / 版本差异 / 测试证据 / 实现限制
## 本篇终点与下一篇的接口
## 证据索引（按来源分组）
```

## 2. 叙事规则

概念以 `概念定义.md` 为准：就地展开 K09、回到主线 K10、由浅入深 K11、像小说 K12。

- **主干**：一级、二级标题按执行顺序排，只读目录就能还原流程。
- **就地展开**：遇到关键环节，在该步内部讲清它，最多下沉一层；讲完，下一个编号回到主线。展开的内容如果在别篇有归属（`_衔接约定.md` 的机制归属），只讲本篇用到的部分，再加一句“详见第 NN 篇某节”。
- **回到主线**：补充块之后的下一句必须是主流程的下一个动作，不写“回到正题”之类的转场。
- **由浅入深**：开头先给一句话主线和全景图，再讲步骤，再在补充块里讲异常与边界，最后在终点小结点明重点。
- **像小说**：每两步之间有因果，上一步的结果是下一步的输入；全篇追踪同一个具体对象（例如“一笔订单”“一个 2 GiB 文件”）；篇首以问题提出主线，篇尾“本篇终点”回答这个问题。
- **重点**：关键结论（K07）用加粗或提示块标出，每个一级节最多 3 处（默认值，可后改）。

## 3. 笔记怎么落到源码位置

- 正文用“直观叫法（原始名称）”首次建立对应，之后只用直观叫法。
- 主线段落的源码名只用来定位：把它删掉以后，句子仍能看懂。
- 精确位置（文件、方法、迁移号、行号）集中放在证据索引；正文只在“读者很可能要跳过去看”的地方点名。
- 名称本身就是接口契约，或者需要区分多个相似对象时，正文可以保留源码名。

## 4. 写作规范表

| 规范 | 正例 | 反例 |
|---|---|---|
| 一句话主线用具体问题开篇 | 真实例句：“一个 2 GiB 的文件，怎么在‘客户端随时能断、服务端随时能崩’的前提下……”；示例，非领域知识：“一笔订单，怎么在支付回调丢失、重复到达时仍然只记一次已支付？” | “本篇介绍上传模块的实现。” |
| 每步写“防的是什么”（K08） | 真实例句：“只信 Redis 会把‘标记在、文件被清’误判为完成；只信磁盘又区分不出‘写完但未登记’，所以两个都要看。” | “第 4 步：调用 hasUploadedChunk 判断是否已上传。” |
| 先说实际发生了什么，源码名放后面 | 真实例句：“给这个序号抢一把会自动过期的锁（`acquireChunk`）” | “`XxxService.execute` 调用 `XxxMapper.selectForUpdate`。” |
| 补充信息用稳定标签下沉 | `**并发情况**：……` 紧跟在它补充的那一步后面 | 把并发、异常、版本差异与主流程写成同级段落 |
| 测试证据只说覆盖到的范围 | 真实例句：“……没有专门针对‘丢 Redis 之后重传’这一次字节是否仍在磁盘上的用例” | “有集成测试覆盖，该机制可靠。” |
| 推断要标出来 | 真实例句：“两个请求都可能查不到既有会话而各建一个 `uploadId`【推导】” | 把没有证据的设计动机写成结论并反复使用 |
| 标题概括整块内容 | “四、读取与控制面：进度查询、任务中心、取消与过期清理” | 用“为什么必须先写 attempt 文件”当整节标题 |
| 写清时序：同一次还是不同次 | 真实例句：“消费者是另一次执行（另一条线程、另一笔事务）” | 只靠表格行顺序暗示先后 |
| 去向完整：谁发出 → 谁承接 → 结果 | 真实例句：“Redis 抛错会一路冒到方法外，触发同样的回滚” | “异常冒泡上去。” |
| 不留修改痕迹 | 直接写正确的现状 | “修正补充：此前理解有误……” |
| 少用模板化转场与 AI 味词 | 直接进入事实 | “明确了上述机制之后，本节继续……”；“钉死”“拓扑” |
| 关键数据追到真实来源（K06） | 示例，非领域知识：“幂等键由客户端生成，放在请求头里传入，服务端以它为唯一键插入去重表，24 小时后过期” | “从请求中获取” |
| 不能把局部行为写成全局 | 示例，非领域知识：“只有订单写接口在提交后清缓存；报表查询走另一条路径，不清” | “系统所有写操作都会在提交后清缓存” |

**说明**：真实的样本笔记在“代码名密度”上也没有完全达标（例如步骤多以方法名开头）。本 Skill 以上表和 `问题清单.md` 为准，样本只作结构和叙事的参考。

## 5. 事实分层

不允许互相升格：

| 层 | 含义 | 正文写法 |
|---|---|---|
| 已确认事实 | 当前源码或生效配置直接证明 | 直接陈述 |
| 可复现实证 | 测试、运行留档能复现的结果 | 写明测试实际断言了什么、覆盖到哪里 |
| 历史实现证据 | 旧版本、提交历史中的实现 | 放 `版本差异` 补充块，写清“旧版本怎么做 → 为什么改 → 新版本怎么做” |
| 目标设计 | 文档里“应该怎样”，代码未必实现 | 明确写“设计文档要求……，当前代码【未确认 / 未实现】” |
| 合理推导 | 从代码推出、但没有直接证据的结论或动机 | 句末标 `【推导】` |
| 未确认 | 缺证据，无法判断 | 句末标 `【未确认】`，原因进 99 |

## 6. 不确定内容怎么写才不破坏阅读流

- 正文只用短标签：`【推导】` `【未确认】`，放在句末；
- 详细的“为什么没法确认、缺什么证据”放进 `99-复核说明.md` 的未确认项表；
- 如果不确定点会改变主流程的走向，就在正文就地写一个 `当前限制` 补充块，而不是只放 99。
