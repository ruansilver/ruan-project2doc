# 质量门

六道门检查同一个结果：笔记准确，读者能解释流程和机制。成文先自查 G2、G3、G5；审读按“G1 追问 → G4 源码抽查 → G6 表达”的顺序执行，并复查其余门。成文自查记在理解稿末尾，审读结论集中记在 `_工作区/_审读记录/NN.md`。

## G1：读者能否回答追问

规划时建追问清单，研读时写答案草稿，审读时独立作答。清单按下面五层覆盖本篇核心机制和判断：

| 层次 | 问什么 | 通用例子 |
|---|---|---|
| L1 是什么 | 当前机制或环节的作用 | 这几步分别拦住什么情况？ |
| L2 怎样实现 | 结构、步骤、组件配合 | 一条记录怎样写入、读取、更新和失效？ |
| L3 为什么 | 判断、顺序和条件的作用 | 为什么先检查状态再执行昂贵操作？ |
| L4 出问题怎么办 | 校验、依赖、并发失败后的结果和代价 | 依赖不可用时谁继续、谁拒绝、什么能力减弱？ |
| L5 为什么不用别的 | 备选方案及代价 | 只保留一层或合并两步会有什么差别？ |

每个核心机制 L1–L5 各至少一题；每个支撑机制至少 L2、L4 各一题；流程每个关键判断至少一题 L3。用户提出的问题全部纳入。不要用“讲得清楚吗”代替具体追问。

审读者先只读正文和追问，不能提前看理解稿或源码。逐题写答案、正文出处，并判“答得出 / 部分 / 答不出”；然后由核对者或同一审读流程的后续阶段对照理解稿与源码核实。正确答案来自源码，不能因笔记表达流畅而放过错误。

**核心题必须全部答得出且正确；其余题答得出且正确的比例至少 80%**，比例为默认值、可后改。部分、答不出、答错都记录具体缺口。小缺口核实后补讲，大缺口退回研读；修订后重新验证受影响题目，不能直接把原判定改为通过。

例如旧版反例有缓存数字，却不能据此回答一次读写如何执行；缓存示范补足了工作方式。用具体作答判断这类差别，不能用命中文词的数量代替理解测试。

## G2：机制讲解完整

成文与审读都检查：核心机制在主讲篇回答《讲解规范》的七问；支撑机制以及链路篇引用的核心机制至少答①问题、③实现、⑤失败。逐个机制记录正文位置，确实不适用的项写原因。没查到不能当作“不适用”。缺失先补理解稿，再补正文。

## G3：流程与数据去向连得起来

成文与审读都沿六问走查起点、校验、处理、判断、状态落点、接手关系；再从最终结果反向追关键数据。每个影响结果的数据都有真实来源，每个分支有承接者和结果，同一次执行与不同次执行分清。记录检查的主流程、关键数据和发现的缺口；关系不清回理解稿与源码核实。

## G4：正文事实准确

研读时建立依据，审读第二轮回源码抽查。正文事实应能在理解稿中找到带源码位置的解释，意图型解释须有出处。每个大步至少抽一处关键断言，优先顺序、条件、失败行为、数字，数量为默认值、可后改。记录正文断言、理解稿位置、源码位置和核对结果。

抽查发现错误时，修正理解稿后再改正文，并扩大检查到共享同一前提的断言。不能为了讲得顺把“尝试、可能、特定路径”改成“保证、一定、所有路径”。缓存示范曾把组件的按键加载锁误套到普通调用路径，正说明讲得深入仍须核实实际接线。

## G5：正文承担讲解

成文与审读都运行 `lint` 获取候选，再人工判断。脚本无命中不代表通过；下面后三类尤其要通读。

| 信号 | 如何判断和处理 |
|---|---|
| 路径加行号，测试类或方法名清单 | 默认移理解稿；少数立即跳转有助理解的位置可保留并记录理由，代码地图不列行号 |
| “本次未运行”“尚无真实容器证据”等过程说明 | 移理解稿和 99；影响主流程理解的未知只在正文简短交代 |
| 迁移号、版本号堆列 | 移理解稿；需要版本演进时说明旧做法、问题与变化原因，不只列号 |
| 【推导】【未确认】合计超过约 5 处 | 检查是否能改为经核实的效果型解释，或把不影响理解的未知移 99 |
| 连续约 4 句只写配置、数字、名称或条件 | 检查是否有作用、原因和步骤解释；把事实组织成机制，不只是删除数字 |
| 机制只有名称和参数 | 补足问题、工作方式与失败行为，核心主讲机制还须回答其余七问 |
| 写“见第 NN 篇”，当前篇没有够用讲解 | 在使用处先补①③⑤，再指向主讲篇说明额外内容 |
| 某节补充块字数多于主文 | 检查主次是否倒置；重要机制移回主文，无助理解的核验材料移出 |

数值均为默认值、可后改。记录实际命中、人工判定、例外理由和处理位置；不把“有引用”一律当错误，也不以引用块的格式替内容自动放行。旧版反例的“测试证据”块、证据索引等形式不再设置，材料仍由理解稿和 99 承接。

## G6：表达让理解更容易

审读第三轮按《表达规范》的十五条检查句子、时序、术语、标题、层级和转场，最后用“说人话”类 Skill 自检。记录实际问题和修订位置；没有相关 Skill 时注明人工检查，不能声称运行过。保留用户有效例子和必要原理，表达修改不得改变事实与结论强度。

## 发生冲突时

| 冲突 | 取舍 |
|---|---|
| 深度与准确 | 不确定就回源码；确认不了就讲到已确认处，缺口记 99，不编造 |
| 理解与覆盖 | 次要分支可简述或留理解稿，核心机制的七问不能省 |
| 理解与精简 | 删重复、空话、无关核验细节，保留背景、原理、过程和例子 |
| 主线与深入 | 在所属步骤用小标题或补充块分层，讲完接回主线，不限定下沉层数 |
| 单篇可读与重复 | 使用篇保留够用讲解，完整讲解由主讲篇承担 |
| 用户要求与固定规范 | 按用户要求执行，在修改记录说明偏离的规范内容 |

各门通过后才进入该篇的用户确认。未通过要指明是规则执行问题、理解缺口还是资料不足，并登记需要返工的单元；不能只写“已检查”或以脚本成功替代这六项结论。
