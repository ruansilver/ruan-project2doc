# 生产流程与交接物

每个单元只读本节要求的输入和所需规则。长任务的步骤、进度、恢复由 ruan-dev-skills 管理，本 Skill 负责理解和写作，不另建接力状态。

## 1. 单元与产物

| 单元 | 输入与执行 | 输出 | 完成后 |
|---|---|---|---|
| U-勘察 | 仓库路径、基准、目录和构建文件，map 状态；运行 deps、scaffold、survey | `_勘察结果.md` | 记录基准、规模、map 状态与脚本结果，进入规划 |
| U-规划 | 勘察结果、用户重点、入口与终点线索、必要的机制调用位置 | `_规划方案.md`、00 骨架、术语表、衔接约定 | **等待用户确认规划方案** |
| 交接编排 | 确认后的规划、规则和模板 | 需求包、dev-skills 资料仓 | 资料仓达到“可接力”，首次调用结束 |
| U-研读 | 本篇规划、术语与衔接、本篇源码、可信范围内的 map、讲解规范 | `_研读/NN.md` | 机制卡、流程、关键数据与每道追问都有答案草稿 |
| U-成文 | 本篇理解稿、规划条目、术语、衔接、讲解与表达规范、对应篇模板 | `NN-标题.md`，必要时更新理解稿 | G2、G3、G5 自查通过 |
| U-审读 | 先只读正文和追问；作答后才读理解稿、定点源码和表达规范 | 修订正文、`_审读记录/NN.md` | G1–G6 通过后，**等待用户确认第 NN 篇** |
| U-收束 | 已确认各篇、理解稿核验材料、规划与交接物 | 完整 00、99、修改提示词文档 | 一致性检查完成，问题台账无 open |

两类确认分别是规划完成和每篇审读完成。每篇研读、成文、审读各为一个新会话步骤，按阅读顺序推进。步骤不得把“文件存在”当作质量门通过，也不得将脚本退出码当作用户确认。

## 2. 勘察与规划

U-勘察只读目录树、构建信息、基准提交和 map 状态，不在这里一次性装入所有业务源码。`survey` 的结果填入 `_勘察结果.md`；没有 map 时按《project-map借鉴》走正向入口、反向终点发现。

U-规划按《篇目规划》识别链路与机制，定级、安排主讲篇和使用篇，写学习目标与追问。规划内容可以包含待研读核实的候选，但不能写成已经确认的机制保证。确认后按《需求包规格》交接，正常首次调用不继续进入研读。

## 3. U-研读：先自己弄懂

从 `templates/_研读.md` 复制为 `_工作区/_研读/NN.md`。按本篇范围沿真实执行关系读源码，研究到足以解释原理、步骤和取舍。理解稿包含：

1. 流程走查：每步做什么、输入从哪来、输出到哪去、关键判断、失败结果，以及是否换了一次执行；附源码位置。
2. 机制卡：核心机制按七问、支撑机制按①③⑤写成可连读的段落，包含必要原理、备选分析和走查例子。
3. 关键数据去向：来源、传递、使用或校验、更新与失效。
4. 追问与答案草稿：逐题回答规划里的问题，补上研读中发现的追问。
5. 设计意图出处：区分效果型、对比型和有出处的意图型解释；后者记录注释、提交或文档位置。
6. 核验材料：测试覆盖及运行情况、配置差异、迁移、未确认项、与 map 的冲突，供审读和 99 使用。
7. 细节去向：不进正文的细节写明去向和理由。

每个事实有源码位置，因果分析有前提。理解稿按“后续作者无需重读大段源码，也能讲清机制”验收；不写成孤立的一行一条，也不限制与正文的篇幅比例。缓存示范中的教训尤其适用：找到组件有一个加载方法，还要沿使用点确认实际调用它，不能把组件能力当成全部调用都具备的行为。

单元读入原始材料加产出，默认不超过可用上下文的一半，可后改。确实容纳不下时拆篇或拆出机制专题，交编排调整；不能以少读关键源码换取完成。

## 4. U-成文：把理解讲给读者

不读其他篇正文；要解释别篇主讲的机制时，只读其理解稿中相关机制卡。根据本篇问题和类型组织正文，在用到机制的步骤就地讲清，而不是按理解稿目录机械搬运。

允许定点回读理解稿标明的源码位置，核实或补足细节。新发现的事实先补入理解稿并注明来源，再写进正文。若需要大范围重新探索，说明理解稿还没完成，退回研读单元。

成文后对照 G2、G3、G5 自查，结果写在理解稿末尾，便于审读者复查。篇首问题由篇尾小结回答；篇尾代码地图只保留关键文件或类及职责。暂不把核验记录搬进正文。

## 5. U-审读：三轮顺序固定

第一轮是 G1。新会话或独立审读者只收到笔记正文和追问，逐题作答并记录正文出处。此时不得读理解稿、源码或预设答案；作答完成后，核对者再对照理解稿和源码判断是否正确。

第二轮是 G4。回源码抽查关键顺序、条件、失败行为和数字，每个大步至少一处（默认值、可后改）；同时复查 G2、G3、G5。

第三轮是 G6。按《表达规范》校对，最后用可用的“说人话”类 Skill 自检；能力缺失时如实记人工检查。三轮结果汇总到 `_审读记录/NN.md`，保留每题答案、判定、正文出处与核对依据。

表达问题可直接改，但不能改变事实和结论强度。小的讲解缺口可以补讲，涉及新事实时必须先回源码核实并补入理解稿。机制没弄懂等大缺口登记 `_问题台账.md`，交 dev-skills 新增研读步骤，不在审读里凭记忆硬补。修正影响哪道追问，就重新做哪道理解检查；事实变更同时复查相关机制和数据关系。

## 6. U-收束与恢复

回填 00 的系统用途、架构、数据主线、机制一览、阅读路线与术语；从各篇理解稿整理 99 的入口全表、不展开原因、核验概览和未确认项。检查术语、数字、主讲篇与够用讲解是否一致，运行 consistency，再生成修改提示词文档。

收束只改 00、99 和各篇篇首篇尾衔接，不改机制讲解。发现正文事实或讲解问题，就登记并返回对应步骤。收束不通过时不把问题台账批量关闭。

中断后按 dev-skills 的接力提示词和当前步骤恢复，再读该单元所需交接物；`progress` 只辅助核对产物和提交。源码基准改变时列出受影响篇目，交编排新增重新研读步骤。冲突以当前源码为准，再修理解稿、术语和衔接、规划、正文与 00；被分析仓库和 map 始终只读。
