# 定位与标杆

首次规划时读本文件；研读或成文拿不准详略时，用这里的成功标准判断。

## 要交付什么

把一个项目讲懂给初学者：读全仓库源码，写成中文系统学习笔记。读者会写一般业务代码，能读懂代码，也知道常见技术名词，但还不了解本项目的业务、架构和各项技术怎样配合。

**准确是底线，理解是目标，可读是手段，覆盖服从理解。** 写进正文的事实必须经当前源码核实；核实过程主要留在理解稿和 99。全仓库入口都要有去向，但不必把每个次要分支写进主文。

读完一篇，读者应能做到三件事：

1. 讲流程：复述主要步骤，说清关键数据从哪里来、在哪里被校验或改变、最后交给谁。
2. 讲机制：解释问题、原理、本项目的结构和步骤、失败时的处理，以及备选方案的差别。
3. 经得起追问：面对“为什么先做这一步”“这里失败会怎样”“为什么不用另一种做法”，能凭本篇内容再回答两三层。

通用原理讲到足以理解项目实现和方案差别为止。正文默认不设面试章节；追问仍是内部质量门，用户可在修改提示词文档中打开面试章节。

## 让读者形成理解的写法

| 写法 | 来源中的例子（节选或摘改） | 它补足哪一层理解 |
|---|---|---|
| 从问题开始 | 认证标杆先问：登录以后怎样持续确认身份，又怎样收回令牌或刷新权限？ | 每个后续机制都有具体用途 |
| 原理紧挨实现 | 限流标杆先解释有序集合按时间删旧记录，再写剩余数量如何参与限流判断 | 读者知道数据结构为什么适合这个问题 |
| 朴素方案、缺陷、改进 | 缓存标杆比较全局一把锁和按键分别加锁：前者让互不相关的请求排队 | 读者能回答为什么不选更简单的方案 |
| 写出结构和顺序 | 缓存标杆分别走查本地读、共享缓存读、回源、写回和广播 | 读者可以在脑中执行一次 |
| 用小场景检验规则 | 认证标杆用连续错误密码说明“达到阈值的请求”和“下一次被锁拦住” | 避免把状态变化和响应时点混为一谈 |
| 故障与代价一起讲 | 认证标杆区分哪些依赖操作故障后继续，哪些会中断 | 读者不会把一个操作的兜底推广到全部操作 |
| 收成全景并说明局限 | 认证标杆把刷新不轮换与凭据泄漏后的可重复使用联系起来 | 读者理解取舍，且不把方案讲成完美保证 |

缓存标杆的旧事实曾被误套到另一个调用路径：组件提供按键加锁的加载方法，不等于用户资料读取实际调用它。缓存示范修正了这一点。**借讲解方法，所有事实回目标项目源码确认。**

标杆里的高密度方法名、戏剧化标题和反复版本叙述不照搬。10.4 只借按执行顺序组织、补充信息下沉的结构；B 的精简要求只删重复、空话和无助理解的细节。

## 反例为何不合格

旧版反例第四节给出了“本机一级配置为 60 秒、Redis 二级为 30 分钟、空值为 30 秒”，随后指向别篇。数字没有连到读写动作，读者无法解释一次未命中如何处理，也无法判断依赖故障的代价。缓存示范则先解释为什么不能只信令牌中的旧角色，再走查读、写、失效和故障路径；这些解释应留在用到缓存的那一步。

旧版反例第二节把登录 IP 限流压成“60 次 / 60 秒”，再指向第 15 篇。限流标杆的写法会继续交代如何表示一次请求、如何删旧、计数和判断，以及拒绝结果由谁转成响应。这才足以回答“第 61 次会怎样”。具体数字与顺序仍须取自当前项目。

旧版工作区有很多逐条核对记录，正文仍缺少机制解释。完成检查记录并不能替代读者作答。最终用《质量门》的 G1 检验理解，再检查准确和表达。
