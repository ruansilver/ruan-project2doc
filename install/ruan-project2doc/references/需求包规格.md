# 需求包规格与笔记工程目录

**何时读本文件**：首次调用（建目录、写需求包、调用 dev-skills）；修改时（准备新的需求材料）。

## 1. 笔记工程目录

```
<仓库名>-笔记工程/                  仓库同级的普通目录（本身不是 Git 仓库）
  笔记/                             笔记仓：独立 Git 根，dev-skills 眼中的“代码仓”
    00-总览与主线地图.md            读者入口：系统边界、篇目清单与衔接、术语表、跨篇机制归属、事实口径
    01-<对象+流程>.md ... NN-<对象+流程>.md
    99-复核说明.md                  依据汇总、未确认项、与文档/project-map 的冲突、要用户决策的点
    修改已有笔记-<仓库名>.md         修改提示词文档（U-收束生成）
    _工作区/                        交接物，读者不用看
      _勘察结果.md _拆分方案.md _术语表.md _衔接约定.md _问题台账.md
      _事实/NN.md  _校对记录/NN.md
  需求包/                           本 Skill 生成的“笔记生成需求包”，交给 dev-skills 归档为 P001
  docs/AI dev docs/                 资料仓：独立 Git 根，由 dev-skills 创建和管理
    笔记v1/                         版本目录：步骤总览、当前状态、开发协议、接力提示词、plans/ ……
```

**为什么这样摆**：dev-skills 要求版本目录位于 `<项目总目录>/docs/AI dev docs/<版本号>/`，资料仓是独立 Git 根，需求源不能放在资料仓里，代码仓是工作目录的 Git 根。三者并列在笔记工程下，就同时满足这些要求，也不在被分析的仓库里写任何东西。笔记仓与资料仓分开，读者看到的笔记目录不会混进步骤和进度文件。

**默认值，可后改**：工程目录名 `<仓库名>-笔记工程/`；笔记文件名 `NN-标题.md`；dev-skills 版本号首次用 `笔记v1`。

**Git**：笔记仓默认 Git 管理并允许自动提交，只提交笔记仓，从不推送。`<工程>/` 本身不要 `git init`，否则会把资料仓和笔记仓包进同一个仓库，dev-skills 的边界检查会失败。

## 2. scaffold 建出的骨架

```bash
python "<SKILL>/scripts/project2doc.py" scaffold --project "<工程>" --repo-name "<仓库名>"
```

- `笔记/`：`git init`；`_工作区/` 下放 `_勘察结果.md`、`_拆分方案.md`、`_术语表.md`、`_衔接约定.md`、`_问题台账.md` 五个模板。`_事实/NN.md`、`_校对记录/NN.md` 在对应单元开始时从 `需求包/模板/` 复制。
- `需求包/`：`00-任务说明.md`、`02-步骤拆分要求.md` 两个待填模板；`规则/`（本 Skill 全部 references 的副本）；`模板/`（全部 templates 的副本）；`工具/project2doc.py`（脚本副本，后续步骤会话用它做机械检查）。
- 已存在的文件一律不覆盖，重复运行是安全的。

## 3. 需求包的组成（归档为 P001）

| 文件 | 内容 | 谁写 |
|---|---|---|
| `00-任务说明.md` | 目标、被分析仓库路径与基准、产出位置、“这里的代码仓是笔记仓，S001 只记录基线”、源码仓变化时的处理 | 本 Skill，按模板填写 |
| `01-拆分方案.md` | 用户确认过的篇目、起点与终点、篇间接口（`_拆分方案.md` 确认版的副本） | 本 Skill，用户确认后复制 |
| `02-步骤拆分要求.md` | 单元类型、粒度、每类单元的输入 / 不读 / 输出 / 完成判据，每篇校对步骤后等待用户确认，每个步骤文件要写明读需求包的哪几份 | 本 Skill，按模板填写 |
| `规则/` | 写作规范、约束取舍表、校对协议、自检清单、project-map 借鉴、问题清单、概念定义、编排与交接物、修改协议、需求包规格 | scaffold 复制，不改 |
| `模板/` | 单篇笔记、00、99、修改提示词文档、全部交接物模板 | scaffold 复制，不改 |
| `工具/project2doc.py` | 辅助脚本 | scaffold 复制，不改 |

dev-skills 的步骤文件用“`P001 + 归档内相对文件 + 标题`”的格式引用具体规则，例如“P001 `需求包/规则/校对协议.md` §4 权限边界”。

**为什么写作规则放需求包、不放协议**：dev-skills 的《开发协议》《开发接力提示词》按其规定原样复制、不得改写。需求包是 dev-skills 允许按需求生成的地方，而且它的协议本来就要求“需求边界不清时读 `plans/索引.md`，再按覆盖范围读 Pxxx”。

**需求包的边界要求**（dev-skills 的摄取检查）：不含空目录、不含符号链接、不位于 `docs/AI dev docs/` 内。不要放密钥、令牌等敏感内容，dev-skills 会原样归档。

## 4. 调用 ruan-dev-skills 初始化

前提：用户已确认拆分方案；`需求包/` 三份文件已写好；笔记仓已有一次提交（骨架）。

1. 把工作目录切到 `<工程>/笔记/`（dev-skills 以工作目录的 Git 根作为代码仓）。
2. 加载 ruan-dev-skills（Skill 工具，或读取它的 `SKILL.md`），以初始化模式执行，参数：
   - 需求材料：`<工程>/需求包/`
   - 版本目录：`<工程>/docs/AI dev docs/笔记v1/`
3. 按 dev-skills 的初始化流程走完：它会 `git init` 资料仓、归档 P001、规划 S001 和后续步骤、复制固定资产，最后把状态改为“可接力”。
4. 本 Skill 不在这次调用里开始 U-取证。

**Windows 注意**：笔记工程路径里有中文（默认名就含“笔记工程”）。在中文 Windows 上，dev-skills 的 `devdocs.py` 用系统默认编码读 git 输出，会因 GBK 解码失败而报错。运行它时一律加 `-X utf8`，例如 `python -X utf8 "<dev-skills>/scripts/devdocs.py" check-root ...`，或先设置环境变量 `PYTHONUTF8=1`。本 Skill 的 `project2doc.py` 已自行处理编码。

## 5. 修改时的需求材料

见 `修改协议.md` 第 3 节：新建一个资料仓之外的目录（例如 `<工程>/需求包-修改-<日期>/`），放修改提示词文档副本和 `00-修改说明.md`，以调整模式交给 dev-skills。旧的需求包和旧 Pxxx 不改。
