# 需求包规格与笔记工程目录

首次建工程、确认规划后交接，以及修改时准备材料，读本文件。各单元细则见《生产流程与交接物》。

## 1. 目录与责任

```text
<仓库名>-笔记工程/               普通目录，不执行 git init
  笔记/                          独立 Git 根（只提交，不推送）
    00-系统总览与阅读路线.md
    NN-标题.md                   链路篇或机制专题篇
    99-复核说明.md
    修改已有笔记-<仓库名>.md
    _工作区/
      _勘察结果.md
      _规划方案.md
      _术语表.md
      _衔接约定.md
      _问题台账.md
      _研读/NN.md                理解稿
      _审读记录/NN.md
  需求包/                        交给 ruan-dev-skills 的需求源
    00-任务说明.md
    01-规划方案.md
    02-步骤拆分要求.md
    规则/                        本版 references 副本
    模板/                        本版 templates 副本
    工具/project2doc.py
  docs/AI dev docs/              ruan-dev-skills 管理的独立资料仓
    笔记v1/                      版本目录
```

笔记仓充当 ruan-dev-skills 所说的“代码仓”；需求包位于资料仓之外，不含空目录、符号链接和敏感信息（它会被原样归档）。这样所有写入都留在输出工程，不进入被分析仓库或 project-map。目录名、文件名和 `笔记v1` 都是默认值，可后改。只提交笔记仓，不推送；本 Skill 不代管资料仓的 Git 操作。

每类文件承担的信息：

| 位置 | 应保存的内容 |
|---|---|
| 00 | 系统解决什么问题、由什么组成、一两条代表性主线、核心机制一览、阅读路线、易混淆术语 |
| 单篇正文 | 全貌、按组织方式展开的过程与机制、影响理解的条件与失败、必要数据结构、例子、小结、代码地图 |
| 规划方案 | 链路候选、机制分级与主讲篇、篇目与组织方式预判、学习目标、阅读顺序、追问清单、入口去向、确认记录 |
| 理解稿 | 已理解并核实的过程与机制、事实来源、追问答案草稿、核对材料、未展开内容，以及讲述方案 |
| 审读记录 | 独立读者的原始复述与答案、初读障碍、核真结果、修改位置与复验、六道门结论 |
| 99 | 源码基准、入口全表、未展开原因、未确认项、与 project-map 的差异、测试与运行核对范围、审读概览 |
| 修改提示词文档 | 固定规范、项目口径、用户追加的要求、变更记录 |

## 2. scaffold 与模板

```bash
python "<SKILL>/scripts/project2doc.py" scaffold --project "<工程>" --repo-name "<仓库名>"
```

`scaffold` 初始化笔记仓，放入 00、99 和工作区的共用交接物，创建空的 `_研读/`、`_审读记录/` 目录；在需求包里复制本版的规则、模板和工具，放入任务说明与步骤拆分要求模板，并在 `_勘察结果.md` 与 `00-任务说明.md` 写入规则版本（如 `ruan-project2doc 1.6.0`）。已有文件不覆盖。按篇的文件在相应单元从模板复制。

空的研读和审读目录位于笔记仓，不进入需求包。需求包归档前不得有空目录或符号链接，不得放在资料仓内。

## 3. 确认规划后的需求包

| 文件 | 内容 |
|---|---|
| `00-任务说明.md` | 学习目标与读者；只读源码仓与基准；project-map 状态；输出位置；用户重点；规则版本；说明代码仓是笔记仓、初始步骤只记基线；源码变化后的重新研读安排 |
| `01-规划方案.md` | 用户确认后的 `_规划方案.md` 完整副本 |
| `02-步骤拆分要求.md` | 每篇研读、成文、审读三个步骤及各自的输入、读取边界、输出、完成判据；审读步骤的下一动作是“等待用户确认第 NN 篇”；最后是收束 |
| `规则/`、`模板/`、`工具/` | 本版 references、templates 与辅助脚本的副本 |

步骤文件用“需求包编号 + 归档内相对路径 + 标题”引用规则，以 ruan-dev-skills 实际返回的归档结构为准，不能猜目录多一层或少一层。每个步骤写明本次要读的规则，不要求通读全部副本。写作规则放在需求包里，不写进 dev-skills 的固定协议和接力提示词。

步骤拆分中各单元的读取边界：

| 单元 | 输入 | 读取边界 |
|---|---|---|
| U-研读 | 本篇规划、相关源码、相关 map 节点、术语与衔接、规则 | 围绕本篇的流程和机制读源码，不整仓重读 |
| U-成文 | 理解稿（含讲述方案）、本篇规划、00 相关背景、术语、衔接、规则、篇型模板 | 可定点回读理解稿标明的源码；不读其他篇正文 |
| U-审读 | 第一轮：骨架视图 → 正文 → 题面；之后：理解稿、相关源码、规则 | 独立读者不得提前接触理解稿、源码和答案 |
| U-收束 | 各篇首尾、理解稿的核对材料、术语、衔接、台账 | 只改 00、99 和各篇首尾衔接 |

## 4. 初始化编排

前提：规划已确认，三份需求文件已填好，笔记仓已有骨架提交。以 `<工程>/笔记/` 为工作目录，加载已安装的 ruan-dev-skills，用初始化模式提供：

- 需求材料：`<工程>/需求包/`；
- 版本目录：`<工程>/docs/AI dev docs/笔记v1/`。

由它初始化资料仓、归档需求、规划步骤，直到状态为“可接力”。第一个步骤只记录笔记仓基线、源码基准和依赖检查结果，不虚构业务构建结果。首次调用在此结束，后续按接力提示词进入新会话。

ruan-dev-skills 是正常长任务的硬依赖，缺失则停止并说明缺什么，不自建编排替代。在 Windows 上运行它的脚本时使用 `python -X utf8`，避免中文路径和 Git 输出按系统编码解码失败；具体参数以当前安装的 dev-skills 说明为准，不凭旧调用拼写。

## 5. 修改与基准变化

修改按《修改协议》另建需求材料目录，交给 dev-skills 调整模式，保留旧归档。源码基准变化时先列出变化路径与受影响篇目，再新增重新研读步骤；既不能悄悄沿用旧事实，也不能在收束步骤大改机制讲解。继续或重做已有工程时，先按《修改协议》核对它归档的规则版本。
