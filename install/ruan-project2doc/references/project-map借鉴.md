# 借鉴 project-map

project-map 是 ruan-project-reader 产出的执行流程知识库。有 map 时优先借鉴，没有时不强求。两条路径产出的笔记，质量标准和格式完全一致，区别只在取证成本。

**何时读本文件**：U-勘察（第 2 节）、U-拆分（第 1、7 节）、U-取证（第 3–6 节）。

## 1. map 能提供什么、不能提供什么

| 能提供（事实骨架） | 不能提供 |
|---|---|
| 入口序号 E#、汇点序号 S#（`COVERAGE.md`） | 按读者节奏切分的篇目（map 的模块按执行职责划分，粒度常常比一篇笔记大） |
| 按执行职责划分的模块，以及总览里的主体流程 | 叙事：动机、“防的是什么”、由浅入深的顺序 |
| 节点级源码依据（模块的 `必要规则与源码依据` 节） | 设计原因（reader 规定没有证据的动机只能标推断） |
| 候选处置：本文已解释 / 模块引用 / 外部边界 / 琐碎 / 待核实 / 阻塞 | 源码事实正确性的保证：reader 的 `check.py` 只核对记录格式与一致性 |
| `## 未决` 表：待核实 / 阻塞 / 限制 | 当前源码的时效性：map 绑定某个基准提交 |
| 源码基准提交号、扫描方法、未检查区域 | |

**不借鉴**：Mermaid 执行图的形式、逐节点约 20 字的短注、候选表、闸门表、验收记录。笔记的图另画，只画读者需要的主干，不追求节点完备。

map 总览的主体流程**只作拆分候选**：按“每篇的终点是一个可观测状态”（`概念定义.md` K02）重新拆或合。证据索引里写明对应的 map 模块与节点 ID。

## 2. 检测：有没有、完不完整、过没过期（U-勘察）

开工时按顺序做，结果写进 `笔记/_工作区/_勘察结果.md`，并报告给用户，不需要用户回答。`project2doc.py survey` 会机械地完成第 1、2、4 步并尝试第 3 步：

```bash
python "<SKILL>/scripts/project2doc.py" survey --repo "<仓库>" [--map "<project-map>"] [--json]
```

1. **找位置**：先找 `<仓库>/project-map/`，再找仓库的同级目录和父目录。都找不到就走第 7 节。
2. **读状态**：读 `STATE.md` 的九项统计（梳理中、待验收、本层完成、已证叶子四类模块数，待办数、阻塞数、入口数、汇点数、覆盖记录数），读每个模块文件顶部的 `状态：`、`限制：` 两行，读 `COVERAGE.md` 的“本轮发现暂时收敛”“本轮范围整体完成”。
3. **机械检查**：有 Python 3.10+ 时运行 reader 的 `check.py <map>`（只读形式，不带任何写入参数）。退出码 0（通过）、1（失败）、2（未验证）原样记录。**不因为退出码是 1 就放弃借鉴**，失败项只降低相关模块的信任。
4. **比对基准**：从 `COVERAGE.md` 或 `README.md` 读出源码基准提交号，和当前 HEAD 比较。不同就记下 `git diff --stat <基准> HEAD` 涉及的路径。一个 map 覆盖多个 Git 仓库时，对每个仓库分别比对。

**没有脚本时的人工做法**：用文本搜索在 `README.md`、`COVERAGE.md` 前 20 行找 7–40 位十六进制的提交号；用 `git -C <仓库> rev-parse HEAD` 取当前提交；用 `git -C <仓库> diff --stat <基准> HEAD` 取变化路径；逐个打开 `modules/*.md` 读前三行。在 `_勘察结果.md` 写明“脚本未执行”。

## 3. 信任分级：按单条事实，不按模块状态（U-取证）

理由：真实的 map 里“已证叶子”常常是 0，“本层完成”又常带着限制，按模块状态几乎分不出高低。所以分级落到“笔记里要写的这一条事实”上。

| 事实所处位置 | 怎么用 |
|---|---|
| 基准过期，且事实涉及的文件在变化路径中 | 只当线索，必须回当前源码重新核对后才能写 |
| 节点或候选挂着 `待核实` | 只当线索；核对后成立就写成事实，核不了就写成待核实 |
| 挂着 `阻塞`，或所在模块“限制：有” | 先读该模块的 `## 限制说明`、`## 未决`，弄清限制范围；范围内的内容按待核实对待 |
| 所在模块“梳理中”或“待验收” | 结构可以参考，事实全部回源码核对 |
| 所在模块“本层完成”或“已证叶子”，而且没挂未决 | 可以直接用，但仍要参加第 4 节的抽查 |
| `check.py` 失败牵涉的模块 | 失败项本身（例如断链）不影响源码事实时照常分级；影响时降一级 |

## 4. 回源码核对的策略

`check.py` 通过不代表源码事实正确，所以借鉴来的内容仍要回源码核对：

- **必须核对**：第 3 节表中前三行的事实；写进本篇主流程的关键数据来源和状态变化；所有数字（超时、阈值、上限、步数）。
- **抽查**：其余借鉴来的事实，主流程的每一大步（`概念定义.md` K16）至少抽 1 处。
- **抽查不一致时**：说明这个模块不能整体信任，把该模块其余借鉴事实全部改为“必须核对”。

## 5. 冲突：map 与当前源码不一致

以当前源码为准，正文直接写现状，不写“map 原来说……”。冲突登记进 `99-复核说明.md` 的“与 project-map 不一致”一节：map 的模块、节点 ID、map 原说法、当前事实、源码位置。交付时汇总告诉用户。**不修改 project-map**，是否回写由用户在 reader 那边决定。

## 6. 依据来源记录

事实摘要（`_事实/NN.md`）每条都带来源，每篇笔记的证据索引按来源分组：

- `源码直取`
- `借鉴 project-map <模块文件>#<节点 ID>，已核对`
- `借鉴 project-map，未核对（只作结构参考）`

这样以后修改时，能追溯到某条事实来自哪里。

## 7. 没有 project-map 时的自带路径

1. 开工时提示一句：“先跑 ruan-project-reader 可以降低取证成本，但不是必须的”。用户选择继续，就不再提。
2. 轻量发现，借用 reader 的两个方向，但不做它的覆盖登记、闸门和验收：
   - **正向**：从入口出发。入口的具体形态按项目类型查 `概念定义.md` 附录 G（例如路由与处理函数、消息消费者、定时任务、主函数、启动钩子、后台工作线程、命令注册点、公开 API）；
   - **反向**：从终点出发。写持久存储、发消息、调外部接口、写文件或对象存储、返回给调用方，反查它们属于哪条流程；
   - 两边对照，得到主体流程候选清单，交给 U-拆分。
3. **隐藏链路最容易漏**（后台清理、补偿扫描、孤儿检查这类没有用户触发的任务）。U-拆分必须列出所有定时任务、消息监听和后台线程的去向：归入某篇，或在 00 标为不覆盖并写原因。
4. 证据纪律不变：正文区分已核实 / 推断 / 待核实；每篇都有证据索引，来源写“源码直取”；核对方式由抽查改为全量自查。

## 8. 只读

对 project-map 只读：不改状态、不补未决、不运行任何写入命令。`check.py` 只用不带写入参数的形式。
