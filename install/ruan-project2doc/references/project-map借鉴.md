# 借鉴 project-map

project-map 是执行流程知识库，可帮助找到入口、交接关系和源码位置。它不决定笔记篇目，也不能替代理解机制。被分析仓库和 map 均只读，不改状态、不补未决，不运行写入命令。

## 1. 检测和勘察

```bash
python "<SKILL>/scripts/project2doc.py" survey --repo "<仓库>" [--map "<project-map>"] [--json]
```

按仓库内、同级、父目录查找 map；用户明确给出的路径优先。读 `STATE.md` 统计、`COVERAGE.md` 的范围与收敛状态、模块顶部的状态和限制，结果写 `_勘察结果.md`。勘察阶段不读完模块正文和全部业务源码。

比较 map 声明的基准与源码 HEAD。基准不同就列出变化路径；覆盖多个仓库时分别比较。可用时运行 reader 的 `check.py <map>`，只用无写入参数的形式，原样记录退出码与未执行原因。结构检查通过不代表源码事实正确，失败也不等于所有 map 内容都失去价值。

没有脚本时，人工读取 README、COVERAGE 中的基准，执行 `git -C "<仓库>" rev-parse HEAD` 与 `git -C "<仓库>" diff --stat <基准> HEAD`，读取模块状态与限制。在勘察结果注明“脚本未执行”。

## 2. 按具体内容判断信任

| 内容情况 | 使用方式 |
|---|---|
| 基准过期，相关文件已变化 | 仅作线索，回当前源码重新核实 |
| 节点或候选待核实 | 仅作线索，查明后才能作为结论 |
| 节点阻塞，或模块标有限制 | 先读限制与未决；受限制的内容按待核实处理 |
| 模块梳理中或待验收 | 借结构，事实回源码核实 |
| 模块本层完成或已证叶子，相关内容无未决 | 可作理解稿的来源线索和起草基础，仍执行下节核对 |
| check.py 失败 | 判断失败是否影响该事实，影响时降低信任；纯结构问题不直接否定独立源码结论 |

map 可提供流程候选、入口和终点、节点源码位置、未决与基准。它不能保证当前正确性，也不能给出适合读者的学习目标、机制讲解和方案取舍。图、候选表、闸门表不照搬进正文；笔记按读者需要另画主干图。

## 3. 回源码核对

过期、待核实或受限制的内容必须核对；关键数据来源、状态变化和全部数字必须核对。其余借鉴事实每个主流程大步至少抽查一处，默认值、可后改。抽查不一致时，将该模块其余借鉴事实全部转为必须核对。

理解稿的每个事实保留源码位置，借用 map 时同时记录模块、节点和核对状态。尚未核对的 map 只用于结构参考，不能被写成正文事实；讲解越具体，越要查清当前使用点实际走的条件和调用路径。源码直读得到的事实也须解释到可回答追问，不只摘抄结论。

## 4. 冲突与来源记录

当前源码优先。冲突写入理解稿并汇总到 99：map 位置、原说法、当前源码行为和源码位置。正文直接讲当前实现，不反复叙述核对过程。不要回改 map，是否更新由用户在阅读项目时另行决定。

来源、测试运行情况、配置差异和未确认项都留在理解稿或 99，篇尾只给关键文件及职责。不再设置证据索引，也不把核验状态作为每段正文标签。

## 5. 没有 map 时

只提示一次可先使用 ruan-project-reader 降低阅读成本；已有继续授权就继续。按《篇目规划》的技术形态表正向找入口，再从返回、写存储、发消息、写文件与外部调用反向找终点，两边对照得到候选链路。

定时任务、后台线程和事件监听容易漏，逐一登记到规划的入口去向表，最后进 99。没有 map 时同样产出理解稿、通过六道质量门；差别只是少了一份导航材料，不另降标准。
