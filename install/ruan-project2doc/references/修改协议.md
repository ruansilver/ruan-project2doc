# 修改协议

用户要求按修改提示词改笔记时读本文件。修改入口是 `笔记/修改已有笔记-<仓库名>.md`，由 `render-revise` 生成四区：固定规范、项目口径、用户追加、变更记录。

## 1. 确定本次要解决的问题

只处理用户追加区中状态为“待处理”的行。填写了目标篇，就只改这些篇；未填写时，根据术语表、规划的主讲篇和衔接约定列出受影响篇及理由，取得用户确认后修改。已有明确的范围授权可直接沿用。

先把阅读反馈转成一个追问：用户缺的是问题背景、原理、实现顺序、判断原因、失败处理，还是方案取舍？再读本篇理解稿与正文，检查该追问能否被回答。不要只改用户指出的一句话，却留下同一个理解缺口。

这一做法来自 B 第一节：阅读反馈可能暴露尚未真正掌握的知识点，补充仍要服务当前问题。例子是旧版反例第四节的缓存参数；用户问“两级到底怎么读”，需要在原处补工作过程，不是把“缓存”换成更通俗的名称。

## 2. 选择修改路径

| 修改范围 | 执行方式 |
|---|---|
| 一篇，纯表达或不改变含义的结构调整 | 当前会话按《表达规范》处理，复查受影响追问，写变更记录并提交笔记仓 |
| 涉及事实、讲解依据，或涉及多篇 | 交 ruan-dev-skills 调整模式，先安排必要研读，再成文与审读 |

表达修改不改变数字、条件、时序、失败结果和结论强度。补充机制细节属于事实工作：先回源码核实，更新 `_工作区/_研读/NN.md`，再改正文。大缺口按《生产流程与交接物》的退回规则处理，不能借“校对”跳过研读。

直接在原位置修正或补讲；原处确实容不下才在附近另起层次。错误分支彻底删掉，不把它换成提醒继续留存。保留有助理解的用户例子，不留修改过程痕迹。

## 3. 交给 dev-skills 的材料

在资料仓之外新建需求材料目录，例如 `<工程>/需求包-修改-<日期>/`，包含修改提示词副本及 `00-修改说明.md`。修改说明写明本次待处理行、已确认篇目、追问缺口、修改类型、源码基准，以及“先更新理解稿，再改正文，最后重新验证受影响追问”的要求。

以 `<工程>/笔记/` 为工作目录，加载当前安装的 ruan-dev-skills，用调整模式交入该目录和现有版本目录。由它归档新的需求包，更新步骤、当前状态与需求索引，沿用固定接力提示词；旧归档不改写。涉及事实的先安排研读，涉及多个篇的说明衔接和术语影响。每篇审读后的下一动作仍为等待用户确认。

## 4. 检查与落盘

修改后执行受影响问题的 G1，核对 G2、G3 的机制与数据关系；涉及事实时执行 G4；再检查 G5、G6。G1 的作答先只读正文，再核对理解稿。把结果记入对应审读记录，不能只写“已修改”。

在变更记录写日期、处理的用户要求、目标篇与位置、变更类型、验证结果和笔记仓提交。该行完成后改为“已处理”。只提交笔记仓，不推送；资料仓交给 dev-skills 管理。

## 5. 项目口径与用户选择

固定规范区使用 1.5 的讲解规范和表达规范。项目口径区可打开默认关闭的“面试怎么讲 + 高频追问”、版本演进叙述或更深原理；面试内容直接由已经验证的追问整理，不新编经历或能力。

用户要求优先于固定规范，偏离之处在变更记录用普通文字说明。重复出现的项目特有问题，可在项目口径区记录问题、适用范围和正反例；不另起通用检查编号体系，不在运行时修改 Skill 本身。
