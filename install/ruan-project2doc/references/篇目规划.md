# 篇目规划

U-规划读本文件，用 `_规划方案.md` 记录选择。先发现系统在做哪些事，再决定读者需要哪些篇；篇数和链路分数都不是目标。

## 1. 找出入口、终点和链路

入口是外部能触发本项目代码开始执行的位置，例如一次用户操作、公开函数调用、消息到达或定时触发。终点是这次执行留下的可独立检查的结果，例如响应、返回值、稳定界面状态、持久记录、文件或下游消息。链路是从一个或多个入口沿真实调用和交接关系，走到第一个这样的终点的执行路径。

入口写实际触发点，不只写模块名；终点写具体结果，不只写“处理完成”。例如通用场景中，“调用导出函数，返回序列化结果”可以成为库的链路，“发送创建请求，生成记录并返回编号”可以成为服务的链路。两者都不要求有数据库或消息系统。

先正向找入口，再从返回、写入和外部交接反向找终点，对照补漏。有 project-map 时借其主体流程作为候选，不直接采用其模块边界。后台清理、订阅回调、定时任务和工作线程也有入口，应登记去向。

| 项目形态 | 入口线索 | 终点线索 | 关注的状态与关系 |
|---|---|---|---|
| HTTP / RPC 服务 | 路由、处理函数、中间件、启动钩子 | 响应、持久记录、消息、外部调用结果 | 身份、持久状态、事务、跨服务交接 |
| 消息或任务服务 | 订阅、监听、调度、批处理注册 | 结果记录、确认、下游消息、失败队列 | 重试、去重、任务状态 |
| 前端应用 | 路由、用户操作、初始化、轮询 | 页面稳定状态、请求、本地保存结果 | 表单、状态仓库、请求与响应 |
| 移动客户端 | 导航、推送回调、后台任务、启动 | 本地记录、界面、通知、请求 | 离线状态、同步游标、跨端契约 |
| 数据或模型管道 | 作业、调度定义、触发器 | 输出数据、文件、模型产物、指标 | 中间产物、检查点、水位、失败重跑 |
| 命令行工具 | 命令注册、参数解析、主函数 | 输出、退出码、文件、外部操作结果 | 参数、配置、执行副作用 |
| 库 / SDK | 导出函数、公开类和方法 | 返回值、错误、回调、传入对象变化 | 实例状态、注册表、调用契约 |
| 多端或单仓多项目 | 各子项目分别发现 | 子项目结果及跨端交接 | 接口、共享存储或消息约定 |

该表只帮助寻找线索，最终以目标项目代码为准。无法归类时回到入口和终点定义，不强行套某一技术栈。

## 2. 分数帮助筛选，不替代成篇判断

每条候选按六项各记 0 或 1，并逐项写理由：改变持久状态；跨进程或跨系统交接；有失败处理、重试或补偿；产生用户可见结果；终点被其他链路依赖；用户点名。

默认参考是：3 分及以上作为独立成篇候选，1–2 分优先并入相关篇或在 00 简述，0 分优先登记为不展开并写原因。数字为默认值、可后改，所有入口的最终去向进入 99。分数够而只有简单增删改查、没有独立学习价值的链路可以合并；低分但能解释重要机制的链路也可以独立成篇。差别仅在少量分支的链路优先按主题合并，并记录理由。

## 3. 给机制定级，指定主讲篇

| 级别 | 判据 | 讲解要求 |
|---|---|---|
| 核心 | 承担安全、一致性、可靠性或性能等关键质量目标；被两条以上主流程依赖；容易被直觉误解；或用户点名 | 主讲篇完整回答七问，其他使用篇给①问题、③实现、⑤失败的够用讲解 |
| 支撑 | 在流程中有独立作用，但主要服务一两处 | 使用处至少讲①③⑤ |
| 细节 | 不改变读者对流程或机制的理解 | 一句带过或不写，理解稿记去向 |

使用广度的数字为默认值、可后改。级别依据写到机制清单中，不能把用户关心的机制降级以省篇幅。每个核心机制有一个主讲篇；这是完整讲解的安排，不限制其他篇提供够用讲解。

机制被多条链路使用而需要全貌，有较多独立原理或方案比较，或被用户点名时，考虑机制专题篇。只有一条使用链路且适合就地讲清的核心机制，直接在该链路篇完整展开。多个小机制属于同一主题时可以合为专题。

例子来自《定位与标杆》：缓存标杆把读、写、失效和多处使用联系起来，适合专题；认证标杆以同一会话组织登录、刷新和收回，适合链路篇。旧版反例把缓存、限流都推到别篇，只留下参数；新规划须明确使用篇仍讲哪些工作方式与故障行为。

## 4. 定篇目、学习目标和追问

在 `_规划方案.md` 中记录链路候选与理由、机制清单与级别、主讲篇、两类篇的篇目表、各篇范围及不展开内容的去向、阅读顺序、学习目标、追问和全仓库入口去向。

每篇用 3–5 个具体问题写“本篇回答”，数量是默认值、可后改。按《质量门》G1 的 L1–L5 生成追问：核心机制每层至少一题，支撑机制至少 L2、L4 各一题，关键判断点至少一个 L3；把用户关心的问题逐个纳入。追问应需要解释真实步骤或条件，不只是背一个名词。

阅读顺序通常先选一条代表系统的主链路，再读它所依赖的机制专题，然后进入其他链路。根据目标读者调整，不按源码目录或机制数量机械排序。

00 先写系统用途、组成与主线图的骨架、核心机制与主讲篇、阅读路线及易混淆术语，待研读后补足结论。全仓库入口清单、不展开原因、核验信息交给 99。`_术语表.md` 约定叫法，`_衔接约定.md` 记录输入输出、主讲篇与使用篇需要的够用范围。正文篇尾用一两句话说明留下了什么、交给谁。

## 5. 确认规划

展示篇目和阅读顺序、机制级别与主讲篇、学习目标、追问，以及用户重点的落点。得到用户确认后，记录日期和调整内容，才把规划复制进需求包并交接编排。已有本次有效授权可以按授权范围执行并如实记载，不伪造用户回答。

研读发现范围或关键认识变化时，先更新受影响的规划与交接关系；涉及篇目或用户重点的实质调整，按已有授权范围确认，交 ruan-dev-skills 调整后续步骤。不能让旧规划反过来限制源码结论。
