# 编排、交接物与生成方向

**何时读本文件**：每个单元开始时读与它相关的一节；U-拆分要读第 1–4 节和第 7 节。

## 1. 为什么交给 ruan-dev-skills

一次性完成“全仓库阅读 + 链路梳理 + 撰写 + 优化”，上下文会被撑满，越往后越涣散：术语漂移、重复叙述、丢失主线、与前文矛盾。所以本 Skill 把长任务拆成单元，单元之间靠落盘的交接物衔接，编排、进度和恢复全部交给 ruan-dev-skills。

ruan-dev-skills 的约束和本 Skill 的应对：

| dev-skills 的规定 | 对本 Skill 意味着什么 |
|---|---|
| 版本目录必须是 `<项目总目录>/docs/AI dev docs/<版本号>/`，资料仓是独立 Git 根；代码仓是当前工作目录的 Git 根 | 笔记工程目录把笔记仓、需求包、资料仓并列摆放（结构见 `需求包规格.md`）。笔记仓就是 dev-skills 眼中的“代码仓” |
| 步骤完成以代码仓的提交 hash 为强证据 | 每个步骤验证通过后在**笔记仓**提交，提交 hash 就是完成证据 |
| S001 固定为“环境确认与原始基线建立” | 对笔记仓没有构建可跑，照常执行，只确认笔记仓状态并记录基线 |
| 《开发协议》《开发接力提示词》原样复制，不按需求改写 | 笔记怎么写、怎么取证、怎么校对，**不能写进这两份文件**，只能放进需求包（归档为 `plans/P001-*/`）和 dev-skills 生成的步骤文件 |

分工：

| 谁 | 做什么 |
|---|---|
| ruan-project2doc（首次调用） | 检测 project-map、勘察仓库、做拆分方案并请用户确认；生成笔记仓骨架和需求包；调用 dev-skills 初始化 |
| ruan-dev-skills | 归档需求包为 P001，规划步骤（S001 + 每篇的取证、成文、校对 + 收束），生成进度与接力文件 |
| 后续每个新会话 | 用《开发接力提示词》推进一个步骤；写笔记仓、提交、回写进度 |
| 用户后续修改 | 在修改提示词文档里追加要求，按 `修改协议.md` 处理 |

## 2. 单元类型

一个项目就是一个“笔记目录生成任务”。U-勘察和 U-拆分由本 Skill 在首次调用时完成，之后的单元由 dev-skills 规划成 S 步骤。S-ID 的编号、拆分和废弃完全按 dev-skills 开发协议执行。

| 单元类型 | 数量 | 由谁执行 | 划分依据 |
|---|---|---|---|
| U-勘察 | 1 | 本 Skill 首次调用 | 检测 map、基准、技术栈，建立笔记工程目录 |
| U-拆分 | 1 | 本 Skill 首次调用 | 定篇目、起点和终点、篇间接口、术语表初稿；产出 00 骨架；用户确认后生成需求包并调用 dev-skills 初始化 |
| S001 环境确认 | 1 | dev-skills 规定 | 对笔记仓只记录基线，照常通过 |
| U-取证（每篇一个） | 篇数 | dev-skills 步骤 | 为一篇笔记取证，产出事实摘要 |
| U-成文（每篇一个） | 篇数 | dev-skills 步骤 | 只读事实摘要和交接物，写成笔记 |
| U-校对（每篇一个） | 篇数 | dev-skills 步骤（天然是独立的新会话） | 可读性校对，见 `校对协议.md` |
| U-收束 | 1 | dev-skills 步骤 | 回写 00 的衔接与术语，写 99，生成修改提示词文档，全局一致性检查 |

**粒度**：一篇对应“取证 + 成文 + 校对”三个单元。取证和成文分开，是因为取证要大量读源码，而成文需要腾出来的上下文去组织叙事；两者放在一个会话里，正是“后半段涣散”的主要来源。

**超长篇的再拆**：取证阶段发现事实摘要超出预算，或触发拆篇信号（`概念定义.md` K18：同级步骤超过约 15 步、跨过两个可观测终点、事实摘要超过约 60 条、读入超出预算），就回到 U-拆分，把这一篇拆成两篇。拆的是篇，不是一篇里的段落：拆半篇会破坏“一篇一条链路”。

每个 dev-skills 步骤的“验证方式”写成 `自检清单.md` 中对应时机的检查；验证通过后在笔记仓提交。

## 3. 每个单元的输入、输出、完成判据

| 单元 | 读什么 | 明确不读 | 输出 | 完成判据 |
|---|---|---|---|---|
| U-勘察 | 目录树、构建文件、map 的 STATE/COVERAGE/模块状态行、`git log -1` | 模块正文、业务源码 | `_勘察结果.md` | 基准、map 状态、规模都写明 |
| U-拆分 | map 总览（或无 map 时的发现结果）、入口与汇点表、用户给的重点 | 下层模块的执行图与候选表 | `_拆分方案.md`、`_术语表.md` 初稿、`_衔接约定.md`、00 骨架 | 每篇有起点、终点状态、不覆盖项与去向；用户已确认 |
| U-取证 | 本篇对应的 map 模块（只读相关节点与未决）、本篇入口到终点之间的源码、`_术语表.md` | 其他篇的源码与 map 模块 | `_事实/NN.md`（含关键步骤覆盖矩阵、附录 B 自查结果） | 每条事实有来源与核对标记；关键数据都追到来源；矩阵每行为“已覆盖”或写明去向；B1、B2 组无未处理的 P0、P1 |
| U-成文 | `_事实/NN.md`、`_术语表.md`、`_衔接约定.md`、`写作规范.md`、`约束取舍表.md` | 源码（需要新事实时回退到 U-取证）、其他篇正文 | `NN-标题.md` | 符合单篇模板；正文里没有不在事实摘要中的事实；附录 A 自查已执行 |
| U-校对 | 该篇、相邻篇事实摘要的首尾、`写作规范.md`、`约束取舍表.md`、`问题清单.md` | 源码、其他篇全文 | 修改后的该篇、`_校对记录/NN.md`（按 ID 逐条记录命中位置） | `校对协议.md` 的停止条件满足 |
| U-收束 | 各篇的标题目录与首尾、`_术语表.md`、`_衔接约定.md`、全部事实摘要的“未确认”节、`_问题台账.md` | 各篇正文全文 | 00 定稿、99、修改提示词文档 | `自检清单.md` 全局项（含 F30–F32）通过 |

**预算**：不写死字节数，规则是“单元读入的原始材料加产出，不超过上下文的一半”（默认值，可后改）。另一半留给推理和自检。U-取证最容易超：它读的源码量取决于链路长度，所以超出时的动作是拆篇，而不是“少读一点”。

## 4. 交接物（落盘在 `笔记/_工作区/`，随笔记仓一起提交）

模板都在本 Skill 的 `templates/`，`scaffold` 命令会复制进来。

| 交接物 | 内容 | 何时更新 |
|---|---|---|
| `_勘察结果.md` | 源码基准、project-map 基准与状态、技术栈与规模 | U-勘察写；源码基准变化时更新 |
| 进度（不由本 Skill 维护） | dev-skills 的《当前状态》《步骤总览》 | 按 dev-skills 开发协议，每步结束时回写 |
| `_拆分方案.md` | 篇目、链路打分、每篇的起点与终点、不覆盖项及去向、对应 map 模块与节点 ID | U-拆分写；拆篇时更新 |
| `_术语表.md` | 术语、本项目中指什么、首次出现在哪篇、源码名 | U-拆分建初稿；U-取证**可以追加，不可以改已有词条的含义**（改含义要回 U-拆分） |
| `_衔接约定.md` | 相邻两篇的交接物（上一篇终点 = 下一篇起点的同一事物）；跨篇机制归属哪篇 | U-拆分写；U-取证发现不一致时记一条冲突，由 U-收束处理 |
| `_事实/NN.md` | 本篇事实条目（`概念定义.md` K15 格式）、关键数据追溯、关键步骤覆盖矩阵、自查结果 | U-取证写；U-成文只读 |
| `_校对记录/NN.md` | 每轮校对按附录 A 的 ID 记录命中位置（节号 + 原句）与处理方式，以及退回准确性链路的条目 | U-校对写 |
| `_问题台账.md` | 附录 B 命中的问题：ID、优先级 P0–P2、篇、问题、代码依据、状态（open / fixed / needs_user_decision） | U-取证、U-校对登记；U-收束要求无 open |

**事实摘要为什么一条一行**：上层引用下层事实时，引用的是条目编号，而不是凭记忆复述；修改时也能按编号追溯。

## 5. 中断与恢复

恢复完全交给 dev-skills：新会话打开版本目录里的《开发接力提示词》，按开发协议开工对账（读《当前状态》、核对笔记仓 HEAD 与基线、判断半成品），不依赖对话记忆。

本 Skill 只补一件 dev-skills 不知道的事：**被分析的源码仓变了怎么办**。每个 U-取证步骤开工时，比较源码仓 HEAD 与 `_勘察结果.md` 的基准：

```bash
git -C "<源码仓>" rev-parse HEAD
git -C "<源码仓>" diff --stat <基准> HEAD
```

变化了就列出受影响的篇目（看各篇事实摘要里引用的路径），作为“需求调整”交给 dev-skills 新增重新取证的 S 步骤，**不在当前步骤里顺手处理**。

## 6. 退化信号与动作

| 信号 | 怎么发现 | 动作 |
|---|---|---|
| 术语漂移：同一对象换了叫法，或用了 `_术语表.md` 没有的叫法 | 成文后用术语表逐词检查；`project2doc.py consistency` | 回读术语表，修正；同一单元内出现两次就结束单元、换会话 |
| 主线丢失：一级节读完不能用一两句话复述 | 附录 A 的 R20 | 交给 U-校对；如果是结构问题，退回 U-拆分 |
| 重复叙述：同一机制在本篇讲了两遍，或别篇已有归属仍完整重讲 | 对照 `_衔接约定.md` 的机制归属 | 改为引用；频繁出现说明单元过大，下次拆小 |
| 与前文矛盾：数字、状态名与事实摘要或术语表不一致 | 成文自检时逐个对照数字 | 以事实摘要为准；事实摘要本身有疑问时退回 U-取证 |
| 正文出现事实摘要里没有的事实 | 成文自检 | 删掉，或退回 U-取证补证；不在成文单元里临时查源码 |

总原则：发现信号时优先**结束当前单元并换会话**，而不是在当前会话里继续修补，因为涣散本身就是上下文过满的结果。

## 7. 进度可见性与用户验收节点

每个步骤结束时按 dev-skills 开发协议回写并提示开新会话，另外报告一行：本步产物、未确认项数量。

用户验收节点有两类：拆分方案确认一次（U-拆分）；之后每篇的取证、成文、校对三个步骤都完成后确认一次。实现方式：需求包要求 dev-skills 把每篇校对步骤的“下一动作”写成“等待用户确认第 NN 篇”，用户确认后再开下一个会话。

## 8. 没有 ruan-dev-skills 时

硬依赖：开工检测到未安装，就停下并提示先安装，不提供降级编排。理由：降级编排等于在本 Skill 里再实现一套同类机制，正是要避免的跑偏风险。

## 9. 生成方向：混合方案

三个阶段：

1. **骨架**（U-拆分）：篇目、起点与终点状态、接口、术语初稿、机制归属。00 只写边界和清单，“一句话结论”一节先空着，收束时再填。
2. **逐篇自底向上**（U-取证 → U-成文 → U-校对）：篇内先取证落盘，再成文。篇与篇之间按衔接顺序进行，让后一篇能读到前一篇的终点摘要。
3. **回顶层统一**（U-收束）：用各篇事实摘要回填 00 的一句话结论和衔接段，统一术语和过渡，写 99。

**关键限定**：骨架**只能包含范围、起点和终点状态、接口、术语初稿，不包含任何事实结论**（例如“某机制保证了什么”）。否则它就退化成自顶向下，后面的取证会去迁就骨架，把推断写成事实。

| 失败模式 | 预防 |
|---|---|
| 骨架里夹带事实结论，取证迁就骨架 | U-拆分的产物只允许范围、状态名、接口；U-收束才写结论 |
| 取证推翻了切分点（例如终点状态并不存在） | 退回 U-拆分，只改受影响的相邻篇，记入 `_拆分方案.md` |
| 逐篇推进时前后篇术语不一致 | `_术语表.md` 只能追加，改含义必须回 U-拆分 |
| 收束阶段“顺手”改写各篇事实 | U-收束只能改 00、99 和各篇的过渡句，不改正文事实 |

例外：用户提供了已确认的权威设计文档时，骨架可以引用它并注明出处（`约束取舍表.md` C19）。

## 10. 上层引用下层事实的规则

1. 00、99、篇首的一句话主线、篇尾的接口段，引用的事实**只能来自已落盘的 `_事实/NN.md`**，在工作区注明条目编号（编号不进正文），不凭记忆复述。
2. 概括可以降低细节，但**不能提高结论强度**：下层是“推断”，上层不能写成确定事实。

## 11. 跨篇一致性

- 术语：以 `_术语表.md` 为唯一来源，00 的术语表从它生成；
- 数字：同一数字只有一个事实条目，其他篇引用该条目；
- 流程名和状态名：在 `_衔接约定.md` 里固定，篇首篇尾的接口必须使用同一个名字。

## 12. 下层与上层冲突时的回修

优先级：**当前源码 > 事实摘要 > 衔接约定和术语表 > 拆分方案 > 00 和过渡句**。

发现冲突时，按优先级找到第一个有错的层修正，再向下游传递：改了事实摘要，就重新成文受影响的段落；改了衔接约定，就更新相邻两篇的接口段；改了拆分方案，就重做受影响篇目的取证。每次回修按 dev-skills 开发协议“范围外问题新增 S-ID”处理，不改已完成步骤的记录。
