# ruan-project2doc 1.4.0

把一个项目仓库读透，写成一套按关键链路展开的中文笔记：每篇以一条主流程为主干，忠于当前源码，读者能顺着读下去。再配一份修改提示词文档：用户以后在里面追加要求，AI 据此修改一篇或多篇。

目标读者：有一般软件工程基础、但不熟悉本项目的开发者（定义见 `references/概念定义.md` K13）。面试视角不是默认内容，用户可以在修改提示词文档里加。

下文 `<SKILL>` 指本 Skill 的安装目录，`<工程>` 指笔记工程目录（默认仓库同级的 `<仓库名>-笔记工程/`）。

## 硬边界

- **被分析的仓库和 project-map 只读**：不改代码，不改 map 的状态和未决，不运行任何写入命令。所有产出都写在 `<工程>/` 下。
- **只提交笔记仓 `<工程>/笔记/`，从不推送**。资料仓 `<工程>/docs/AI dev docs/` 的提交由 ruan-dev-skills 负责。
- **面向任意项目**：规则用“入口、终点、状态、跨系统交接”这类与技术栈无关的词。写进笔记的例子必须来自目标项目自己的代码；references 里的例句只说明问题长什么样，不代表目标项目里有这些组件。
- **长任务编排全部交给 ruan-dev-skills**，本 Skill 不另建进度、恢复机制。理由：自建同类机制容易跑偏。
- **准确优先于顺口**：校对只改表达；涉及事实的改动一律回到取证（`references/约束取舍表.md` C17）。
- 不在运行时修改本 Skill 自身。项目特有的规则写进该项目修改提示词文档的项目口径区。

## 不适用（开工时识别，说明原因后停止，不做降级处理）

- 单个函数或类的解释、局部代码问答：直接回答即可；
- 建立带闸门与验收的执行流程知识库：用 ruan-project-reader；
- API 参考手册、部署手册、需求文档；修改业务代码；没有源码只有需求的分析；
- 没有执行链路的仓库：纯配置或基础设施即代码仓库、纯文档仓库等。判断依据：按 `references/概念定义.md` 附录 G 找不到任何入口（K01）。

## 先判断是哪种调用

| 情况 | 怎么识别 | 做什么 |
|---|---|---|
| 首次生成 | 没有 `<工程>/`，或有但 `笔记/_工作区/_拆分方案.md` 还没有“用户已确认”标记 | 走「首次调用流程」；已有 `_勘察结果.md`、`_拆分方案.md` 就从它们恢复，不重做 |
| 继续生成 | 已有 `<工程>/docs/AI dev docs/<版本>/开发接力提示词.md` | 不在本 Skill 里自行续写。读这份接力提示词并照它执行：按 dev-skills 开发协议开工对账，只推进当前一个步骤 |
| 正在执行某个 dev-skills 步骤 | 《当前状态》指向某个 S 步骤，步骤文件引用 P001 | 以步骤文件和 `plans/P001-*/` 里的需求包为准。需求包的规则是本 Skill references 的副本，按步骤文件引用的文件名读取 |
| 修改已有笔记 | 用户说“按修改提示词改”“改一下第 N 篇”“我加了要求” | 走「修改流程」 |

## 开工检查（自行检测，只报告，不问用户）

```bash
python "<SKILL>/scripts/project2doc.py" deps
```

- **ruan-dev-skills 未安装就停止**，提示用户先安装，不提供降级编排（硬依赖）。
- 没有 Git 就停止。没有 Python 时，按 `references/project-map借鉴.md` 的人工步骤做同样的检查，并在 `_勘察结果.md` 写明“脚本未执行”。
- 先跑一次 ruan-project-reader 可以降低取证成本，但不是必须的。没有 project-map 时只提示一句；用户选择继续，就不再提。

## 开工确认（一次问清这三项，之后自主推进）

| 问题 | 默认值 | 说明 |
|---|---|---|
| 仓库路径，以及要分析的版本或分支 | 当前 HEAD | 范围固定为全仓库 |
| 输出目录 | 仓库同级 `<仓库名>-笔记工程/` | 目录结构见 `references/需求包规格.md` |
| 你自己的重点或已知关键流程 | 可不填 | 填了就作为拆分方案的召回检查：方案里漏掉的要说明理由 |

**必停点只有两类**：拆分方案出来后确认一次；之后每篇的取证、成文、校对都完成后确认一次。其余步骤自主推进。理由：这两处返工代价最大。

## 工作流总表

| 步骤 | 做什么 | 满足这一条才往下走 | 谁执行 |
|---|---|---|---|
| 1 读仓库 | 检测 project-map、技术栈、规模；建笔记工程目录 | `_勘察结果.md` 写明源码基准、map 状态、规模 | 本 Skill 首次调用（U-勘察） |
| 2 识别链路 | 有 map 时从总览的主体流程起步；没有时做轻量正反向发现 | 每条候选链路都有入口和终点状态 | 本 Skill 首次调用 |
| 3 拆分 | 定篇目、每篇的起点和终点、篇间接口、术语表初稿 | **用户确认拆分方案（必停点）** | 本 Skill 首次调用（U-拆分） |
| 4 交接编排 | 生成需求包，调用 ruan-dev-skills 初始化 | 资料仓状态为“可接力” | 本 Skill 首次调用 |
| 5 写作 | 每篇先取证写事实摘要，再成文 | 事实摘要每条都有来源；成文符合单篇模板 | dev-skills 步骤（U-取证、U-成文） |
| 6 校对 | 准确性自检和可读性校对分开做 | 自检清单通过；**用户确认该篇（必停点）** | dev-skills 步骤（U-校对） |
| 7 收束 | 回写 00 的衔接与术语，写 99，生成修改提示词文档 | 全局检查通过，问题台账无 open | dev-skills 步骤（U-收束） |

单元的输入、明确不读的内容、输出和完成判据见 `references/编排与交接物.md`。生成方向是混合方案：先定骨架（只含范围、状态名、接口，**不含任何事实结论**），再逐篇自底向上取证成文，最后回到顶层统一。

## 首次调用流程

1. **识别与检查**：确认不属于不适用场景；运行 `deps`。
2. **开工确认**：一次问清上面三项。
3. **建笔记工程**（机械复制，不覆盖已有文件）：

   ```bash
   python "<SKILL>/scripts/project2doc.py" scaffold --project "<工程>" --repo-name "<仓库名>"
   ```

   它会建好 `笔记/`（独立 Git 根）、`笔记/_工作区/` 的交接物模板，以及 `需求包/` 里的规则副本、模板副本和脚本副本。
4. **U-勘察**：读 `references/project-map借鉴.md`，运行

   ```bash
   python "<SKILL>/scripts/project2doc.py" survey --repo "<仓库>" [--map "<project-map>"]
   ```

   按输出填写 `笔记/_工作区/_勘察结果.md`。只读目录树、构建文件、map 的 STATE、COVERAGE 和模块状态行、`git log -1`；**不读模块正文和业务源码**。
5. **识别链路**：有 map 时，map 总览的主体流程只作拆分候选；没有 map 时，按 `references/project-map借鉴.md`「没有 project-map 时」做正向入口和反向终点发现，入口和终点的对应物查 `references/概念定义.md` 附录 G。
6. **U-拆分**：读 `references/编排与交接物.md` 的 U-拆分一节和 `references/概念定义.md` 的 K02–K04、K14、K18、K19。产出：
   - `_拆分方案.md`：每条链路按 K04 六项打分并逐项写理由；≥3 分为独立成篇候选，1–2 分并入相关篇的补充块或在 00 速览，0 分写进 00 的不覆盖表；每篇写起点入口、终点（按 K02 的“去哪查 / 查什么 / 看到什么算到达”）、不覆盖项及去向、对应的 map 模块与节点 ID；
   - 横切专题清单（附录 B 的 F31）和所有定时任务、消息监听、后台线程的去向（F30）；
   - `_术语表.md` 初稿、`_衔接约定.md`；
   - 按 `templates/00-总览与主线地图.md` 写 00 的骨架：只写边界和清单，“一句话结论”一节先空着。
7. **必停点：请用户确认拆分方案**。展示篇目表、每篇的起点和终点、分数、不覆盖表，以及用户点名的重点在方案里的落点。用户调整的内容记进 `_拆分方案.md`。确认后在文件顶部写上“用户已确认：<日期>”。
8. **写需求包**：读 `references/需求包规格.md`，填写 `需求包/00-任务说明.md`、`需求包/02-步骤拆分要求.md`，把确认后的 `_拆分方案.md` 复制为 `需求包/01-拆分方案.md`。然后在笔记仓提交骨架（只提交 `笔记/`）。
9. **调用 ruan-dev-skills 初始化**：加载 ruan-dev-skills（能用 Skill 工具就用它，否则读它的 `SKILL.md`），在 `<工程>/笔记/` 作为工作目录的前提下，以初始化模式执行：需求材料 = `<工程>/需求包/`，版本目录 = `<工程>/docs/AI dev docs/笔记v1/`（版本号默认 `笔记v1`，可后改）。按它的规则做完，直到资料仓状态为“可接力”。在 Windows 上运行它的 `devdocs.py` 时加 `python -X utf8`，否则中文路径会让它解码失败（见 `references/需求包规格.md` 第 4 节）。
10. **交付本次调用**：报告下面「最终汇报」的内容，并提示用户用 `<版本目录>/开发接力提示词.md` 开新会话推进。**不要在本次调用里开始 U-取证**：取证和成文分在不同会话，是为了不让上下文后半段涣散。

## 修改流程

细则见 `references/修改协议.md`，这里是骨架：

1. 只处理修改提示词文档「三、用户追加区」里状态为“待处理”的行。
2. 目标篇已填就只改这些篇；没填就按术语表的首次出现篇和衔接约定的机制归属，列出受影响篇目和理由，**等用户确认后再改**。
3. **只改一篇、只涉及表达**的修改可以在当前会话直接改：按 `references/校对协议.md` 的权限边界执行，改完在笔记仓提交并写变更记录。
4. **涉及事实或多篇**的修改必须走 ruan-dev-skills 的调整模式：把修改提示词文档（连同已确认的篇目清单）作为新需求材料交给它，归档为新的 Pxxx，再由它规划修改步骤（涉及事实的先规划取证步骤）。
5. 用户要求和固定规范冲突时，以用户要求为准，并在变更记录里写明偏离了哪条规范。

## 每个单元都要守的纪律

- 单元只读 `references/编排与交接物.md` 规定的输入。读入的原始材料加产出，不超过上下文的一半（默认值，可后改）；超出时拆篇，不是“少读一点”。
- 自检按 ID 执行并落到文件，逐个写“命中位置 / 无”。只写“已检查”视为没有执行。
- 发现退化信号（术语漂移、主线丢失、重复叙述、与前文矛盾、正文出现事实摘要里没有的事实）时，优先结束当前单元、换会话，不在当前会话里继续修补。
- 冲突回修的优先级：当前源码 > 事实摘要 > 衔接约定和术语表 > 拆分方案 > 00 和过渡句。

## references：什么时候读哪一份

| 文件 | 内容 | 什么时候读 |
|---|---|---|
| `references/project-map借鉴.md` | 检测、信任分级、核对、冲突、来源记录、无 map 时的路径 | U-勘察、U-取证 |
| `references/编排与交接物.md` | 与 dev-skills 的分工、单元表、交接物、中断恢复、退化信号、生成方向、跨篇一致性 | 每个单元开始时读相关一节 |
| `references/写作规范.md` | 单篇结构、叙事规则、源码名的用法、写作规范表、事实分层与不确定内容的写法 | U-成文、U-校对 |
| `references/约束取舍表.md` | C1–C23：目标、失败方式、冲突时怎么取舍 | U-成文、U-校对、修改时 |
| `references/校对协议.md` | 校对的输入、两轮分工、权限边界、停止条件 | U-校对、修改时 |
| `references/修改协议.md` | 修改提示词文档的使用协议 | 修改时 |
| `references/自检清单.md` | 什么时机执行哪一组检查、结果写到哪里、全局检查与验收 | 每个单元结束时 |
| `references/概念定义.md` | K01–K19 操作化定义；附录 G 各技术栈的入口、终点、状态映射 | U-勘察、U-拆分、U-取证；任何步骤遇到这些概念时 |
| `references/问题清单.md` | 带 ID 的完整清单：R（可读性）、F（全面性与准确性）、M（修改行为），以及维护规则 | U-取证、U-成文、U-校对、修改时；只按 ID 引用 |
| `references/需求包规格.md` | 笔记工程的目录结构、需求包组成、调用 dev-skills 的参数 | 首次调用、修改时 |

模板在 `templates/`：单篇笔记、00 总览、99 复核说明、修改提示词文档，以及交接物 `_勘察结果`、`_拆分方案`、`_术语表`、`_衔接约定`、`_事实`、`_校对记录`、`_问题台账`，需求包的 `00-任务说明`、`02-步骤拆分要求`。

## 辅助脚本 `scripts/project2doc.py`（Python 标准库）

| 命令 | 读写 | 做什么 |
|---|---|---|
| `deps` | 只读 | 检查 Python、Git、ruan-dev-skills、ruan-project-reader 的 `check.py`、“说人话”类 Skill 是否可用 |
| `survey --repo R [--map M]` | 只读 | 找 project-map，读状态行与 STATE 统计，比对基准提交和 HEAD，列出变化路径，运行 reader 的 `check.py`（只读形式），统计技术栈与规模 |
| `scaffold --project P --repo-name N` | 只新建 | 建笔记工程骨架，复制交接物模板、规则副本、模板副本、脚本副本；已存在的文件一律不覆盖 |
| `progress --notes 笔记 --version-dir V` | 只读 | 核对《步骤总览》里已完成步骤的提交 hash 是否在笔记仓中，以及各篇产物是否齐全 |
| `consistency --notes 笔记` | 只读 | 00 的篇目清单和实际文件、跨篇源码名是否进了术语表、衔接约定的接口名是否出现在相邻两篇、事实编号、问题台账 open 数、自查记录是否逐 ID 落盘 |
| `lint --file F [--words W ...]` | 只读 | 列出修改痕迹词（M01）、AI 味词（R07）、非标准补充标签（R23）、推销式标题（R33）、模板化转场（R40）的**候选**命中；是否真有问题由人判断 |
| `render-revise --notes 笔记 --repo-name N` | 只新建 | 用 `templates/修改已有笔记.md` 和 references 拼出修改提示词文档；文件已存在就拒绝，避免覆盖用户追加区 |

可读性判断不脚本化。脚本输出只是线索，不能代替按 ID 的人工检查。

## 最终汇报

首次调用结束时报告：

1. 笔记工程位置；源码基准；project-map 情况（有无、状态、基准是否过期、`check.py` 退出码）。
2. 已确认的篇目数，以及不覆盖项的数量。
3. dev-skills 初始化结果：版本目录绝对路径、步骤数、当前步骤。
4. 下一步：用 `<版本目录>/开发接力提示词.md` 开新会话推进；每篇三个步骤完成后会停下来等用户确认。

修改结束时报告：改了哪些篇哪些节、改动类型、退回准确性链路的条目、笔记仓提交 hash；走 dev-skills 时报告新的 P-ID 和规划出的步骤数。
