# ruan-project2doc 1.6.0

把一个项目讲懂给初学者。读者会写一般业务代码、能读懂源码、知道常见技术名词，但还不熟悉本项目，也未必理解这些技术怎样配合。必要原理讲到足以理解本项目实现与备选方案差别为止。

读完一篇，读者能做到四件事：**讲整体**（解决什么问题、有哪些参与方和核心对象、分哪几个阶段、每阶段留下什么）、**讲流程**（关键数据从哪里来、在哪里被校验或改变、最后交给谁）、**讲机制**（问题、原理、实现、失败处理与取舍）、**经得起追问**（再回答两三层）。四条标准与讲解手法见 [定位与标杆](references/定位与标杆.md)。

**准确是底线，理解是目标，可读是手段，覆盖服从理解。** 正文讲解系统，源码位置与核对过程保留在理解稿和 99。写进笔记的事实一律回目标项目的当前源码核实。

下文 `<SKILL>` 是本 Skill 所在目录，`<工程>` 是笔记工程，`<笔记>` 是 `<工程>/笔记/`。

## 硬边界

- 源码仓和 project-map 只读，不改代码、状态或未决，不在其中运行写入命令；所有产出写入独立的笔记工程。
- 只提交笔记仓，不推送；资料仓的操作由 ruan-dev-skills 负责。长任务的步骤、进度和恢复全部交给它，不另建同类机制。
- 面向任意技术栈。入口、终点、状态和机制由目标源码决定，不能假设一定存在样例中的组件。references 的正反例只说明写法。
- 不为表达顺畅改变事实、条件或结论强度。新事实先核实并更新理解稿，再进入正文。
- 不在运行时修改本 Skill。项目特有要求写进该项目修改提示词文档。
- 对 frontmatter 列出的不适用场景说明原因后停止，不降级生成一套不相符的笔记。库和 SDK 适用：公开调用、返回值、错误、回调与实例状态同样构成可讲解的执行关系。
- 两个确认点由用户做出：规划确认、每篇审读通过后的确认。已有明确授权时按授权范围执行并记录依据；生成文件或脚本成功不等于用户确认。

## 判断调用类型

| 类型 | 识别与动作 |
|---|---|
| 首次生成 | 尚无已确认规划；按下面流程做勘察、规划、确认和交接。已有材料则先核对后继续，不覆盖。 |
| 继续生成 | 已有 dev-skills 接力提示词；读取它并按当前步骤恢复，只推进该步骤。先按 [修改协议](references/修改协议.md) 核对工程的规则版本，与当前安装版本不同时用一句话告知用户，不混用两版规则。 |
| 执行编排步骤 | 以步骤文件和归档需求包为准，读本单元指定的规则与交接物。 |
| 修改已有笔记 | 按 [修改协议](references/修改协议.md) 处理修改文档中待处理的要求；先判断缺口在哪一层，再选修改路径。 |

## 开工检查与确认

运行辅助脚本需要 Python 3.8+（仅标准库）和 Git；长任务编排需要 ruan-dev-skills 2.0，可选借鉴 project-map。

先运行 `python "<SKILL>/scripts/project2doc.py" deps`，检查 Git、ruan-dev-skills 和可用的表达检查能力。缺少 Git 或 ruan-dev-skills 时停止，说明缺少什么；没有 Python 时如实记录脚本未执行，按 [project-map借鉴](references/project-map借鉴.md) 人工完成相应检查。

核对仓库路径和分析基准（默认 HEAD）、输出目录（默认仓库同级的 `<仓库名>-笔记工程/`）、用户重点。用户已经提供的直接沿用，只补问影响工作的缺项。分析范围固定为全仓库；没有 project-map 时只提示一次，可按源码入口与终点发现继续。

## 流程总表

| 单元 | 做什么 | 主要产物 | 继续条件 |
|---|---|---|---|
| U-勘察 | 建笔记工程，核对源码基准、规模与 map 状态 | `_勘察结果.md` | 源码基准、map 状态和范围已明确 |
| U-规划 | 发现链路与机制，定级、定篇目与组织方式预判，写学习目标、追问清单和规划期的 00 | `_规划方案.md`、00、术语表、衔接约定 | **必停点一：用户确认规划** |
| 交接编排 | 填需求包，交 ruan-dev-skills 初始化 | 资料仓达到“可接力” | 首次调用到此结束 |
| U-研读 | 沿本篇源码弄懂流程与机制，写理解稿，设计讲述方案 | `_研读/NN.md` | 流程、机制、数据去向、追问答案都有源码依据；讲述方案已完成 |
| U-成文 | 按讲述方案先写骨架，再展开成文 | `NN-标题.md` | G2、G3、G5 自查通过 |
| U-审读 | 独立读者按骨架复述、通读复述、逐题作答三阶段作答，核对者核真，校对表达 | 修订后的正文、`_审读记录/NN.md` | G1–G6 通过；**必停点二：用户确认该篇** |
| U-收束 | 补全 00，写 99，生成修改提示词文档，做跨篇检查 | 00、99、修改提示词文档 | 跨篇口径一致、入口都有去向、问题台账没有未处理项 |

每篇的研读、成文、审读是三个独立的新会话步骤，按确认的阅读顺序推进。两个确认点已有明确授权时按授权范围执行并记录依据，不能把生成文件或脚本成功当成用户确认。

具体输入、读取边界、退回研读条件及源码基准变化的处理，见 [生产流程与交接物](references/生产流程与交接物.md)。核心机制在主讲篇讲完整，其他使用篇仍讲清本流程的问题、工作顺序和失败行为，再指向主讲篇。不要用一行参数代替讲解。

## 脚本命令

脚本为 `<SKILL>/scripts/project2doc.py`，仅用标准库；支持 `--json`。路径加引号。

| 命令 | 作用与写入范围 |
|---|---|
| `deps` | 只读检查依赖 |
| `survey --repo R [--map M]` | 只读检查源码基准、map状态、技术栈和规模 |
| `scaffold --project P --repo-name N` | 创建笔记仓、骨架、规则/模板/工具副本，写入规则版本；不覆盖已有文件 |
| `progress --notes N --version-dir V` | 只读对账编排步骤、笔记提交与产物；不管理进度 |
| `consistency --notes N [--final]` | 只读检查交接物结构：篇目、主讲篇、讲述方案、审读三阶段、术语衔接、台账和规则版本；final 用于全部篇目完成后的收束 |
| `lint --file F [--words W ...]` | 只读列出 G3、G5、G6 的候选：行号、测试名、过程说明、标签与版本列举、指路代讲、补充块密度、数量声明、图例不符、名称密度、否定限定、长并列句、用词与转场 |
| `skeleton --file F [--out O]` | 只读输出骨架视图：篇首块、全貌一节全文、其余一至三级标题及其下第一段；供审读阶段 A 和成文自查使用 |
| `render-revise --notes N --repo-name R` | 新建四区修改提示词文档；存在则拒绝覆盖 |

脚本只检查结构和候选，不能证明读者理解、事实正确或表达合格。逐题作答和源码核对必须实际执行。

## 最终汇报

生成时报告：工程位置、源码基准、map 状态、规则版本、已确认的规划与实际完成的篇目、各篇质量门结果与未决项、编排目录与下一动作。阶段性产出不写成全仓笔记已经完成。

修改时报告：改动的篇与位置、缺口层级、补足了什么、复验结果、理解稿是否更新、笔记仓提交；走编排时说明新需求包与步骤。正文默认不设面试章节，用户可在修改提示词文档的项目口径区启用。
