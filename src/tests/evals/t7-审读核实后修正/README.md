# 审读回归：先核实，再修正讲解

这是通用订单场景的合成夹具，用于验证 1.5 的审读权限和事实回写。它只测一个审读片段，不宣称完整笔记已经通过六道质量门。

旧用例要求审读者原样保留错误数字、顺序和结论，并逐条填旧检查编号。1.5 允许审读者回源码核实后补讲，因此改写用例，保留“不能为了顺口改变事实”的长期约束，删除机械编号落盘的目标。

## 输入与执行

1. 给一位没有本次上下文的读者 `01-订单创建.md` 和下方三个追问，先保存只凭正文得出的答案。
2. 给审读者当前 Skill、读者答案、`_研读-01.md` 和 `source/order.py`。源码夹具只读；把需要修正的理解先写回理解稿，再修改正文。不要提交。
3. 重新让独立读者回答三个追问，并记录原答案、修改位置、复验答案和源码核对结果。

追问：

- 库存检查和预扣款谁先发生？库存不足时会不会调用支付端？
- 支付端一直失败时，最多调用几次？“重试次数”和“总调用次数”有什么区别？
- 短信发送失败后，调用者收到什么？系统是否保证最终通知到用户？

## 合格答案要点

| 追问 | 回源码核对后的答案 | 应有的处理 |
|---|---|---|
| 顺序 | 先调用库存检查；不足时返回 409，尚未调用支付端 | 改正文前核实 `create_order` 的两个分支，在理解稿记下核对；不能只凭流程图或常识改顺序 |
| 次数 | 最多调用 4 次，包含首次和 3 次重试；前三次失败后各等 200 毫秒，第四次失败后释放库存并返回 502 | 把“失败最多重试 5 次”改为精确的调用场景，区分次数口径 |
| 通知 | 短信异常只记录日志；订单创建仍返回 201，没有队列、重试或最终送达保证 | 去掉“一定通知到”的承诺，解释创建结果与通知结果分开处理的代价 |

不合格：没看源码就改数字；把“有重试”写成“一定成功”；保留错误正文却声称 G4 通过；给只读正文的独立读者提供理解稿答案。

`source/order.py` 只定义调用顺序与返回行为，依赖通过参数注入。它没有实现真实数据库事务、库存锁或支付幂等，不能据此声称这些机制已经得到保证。

本用例改写时已核对夹具和答案口径；独立 Agent 行为评测须按上述步骤另行执行，不沿用旧版评测结果。
