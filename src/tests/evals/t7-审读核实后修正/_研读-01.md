# 01 · 订单创建理解稿

源码基准：本用例的 `source/order.py`；这是合成夹具，不对应真实项目。

## 一、流程走查

请求把商品编号、数量和联系人交给 `create_order`。处理器先调用库存检查函数；调用超时返回 503，库存不足返回 409。这两个分支都在支付循环之前，所以失败时没有发生预扣款。库存检查通过后才调用支付端。支付调用最多执行四次，前三次失败后分别等待 200 毫秒；第四次失败时调用库存释放函数并返回 502。来源：`source/order.py#create_order` 的库存分支和 `range(4)` 循环。

支付调用成功后，处理器保存一条 `pending` 订单，再发送短信。短信抛出异常只写日志，处理器仍把 201 和订单编号交给调用者。这些调用都在当前调用中执行，没有另外启动线程或消息任务。来源：`source/order.py#create_order` 的保存、通知和返回部分。

## 二、机制卡：有上限的重试（核心）

**问题。** 外部支付调用短暂失败时，如果一次失败就结束，原本可以恢复的请求也会直接失败。

**原理。** 调用者在失败后等待，再重复调用；限制次数避免无止境占用执行资源。这里讨论的是调用次数和等待，不能据此认定支付操作具备幂等性。

**实现。** `range(4)` 产生四次尝试机会，编号从 0 到 3。成功就跳出循环；失败且尝试编号小于 3 时等待 0.2 秒，编号为 3 时释放库存并返回 502。来源：`source/order.py#create_order`。

**判断。** 是否已经到最后一次尝试决定“等一下再试”还是“释放库存并结束”。如果前三次都失败而第四次成功，就发生四次支付调用和三次等待。

**失败与兜底。** 四次调用全失败时，函数调用库存释放操作并返回 502。夹具没有实现释放操作内部的失败处理，因此不能进一步声称库存释放必然成功。

**取舍。** 与只调用一次相比，重试可以容忍短暂异常，但延长响应时间，也要求调用方处理重复调用的副作用。这是对比型分析，没有断言作者最初的动机。

**局限。** 次数有限并不等于操作最终成功；夹具也没有给出支付幂等协议。不能把重试描述成资金一致性的保证。

## 三、关键数据去向

商品编号和数量由请求带入，先交给库存检查，再交给支付调用和订单保存。联系人由请求带入，交给短信发送端。订单编号由保存函数返回，经通知调用后进入 201 响应。源码没有定义客户端何时丢弃编号，不能补写失效时间。来源：`source/order.py#create_order` 的参数和调用参数。
