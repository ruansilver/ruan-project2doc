# 修改回归：事实、结构与图三类反馈

本用例沿用 `../t7-审读核实后修正/` 的合成订单场景和只读源码 `../t7-审读核实后修正/source/order.py`，在它的事实类反馈之外，增加一条结构类反馈和一条图的反馈，用来验证 1.6 的修改协议：先判断缺口在哪一层，结构问题按结构修，图的问题通过改图解决，修改落在实处且范围不扩大。

## 材料

| 文件 | 用途 |
|---|---|
| `01-订单创建.md` | 待修改的正文：事实有三处与源码不符，没有全貌，图把之后的查询请求画成下单的下一步 |
| `_研读-01.md` | 理解稿：事实部分已经与源码一致；讲述方案很薄，没有全貌，也没有标出另一次执行 |
| `修改已有笔记-demo.md` | 修改提示词文档，用户追加区有三条待处理的要求 |
| `判定要点.md` | 核对者使用，不交给独立读者，也不交给执行修改的 Agent |

## 执行步骤

1. 给执行修改的 Agent 当前 Skill、`修改已有笔记-demo.md`、`01-订单创建.md`、`_研读-01.md` 和只读源码。让它按修改协议处理三条待处理要求；修改写在测试工程的副本上，不改本夹具。
2. 核对者读 `判定要点.md`，逐条判定：缺口层级判断、修改路径、是否落在实处、复验是否执行、范围是否扩大。
3. 结构类修改后冻结新版本，由一位新的独立读者只看 `skeleton` 输出的骨架视图重跑阶段 A。
4. 另做一次负向核对：把“只在图后补一段读图说明、不改图”的做法交给核对者，应被判为未完成。

独立读者只接触骨架视图和正文，不得读判定要点、理解稿或源码。本夹具写成时只核对了文本与源码的事实口径；Agent 行为评测须按上述步骤另行执行，记录归入当次的验收材料。
