# 用户资料读取怎样接上两级缓存

EMG指定基准中，鉴权服务调用另一个受代理管理的用户资料服务。其 `UserProfileCacheService.load` 使用 `@Cacheable`，没有声明 `sync=true`，返回普通的用户资料值。实际读序是代理先调用普通 `Cache.get(key)`；两级都没有结果时，代理再执行load方法里的用户表查询，然后put。来源：`backend-java/src/main/java/com/wristband/platform/users/UserProfileCacheService.java#load`；Spring Framework 6.1.6 `Cacheable`与`CacheAspectSupport#execute/evaluate`。

普通get在 `CompositeCache` 中先读L1，再读L2；L2命中会回填L1。这个方法没有业务loader，也没有按键加载锁。另一个 `get(key, Callable)` 重载才在miss后取得同一键的本机锁，进锁后再读，仍miss才加载并put。组件测试直接调用这个重载，不能据此推断用户资料注解入口也走了它。两个同时miss的普通业务请求可能分别查库。来源：同仓 `common/cache/CompositeCache.java#get(Object)/get(Object,Callable)/read`；`src/test/java/.../common/cache/CompositeCacheTest.java`的直接loader调用。

为什么仍需要两级：受保护请求反复装载用户，L1命中省去网络访问，L2让实例复用已有查询结果；数据库仍是回源位置。直接相信JWT里签发时的角色，会错过之后资料变化；装载缓存资料也不是绝对实时保证。来源：`security/JwtAuthenticationFilter#doFilterInternal`、`security/CustomUserDetailsService#loadUserById`及上述实际缓存路径；成本比较为效果型分析。

缓存put按“删旧L2 → 写本机L1 → 写L2 → 广播”执行。evict按“本机删 → L2删 → 广播”执行。接收者收到put/evict通知只删自己的L1，不直接拿到新值，也不再次广播。来源：`CompositeCache#put/evict`、`CacheInvalidationListener#onMessage`。

L2读错可返回miss，普通代理路径随后回数据库；L2删错则是旧共享条目可能仍在，后续广播照常尝试。如果删除失败而广播送达，另一实例可能先清掉L1，再在下次读取时从尚存的旧L2回填。不能把所有Redis故障概括成“只会查库”。这个场景是由顺序和catch范围推出的条件性反例，不是声称已经运行故障演练。来源：`RedisL2Cache#read/delete`、`CompositeCache#evict/read`、`CacheInvalidationPublisher`。

本片段解释真实调用和边界，不给出“所有并发只查一次”“所有实例立即一致”之类超出源码的保证。
