# ruan-project2doc 1.5.0

把一个项目讲懂给初学者。读者会写一般业务代码、能读懂源码、知道常见技术名词，但还不熟悉本项目，也未必理解这些技术怎样配合。必要原理讲到足以理解本项目实现与备选方案差别为止。

读完一篇，读者能复述主要流程和关键数据去向，能解释核心机制的问题、原理、实现、失败处理与取舍，并回答两三层追问。

**准确是底线，理解是目标，可读是手段，覆盖服从理解。** 正文讲解系统，源码位置与核对过程保留在理解稿和 99。主标杆提供讲解方法；写进笔记的事实一律回目标项目的当前源码核实。

下文 `<SKILL>` 是本 Skill 所在目录，`<工程>` 是笔记工程，`<笔记>` 是 `<工程>/笔记/`。

## 硬边界

- 源码仓和 project-map 只读，不改代码、状态或未决，不在其中运行写入命令；所有产出写入独立的笔记工程。
- 只提交笔记仓，不推送；资料仓的操作由 ruan-dev-skills 负责。长任务的步骤、进度和恢复全部交给它，不另建同类机制。
- 面向任意技术栈。入口、终点、状态和机制由目标源码决定，不能假设一定存在样例中的组件。references 的正反例只说明讲解方式。
- 不为表达顺畅改变事实、条件或结论强度。新事实先核实并更新理解稿，再进入正文。
- 不在运行时修改本 Skill。项目特有要求写进该项目修改提示词文档。
- 对 frontmatter 列出的不适用场景说明原因后停止，不降级生成一套不相符的笔记。

## 判断调用类型

| 类型 | 识别与动作 |
|---|---|
| 首次生成 | 尚无已确认规划；按下面流程做勘察、规划、确认和交接。已有材料则先核对后继续，不覆盖。 |
| 继续生成 | 已有 dev-skills 接力提示词；读取它并按当前步骤恢复，只推进该步骤。 |
| 执行编排步骤 | 以步骤文件和归档需求包为准，读本单元指定的规则与交接物。 |
| 修改已有笔记 | 按 [修改协议](references/修改协议.md) 处理修改文档中待处理的要求；先识别其背后的理解缺口。 |

## 开工检查与确认

运行辅助脚本需要 Python 3.8+（仅标准库）和 Git；长任务编排需要 ruan-dev-skills 2.0，可选借鉴 project-map。

先运行 `python "<SKILL>/scripts/project2doc.py" deps`，检查 Git、ruan-dev-skills 和可用的表达检查能力。缺少 Git 或 ruan-dev-skills 时停止，说明缺少什么；没有 Python 时如实记录脚本未执行，按 [project-map借鉴](references/project-map借鉴.md) 人工完成相应检查。

核对仓库路径和分析基准（默认 HEAD）、输出目录（默认仓库同级的 `<仓库名>-笔记工程/`）、用户重点。用户已经提供的直接沿用，只补问影响工作的缺项。分析范围固定为全仓库；没有 project-map 时只提示一次，可按源码入口与终点发现继续。

## 流程总表

| 单元 | 动作与产物 | 继续条件 |
|---|---|---|
| U-勘察 | scaffold 建工程，survey 核对基准、规模与 map，填写 `_勘察结果.md` | 源码基准、map 状态和范围明确 |
| U-规划 | 识别链路与机制，定级和主讲篇；写 `_规划方案.md`、00 骨架、术语与衔接，包含学习目标、阅读顺序和追问 | **必停点一：用户确认规划方案** |
| 交接编排 | 填需求包，把已确认规划复制为 `01-规划方案.md`，按需求包规格调用 ruan-dev-skills | 资料仓“可接力”；正常首次调用在此结束 |
| U-研读 | 沿本篇源码理解流程与机制，写 `_工作区/_研读/NN.md` | 机制七问或支撑三问、流程与数据去向、逐题答案草稿都有源码依据 |
| U-成文 | 依据理解稿写链路篇或机制专题篇；可定点回读，新增事实先回写理解稿 | G2、G3、G5 自查通过 |
| U-审读 | 新会话先只凭正文作答，再抽查源码，最后校对表达，写 `_工作区/_审读记录/NN.md` | G1–G6 通过；**必停点二：用户确认该篇** |
| U-收束 | 回填00系统总览与阅读路线，整理99，生成修改提示词文档 | 跨篇口径一致、入口有去向、问题台账无open |

每篇的研读、成文、审读是三个独立的新会话步骤，按确认的阅读顺序推进。两个确认点已有明确授权时按授权范围执行并记录依据，不能把生成文件或脚本成功当成用户确认。

具体输入、读取边界、退回研读条件及源码基准变化的处理，见 [生产流程与交接物](references/生产流程与交接物.md)。核心机制在主讲篇讲完整，其他使用篇仍讲清本流程的问题、工作顺序和失败行为，再指向主讲篇。不要用一行参数代替讲解。

## 脚本命令

脚本为 `<SKILL>/scripts/project2doc.py`，仅用标准库；支持 `--json`。路径加引号。

| 命令 | 作用与写入范围 |
|---|---|
| `deps` | 只读检查依赖 |
| `survey --repo R [--map M]` | 只读检查源码基准、map状态、技术栈和规模 |
| `scaffold --project P --repo-name N` | 创建笔记仓、骨架、规则/模板/工具副本；不覆盖已有文件 |
| `progress --notes N --version-dir V` | 只读对账编排步骤、笔记提交与产物；不管理进度 |
| `consistency --notes N [--final]` | 只读检查规划篇目、主讲篇、新交接物、逐题审读记录、术语衔接和台账；final用于全部篇目完成后的收束 |
| `lint --file F [--words W ...]` | 只读列出G5/G6候选，包括行号、测试名、过程说明、标签数量及指路附近的讲解信号 |
| `render-revise --notes N --repo-name R` | 新建四区修改提示词文档；存在则拒绝覆盖 |

脚本只检查结构和候选，不能证明读者理解、事实正确或表达合格。逐题作答和源码核对必须实际执行。

## 最终汇报

生成时报告工程位置、源码基准、map状态、已确认规划与实际完成篇目、各篇质量门和未决项、编排目录与下一动作。阶段性产出不能写成全仓笔记已经完成。

修改时报告改动篇与位置、补足了什么理解、追问复验及源码核对、理解稿更新、笔记仓提交；走编排时说明新需求包与步骤。正文默认不设面试章节，用户可在修改提示词文档的项目口径区启用。
