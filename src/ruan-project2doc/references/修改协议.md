# 修改协议

**何时读本文件**：用户说“按修改提示词改笔记”“改一下第 N 篇”“我在修改提示词里加了要求”时。

修改提示词文档是 `笔记/修改已有笔记-<仓库名>.md`，由 U-收束用 `project2doc.py render-revise` 生成，分四区：使用方法、一固定规范区（勿改）、二项目口径区（可改）、三用户追加区、四变更记录。

## 1. 使用协议：AI 如何选择并修改一篇或多篇

1. **读要求**：只处理「三、用户追加区」中状态为“待处理”的行。
2. **定目标篇**：
   - 填了目标篇：只改这些篇。
   - 没填：按要求涉及的术语、机制、流程名，查 `_工作区/_术语表.md` 的首次出现篇和 `_工作区/_衔接约定.md` 的机制归属，列出受影响篇目和理由，**等用户确认后再改**。理由：防止 AI 自行扩大范围。
3. **定类型**：
   - 只涉及表达或结构：走 `校对协议.md` 的流程，输入是该篇加这条要求；
   - 涉及事实：先走 U-取证核对源码，更新 `_事实/NN.md`，再改正文。
4. **改**：直接改在原位置，正文不留痕迹（C14、M01）。
5. **改完自检**：执行 `问题清单.md` 附录 D（M01–M08），加上受影响段落相关的附录 A 条目；改动影响了篇首篇尾接口或术语时，同步检查相邻篇。
6. **留痕**：在「四、变更记录」追加一行，把对应要求的状态改为“已处理”。

## 2. 走哪条路

| 修改范围 | 怎么做 |
|---|---|
| **只改一篇、只涉及表达** | 可以在当前会话直接改：按 `校对协议.md` 的权限边界执行，改完在笔记仓提交，写变更记录 |
| 涉及事实，或涉及多篇 | 必须走 ruan-dev-skills 的“需求调整”模式（下一节） |

## 3. 走 ruan-dev-skills 调整模式

1. 第 1 节的第 2 步“列受影响篇目并等用户确认”，由本 Skill 在调整前完成。
2. 准备一份新的需求材料目录（放在资料仓之外，例如 `<工程>/需求包-修改-<日期>/`，不要含空目录）：
   - 修改提示词文档的副本；
   - `00-修改说明.md`：本次只覆盖「用户追加区」里哪几行（日期 + 要求摘要）、已确认的目标篇清单、每行的类型（表达 / 事实 / 结构），以及“涉及事实的先规划取证步骤；正文修改遵守校对权限边界；改完写变更记录”。
3. 在 `<工程>/笔记/` 作为工作目录的前提下，加载 ruan-dev-skills，以调整模式执行：需求材料 = 上面的目录，版本目录 = 现有的 `<工程>/docs/AI dev docs/<版本号>/`。它会把材料归档为新的 Pxxx，并在 `plans/索引.md` 标明覆盖范围。
4. dev-skills 为每篇规划修改步骤（涉及事实的先规划取证步骤），之后按接力提示词逐步执行。

理由：所有修改都有笔记仓提交 hash 可追溯；小改动多一次规划的代价可以接受。

## 4. 用户要求与固定规范冲突时

例如用户要求“每个类名都保留”。以用户要求为准，并在变更记录里注明偏离了哪条规范（写规范 ID，如 C8、R06）。理由：修改提示词文档允许用户随时增删要求，是用户意图的最高来源。

## 5. 项目级问题条目

用户追加的要求，如果**同一类出现了第二次**，就在项目口径区的“项目特有问题”表里登记一个项目级 ID（`P-R01`、`P-F01`……），格式与附录 A 相同：毛病、检验、反例与正例、出处。项目级条目只在本项目内生效；是否并入本 Skill 由用户决定，AI 不在运行时修改 Skill 本身。
