# 修改协议

用户要求按修改提示词改笔记，或要继续、重做一个已有的笔记工程时，读本文件。修改入口是 `笔记/修改已有笔记-<仓库名>.md`，由 `render-revise` 生成四区：固定规范区（本版的讲解、组织与措辞要点）、项目口径区、用户追加区、变更记录。

## 1. 确定本次要处理什么

只处理用户追加区里状态为“待处理”的行。填了目标篇就只改这些篇；没有填时，根据术语表、规划中的主讲篇和衔接约定列出受影响的篇及理由，取得用户确认后再改。已有明确的范围授权直接沿用。

## 2. 先判断缺口在哪一层

收到阅读反馈时，先把它转成一个可以回答的问题，并判断缺口在哪一层。不预设“看不懂”只是措辞问题。

| 缺口层级 | 典型反馈 | 处理 |
|---|---|---|
| 整体模型与组织 | “不知道整体怎么走”“章节混乱”“标题看不出顺序” | 更新讲述方案，重组全貌和章节（走第 3 节的结构修改路径） |
| 章节职责或子流程 | “这一节读不下去”“看不懂这个过程” | 更新讲述方案的相关条目，重组该节；给子流程补骨架 |
| 机制讲解 | “讲不清它怎么工作” | 判断缺的是背景、原理、实现、判断、失败还是取舍；必要时补研读，再在原位置补讲 |
| 术语或句子 | “这个词不懂”“这句读不通” | 就地补解释或改写 |
| 事实 | “这里和代码不一致” | 回源码核实，先修理解稿，再改正文 |

用户指出的那一处要改；同一个缺口是否在本篇其他位置也存在，一并检查。补充要服务当前问题，不借机扩展成无关主题。

## 3. 修改路径与复验

| 修改范围 | 执行方式 |
|---|---|
| 一篇之内，纯表达，或不改变含义的结构调整 | 当前会话处理，复验后写变更记录并提交笔记仓 |
| 涉及事实、讲解依据，或涉及多篇 | 交 ruan-dev-skills 调整模式：在资料仓之外新建需求材料目录（修改提示词副本、修改说明），由它归档并安排步骤；涉及事实的先安排研读 |

修改规则：

- 直接在原位置修正或补讲；原处确实容不下，才在附近另起层次。
- 错误的内容彻底删掉，不把它改写成新的限制或提醒继续保留。
- 保留用户为了理解而写的解释和例子；只要没有错误和明显重复，优先在原有表达上优化。
- 修改既做加法也做减法。正文不留修改过程的痕迹。
- 表达修改不改变数字、条件、时序、失败结果和结论强度；补充机制细节属于事实工作，先回源码核实并更新理解稿，再改正文。

复验：

- 结构类修改完成后，按《生产流程与交接物》的复验规则重跑阶段 A（必要时连同阶段 B 的复述）：冻结新版本，换一位新的独立读者。
- 其他修改：复验受影响的追问（G1），核对 G2、G3；涉及事实时执行 G4；再检查 G5、G6。
- 结果记入对应的审读记录，不只写“已修改”。

交给编排的材料：在资料仓之外新建需求材料目录，例如 `<工程>/需求包-修改-<日期>/`，包含修改提示词副本及 `00-修改说明.md`。修改说明写明本次待处理行、已确认篇目、缺口层级、修改类型、源码基准，以及“先更新理解稿，再改正文，最后复验”的要求。以 `<工程>/笔记/` 为工作目录，加载当前安装的 ruan-dev-skills，用调整模式交入该目录和现有版本目录；旧归档不改写。每篇审读后的下一动作仍为等待用户确认。

## 4. 修改必须落在实处

- **每一处“已处理”，都要能指到实际改动的文字。** 只增加一段解释性说明（例如在图后补一段通用的读图说明）、只声明“已有背景，未再改动”、只改标题不改内容，都不算完成。
- 结构问题按结构修：图的关系画错了就改图；章节职责混乱就重组章节；标题不能概括内容就调整标题体系。补一段文字说明“其实不是这个顺序”，不能代替把它改对。
- 批量处理多篇时逐篇记录：改了哪些节、结构是否变化、复验了什么。没有改动的篇如实写“未改动”和理由，由用户决定是否接受。
- 变更记录写明：日期、对应的用户要求、目标篇与位置、缺口层级、改动类型、复验结果、理解稿是否更新、偏离的规范（如有）、笔记仓提交。完成后把该行状态改为“已处理”。只提交笔记仓，不推送；资料仓交给 ruan-dev-skills 管理。

## 5. 项目口径、用户选择与回流

- 项目口径区记录本项目的篇目与阅读路线、源码位置与基准、术语索引、未确认项索引，以及项目特有的约定（问题、适用范围、正反例、生效日期）。
- 用户可以在项目口径区打开默认关闭的内容：每篇的“面试怎么讲与高频追问”章节（内容取自已经验证的追问，不编造经历）、版本演进叙述、更深的原理展开。
- 用户要求优先于固定规范；偏离之处在变更记录里用普通文字说明。
- 反复出现的项目特有问题只在本项目生效；是否并入 Skill 由用户决定。不另建检查编号体系，不在运行时修改 Skill。

## 6. 既有工程与规则版本

- **一个笔记工程从建立起，一直使用它归档的那一版规则。** 本机安装新版本不改变已经归档的任务。
- 新建工程时，`00-任务说明.md` 和 `_勘察结果.md` 写入“规则版本”（如 `ruan-project2doc 1.6.0`）。审读记录也记下实际使用的规则版本。
- 继续一个已有工程时，先读它归档的规则版本，与当前安装的版本对照。不同就在开工时用一句话告诉用户：“这个工程按 X 版规则继续；要使用 Y 版规则，需要另建工程。”不混用两版规则，不把旧规则的产出称为新版的结果。没有版本字段的工程报告为“未标注（早于 1.6）”，不自行推定是哪一版。
- 要用新版规则重做已有的笔记：另建新的笔记工程。旧工程的笔记和工作区材料只作线索，用法同 project-map（见《project-map借鉴》）——可以借它定位和导航，写进正文的事实回当前源码核实。不移动、改名或覆盖旧工程的文件。
