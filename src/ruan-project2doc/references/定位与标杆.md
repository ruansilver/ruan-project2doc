# 定位与标杆

首次规划时读本文件；研读或成文拿不准详略时，用这里的成功标准判断。讲解手法只借讲法；写进笔记的事实一律回目标项目的当前源码核实。

## 交付什么

读一个软件项目的全仓库源码，写成一套中文系统学习笔记：00 系统总览与阅读路线、链路篇与机制专题篇、99 复核说明，并配一份修改提示词文档。00 让第一次接触项目的人建立系统地图；各篇按阅读顺序讲清一条业务流程或一个核心机制；99 承接分析范围、入口去向、未确认项等核对材料。

读者会写一般业务代码，能读懂源码，也知道常见技术名词大概是什么，但还不熟悉本项目，也未必理解这些技术在真实系统里怎样配合。所以笔记不解释“什么是数据库”，但要解释“这里为什么需要两级缓存”“这次登录为什么要跳到另一个系统再回来”。读者不认识项目里的类名、表名、错误码，也不应该被要求先认识它们才能读懂。

## 读完一篇，读者能做到什么

1. **讲整体**：不看笔记，能说出这件事解决什么问题、有哪些参与方和核心对象、整个过程分哪几个阶段、每个阶段留下什么。
2. **讲流程**：能复述主要步骤，说清关键数据从哪里来、在哪里被校验或改变、最后交给谁；能分清哪些动作属于同一次执行，哪些是另一次。
3. **讲机制**：对核心机制，能讲出它解决什么问题、靠什么原理、本项目怎样实现、失败时怎样处理、为什么选这种做法。
4. **经得起追问**：面对“为什么要这个判断”“这一步失败会怎样”“为什么不用另一种做法”，能凭笔记内容再回答两三层。

这四条是全部设计的出发点，也是质量门 G1 直接检验的对象。

## 价值排序

**准确是底线，理解是目标，可读是手段，覆盖服从理解。**

- **准确**：写进正文的每个项目事实都经当前源码核实；没有依据的设计意图不写成事实。证明材料留在理解稿和 99，不占正文。
- **理解**：用上面四条衡量。先让读者建立整体，再沿流程展开细节；冲突时宁可少写一个次要分支，也要把主线和核心机制讲透。
- **可读**：组织和措辞为理解服务。通俗化是把技术信息讲明白，不是删掉技术信息。
- **覆盖**：全仓库每个入口都有去向（成篇、简述或不展开的原因）；正文不追求穷举分支和配置。

## 让读者形成理解的写法

| 手法 | 起什么作用 | 来源中的例子（节选或摘改） |
|---|---|---|
| 从问题起步 | 读者先知道这个机制要对付什么，后面每个设计都有着落 | 认证标杆先问：登录以后怎样持续确认身份，又怎样收回令牌或刷新权限？ |
| 原理紧挨实现 | 读者知道这种结构为什么适合这个问题 | 限流标杆先解释有序集合按时间删旧记录，再写剩余数量如何参与限流判断 |
| 朴素方案 → 缺陷 → 改进 | 读者理解的是“为什么必须这样”，不只是“代码是这样” | 缓存标杆比较全局一把锁和按键分别加锁：前者让互不相关的请求排队 |
| 写出结构和顺序 | 读者能在脑中执行一次 | 缓存标杆分别走查本地读、共享缓存读、回源、写回和广播 |
| 用小场景和具体数字检验规则 | 把抽象规则变成可检验的结论 | 认证标杆用连续错误密码说明“达到阈值的请求”和“下一次被锁拦住” |
| 故障与代价一起讲 | 读者知道依赖出问题时系统的真实表现 | 认证标杆区分哪些依赖操作故障后继续，哪些会中断 |
| 收成全景并说明局限 | 把分散的机制连成整体，不把方案讲成完美 | 认证标杆把刷新不轮换与凭据泄漏后的可重复使用联系起来 |
| 提前拆掉常见误解 | 防止读者凭直觉建立错误模型 | 缓存示范先说明：组件提供按键加锁的加载方法，不等于用户资料读取实际走这条路径 |

标杆里的高密度方法名、戏剧化标题和反复版本叙述不照搬；表达来源 B 只借按执行顺序组织、补充信息下沉的结构，其精简要求只删重复、空话和无助理解的细节。

## 局部答得出不等于整体读得懂

追问测试只测“答案在不在正文里”，测不到读者是否建立了整体模型。实测中，由 AI 承担的独立读者在再密的文本里也能检索出答案：全部机制题被评为“答得出”，但同一批文章的共性问题依然存在——全貌很薄、把四次独立请求画成一条链、进入流程第一步后立刻展开几十行细节。检索出答案与读懂整体是两回事。

所以 G1 用四项证据：阶段 A 骨架复述、阶段 B 通读复述、初读障碍清单、阶段 C 逐题作答；承担独立读者的必须是只拿到规定输入的独立会话或 agent，不能由做过研读或成文的会话兼任。详见《生产流程与交接物》的审读部分与《质量门》G1。

## 反例为何不合格

缓存示范的教训常被误用：组件提供按键加锁的加载方法，不等于用户资料读取实际调用它。**借讲解方法，所有事实回目标项目源码确认。**

按 1.4 规则生成的 EMG 登录会话篇，第四节给出“本机一级配置为 60 秒、Redis 二级为 30 分钟、空值为 30 秒”，随后指向别篇。数字没有连到读写动作，读者无法解释一次未命中如何处理，也无法判断依赖故障的代价。缓存示范则先解释为什么不能只信令牌中的旧角色，再走查读、写、失效和故障路径；这些解释应留在用到缓存的那一步。

同一篇把登录 IP 限流压成“60 次 / 60 秒”，再指向第 15 篇。限流标杆的写法会继续交代如何表示一次请求、如何删旧、计数和判断，以及拒绝结果由谁转成响应——这才足以回答“第 61 次会怎样”。具体数字与顺序仍须取自当前项目。

按 1.5 规则实测的两篇，已没有取证格式，机制有因果、有走查，但全貌仍然很薄：一张图把四次独立请求画成一条链；进入流程第一步后立刻展开几十行限流细节；全文十余处“不能据此断言……”式的否定句。这些正是《讲解规范》的组织规则与《表达规范》要避免的写法。

旧版工作区有很多逐条核对记录，正文仍缺少机制解释。完成检查记录并不能替代读者作答；最终用《质量门》的 G1 检验整体理解，再检查准确和表达。
