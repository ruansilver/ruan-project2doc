# 生产流程与交接物

每个单元只读本节要求的输入和所需规则。长任务的步骤、进度、恢复由 ruan-dev-skills 管理，本 Skill 负责理解和写作，不另建接力状态。

## 1. 单元与产物

| 单元 | 做什么 | 主要产物 | 满足这一条才往下走 |
|---|---|---|---|
| U-勘察 | 建笔记工程，核对源码基准、规模与 project-map 状态 | `_勘察结果.md` | 源码基准、map 状态和范围已明确 |
| U-规划 | 发现链路与机制，定级、定篇目与组织方式预判，写学习目标、追问清单和规划期的 00 | `_规划方案.md`、00、术语表、衔接约定 | **用户确认规划** |
| 交接编排 | 填需求包，交 ruan-dev-skills 初始化 | 资料仓达到“可接力” | 首次调用到此结束 |
| U-研读 | 沿本篇源码弄懂流程与机制，写理解稿，设计讲述方案 | `_研读/NN.md` | 流程、机制、数据去向、追问答案都有源码依据；讲述方案已完成 |
| U-成文 | 按讲述方案先写骨架，再展开成文 | `NN-标题.md` | G2、G3、G5 自查通过 |
| U-审读 | 独立读者复述与作答，核对者核真，校对表达 | 修订后的正文、`_审读记录/NN.md` | G1–G6 通过；**用户确认该篇** |
| U-收束 | 补全 00，写 99，生成修改提示词文档，做跨篇检查 | 00、99、修改提示词文档 | 跨篇口径一致、入口都有去向、问题台账没有未处理项 |

每篇的研读、成文、审读是三个步骤，按确认的阅读顺序推进，各在新的会话中执行。任何步骤都不把“文件存在”当作质量门通过，不把脚本退出码当作用户确认。

单元读入的原始材料加产出，默认不超过可用上下文的一半（可后改）。装不下时调整篇目或拆出机制专题，交编排处理；不以少读关键源码换取完成。

## 2. U-勘察与规划

U-勘察只读目录树、构建信息、基准提交和 map 状态，不在这里装入全部业务源码。`survey` 的结果填入 `_勘察结果.md`，其中记录本工程使用的规则版本；没有 map 时按《project-map借鉴》走正向入口、反向终点发现。

U-规划按《篇目规划》识别链路与机制，定级、安排主讲篇和使用篇，写学习目标与追问，产出规划期的 00。规划内容可以包含待研读核实的候选，但不能写成已经确认的机制保证。确认后按《需求包规格》交接，正常首次调用不继续进入研读。

## 3. U-研读：先自己弄懂，再设计怎么讲

从 `templates/_研读.md` 复制为 `_工作区/_研读/NN.md`。按本篇范围沿真实执行关系读源码，研究到足以解释原理、步骤和取舍。理解稿包含：

1. **流程走查**：按执行顺序，每一步做什么、输入从哪来、输出到哪去、关键判断、失败去向、是否换了一次执行；附源码位置。
2. **机制卡**：每个核心机制按七问、每个支撑机制按①③⑤写成可以连读的段落，含必要的原理、备选分析和走查例子；区分组件能力与业务实际走的路径。
3. **关键数据去向**：来源 → 传递 → 使用或校验 → 更新与失效。
4. **追问与答案草稿**：逐题回答规划中的问题，含整体复述题与子流程复述题；研读中发现的必要追问回写规划。
5. **设计意图出处**：每个“为什么”属于效果型、对比型还是有出处的意图型，后者记录注释、提交或文档位置。
6. **核对材料**：测试覆盖与运行情况、配置差异、版本演进、未确认项、与 project-map 的差异。
7. **细节去向**：不进正文的细节及其去向。
8. **讲述方案**：按《讲解规范》的格式，把已核实的内容组织给读者——组织方式与理由、读者先要建立的模型、全流程走查、贯穿示例、哪些内容不是同一次执行，以及逐章的暂定标题、每节回答什么、进入本节时已知什么、本节产物与前后关系、深入与边界内容放在哪里。成文以它为骨架。

每个事实有源码位置，因果分析写明前提。理解稿的完成标准：**下一位作者只读这份理解稿，不必重读大段源码，就能写出合格的文章骨架并讲清机制。** 不写成孤立的一行一条，不限制与正文的篇幅比例。

## 4. U-成文：按讲述方案写

输入：本篇理解稿（含讲述方案）、规划条目、00 的相关背景、术语表、衔接约定、规则文件和对应篇型模板。不读其他篇的正文；需要讲别篇主讲的机制时，只读那一篇理解稿里的相关机制卡。

步骤：

1. **先写骨架**：按讲述方案写出各级标题、全貌一节，以及每个章节的节首段。检查两件事：只看目录能否还原过程或主题结构；把各节首段连起来读，能否讲成一条连续的线。骨架和讲述方案不一致时，先决定改哪一个，再让两者一致。
2. **再展开**：逐节补入主干、深入和边界内容，执行《讲解规范》与《表达规范》。不按理解稿的条目顺序搬运。
3. **回读与新事实**：可以定点回读理解稿标明的源码位置。成文中新发现的事实，先补进理解稿并注明来源，再写进正文。需要大范围重新探索，说明理解稿没有完成，退回研读。
4. **回填 00**：把本篇已核实、属于 00 的内容补进 00，只动与本篇有关的部分。
5. **成文自查**，结果写在理解稿末尾：
   - G2、G3、G5（见《质量门》）；
   - 运行 `skeleton` 查看自己的骨架视图，做目录检验和节首检验；
   - 对全篇最复杂的两三处做折叠检验（默认值，可后改）；
   - 运行 `lint`，逐条处理候选或写明保留理由。

自查不能代替审读中独立读者的结论。篇首问题由篇尾小结回答；篇尾代码地图只保留关键文件或类及职责。

## 5. U-审读：三轮

**读者与正文版本。** 独立读者必须是没有接触过本篇理解稿、源码和成文过程的会话或 agent。如果当前会话做过本篇的研读或成文，就另起一个独立 agent 承担读者，并且只给它规定的输入。审读开始前冻结正文版本（提交号或内容哈希），第一轮期间不修改正文。读者的设定是《定位与标杆》的目标读者：不用源码、理解稿、其他篇或一般常识补答案，正文没讲清的地方如实标出。

**第一轮：独立读者，只接触正文。** 分三个阶段，每个阶段先保存原答再进入下一阶段：

| 阶段 | 读者拿到什么 | 读者做什么 |
|---|---|---|
| A 骨架复述 | 只有骨架视图（`skeleton` 的输出）：篇首块、全貌一节全文、其余各级标题及每个标题下的第一段 | ① 讲出这件事的全貌：解决什么问题、参与方与核心对象、过程分哪几个阶段、每个阶段留下什么、谁接手；② 逐章说出这一章讲什么、处在整个过程的什么位置；③ 指出哪些内容不是同一次执行；④ 列出凭骨架判断不了的关系 |
| B 通读复述与初读障碍 | 正文全文 | ① 用自己的话完整复述；② 按阅读顺序写出初读障碍清单 |
| C 逐题作答 | 追问题面（没有答案） | 逐题回答，标“答得出／部分／答不出”，给出正文出处 |

初读障碍清单记录读者在第一次顺序阅读时卡住的地方，约 20 条以内，优先记最影响理解的：

- 没有解释就使用的术语、缩写、内部名称；
- 读完说不出“谁对什么做了什么、结果怎样”的句子；
- 断掉的关系：前面提到而后面没有交代，或突然出现的对象；
- 读到这里才发现缺的前置信息；
- 条件或数字过密、需要反复回读的句子。

读者可以回看正文，这不是记忆测试。

**第二轮：核对者，可以读理解稿和源码。**

1. 对照理解稿和源码判定阶段 A、B 的复述与阶段 C 的答案是否正确（G1）。答案正确但来自读者的外部知识、正文没有对应内容的，算文章缺口。
2. 回源码抽查关键断言（G4），复查 G2、G3、G5。
3. **修复顺序：先结构，再事实，最后表达。** 骨架或复述暴露的组织问题先处理：更新讲述方案，重组章节，再改正文。

**第三轮：表达校对（G6）。** 在结构稳定的正文上进行：先处理初读障碍清单里还没解决的条目，再按《表达规范》逐节校对，最后用可用的“说人话”类 Skill 自检；没有该能力时人工检查并如实记录。

**修改权限与复验：**

- 表达问题，以及不改变含义的结构调整，审读中直接改。
- 需要新事实的小缺口：先回源码核实并补入理解稿，再补讲。
- 大缺口（机制没弄懂、讲述方案需要重做）：登记 `_问题台账.md`，交 ruan-dev-skills 新增研读或成文步骤，不在审读里凭记忆硬补。
- 复验规则：章节增删、顺序调整、全貌重写、标题体系变化之后，冻结新版本，**换一位新的独立读者**重跑阶段 A；全文组织变化时同时重跑阶段 B 的复述。局部补讲或改写，复验受影响的追问和障碍条目。首次结果与复验结果分开保留，不把原判定直接改成通过。
- 没有可用的独立读者时，G1 不能记为通过：如实标为“待独立读者验证”并告知用户。用户本人的阅读结论可以作为读者证据。

三轮结果集中记在 `_审读记录/NN.md`。

## 6. U-收束

- 补全 00，使六项内容完整、与各篇一致。
- 用各篇理解稿的核对材料写 99：源码基准与检查范围、全仓库入口去向、未展开的内容及原因、未确认项、与 project-map 的差异、测试与运行核对概览、各篇审读结果。
- 跨篇检查：术语、数字；核心机制的主讲篇与使用篇是否矛盾；篇与篇之间的真实交接；跨篇共用示例的名称、数值、含义是否一致；同一事实在不同篇的说法是否一致。
- 运行 `consistency --final`，生成修改提示词文档。

收束只改 00、99 和各篇的篇首篇尾衔接。发现正文的事实或讲解问题，登记后返回对应步骤，不在收束里改。问题台账不得留有未处理项；需要用户决定的项写清影响与确认结果。阶段性产出如实说明已完成哪些篇，不写成全仓笔记已经完成。

## 7. 恢复、源码变化与执行方式

- 中断后按 ruan-dev-skills 的接力提示词和当前步骤恢复，再读该单元需要的交接物。`progress` 只辅助核对产物与提交。
- 源码基准变化时，列出受影响的篇目，交编排新增重新研读步骤；先更新理解稿、术语与衔接、必要的规划，再重新成文和审读。不把不同基准的事实混进一篇。
- 用户要求在同一会话连续推进多个步骤时，可以照办，但要如实记录这一偏离；质量门的判据不因此改变，独立读者仍由受限输入的独立 agent 承担。
- 每篇写作中得到的教训，属于本项目的写进修改提示词文档的项目口径区（见《修改协议》）；接力状态只记编排状态，不积累写作规则。

## 8. 交接物模板要点

| 交接物 | 要点 |
|---|---|
| `_勘察结果.md` | 源码路径与基准、技术栈与规模、map 状态与信任结论、依赖检查结果、规则版本 |
| `_规划方案.md` | 《篇目规划》的全部内容：链路候选、机制清单、篇目表（含组织方式预判与主要对象）、学习目标、追问清单（含必答标记）、入口去向、确认记录 |
| `_术语表.md` | 只收会混淆的叫法、跨篇对象和必要的源码名：直观叫法、在本项目中指什么、首次出现位置、源码名、别名 |
| `_衔接约定.md` | 流程之间的真实交接（阅读相邻不等于业务相邻）；机制的主讲篇与使用篇以及使用篇必须就地讲清什么；跨篇共用示例（名称、关键数值、含义、出现的篇）；冲突记录 |
| `_问题台账.md` | 编号、质量门、优先级（P0 错误事实、P1 结构或理解缺口、P2 局部表达）、篇、问题、源码依据、状态（open、fixed、needs_user_decision）、处理说明 |
| `_研读/NN.md` | 流程走查、机制卡、关键数据去向、追问与答案草稿、设计意图出处、核对材料、细节去向、讲述方案、成文中的补充研读与成文自查 |
| `_审读记录/NN.md` | 正文冻结版本、规则版本、独立读者标识与每阶段输入；阶段 A、B、C 的原答；初读障碍清单与处理；判定与核对依据；G4 抽查表；G3 组织检查逐项记录；G6 的问题与修改位置；六道门汇总；问题处理与复验；用户确认 |
| 99 | 源码基准与检查范围、全仓库入口去向、未展开内容、未确认项、与 project-map 的差异、测试与运行核对概览、各篇审读结果（含骨架复述与通读复述结论） |
