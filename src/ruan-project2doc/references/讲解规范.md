# 讲解规范

U-研读先据此写理解稿；U-成文把已经弄懂的内容组织给读者；U-审读按《质量门》复查。下文“缓存标杆、限流标杆、认证标杆、旧版反例、缓存示范”的来源见《定位与标杆》。例子说明写法，不代表目标项目必有这些技术。

## 1. 把流程和机制交织起来

流程讲解回答一件事怎样从开始走到结束，机制讲解回答某一步依赖的做法怎样起作用。链路篇按执行顺序组织，把机制放在用到的地方；专题篇按“问题 → 原理 → 实现 → 失败 → 取舍 → 使用点”组织。

合格写法见缓存示范：讲受保护请求装载用户时，接着解释为什么重新读资料、怎样逐级读缓存、失败时怎样继续。旧版反例第四节只说“从数据库或用户资料缓存装载当前用户”，再另列参数；动作虽存在，读者却无法跑通这个环节。

## 2. 核心机制回答七问

理解稿中按七问写成段落；正文可以按自然顺序合并，不必把七问当七个固定标题。

| 问题 | 必须讲清什么 | 合格示例或写法 | 不合格对照 |
|---|---|---|---|
| ① 解决什么问题 | 没有它，在什么情形下会出现什么坏结果 | 缓存示范：逐请求读用户资料会给所有受保护接口增加一次数据库读取，缓存减少这类重复读取 | 旧版反例只列“用户资料缓存”的名称和有效期，未说明为何需要它 |
| ② 靠什么原理 | 理解当前实现所需的最小原理 | 限流标杆：把请求时刻作为有序集合分数，删掉窗口外的记录，剩下的数量才是当前窗口内的请求数 | 旧版反例仅写“60 次 / 60 秒”，读者不知道窗口如何移动 |
| ③ 怎样实现 | 数据结构、关键步骤、组件怎样配合；能走查一次 | 缓存示范：先读本地；未命中再读共享缓存并回填；两边都没有才查库并写回 | 旧版反例给出几项缓存参数后指向第 07 篇，未交代本篇读取顺序 |
| ④ 为什么判断、怎样分支 | 判断保护什么条件，各种结果交给谁 | 缓存标杆：等待同一键的加载锁后再读，是因为前一个请求可能已填好缓存；必须先确认目标调用确实走这个加载方法 | 旧版反例说限流有“IP 门”，但没有展开满与未满如何分支 |
| ⑤ 失败怎样处理 | 校验失败、依赖错误、并发冲突的处理与代价 | 缓存示范：共享缓存读失败按未命中继续回源，代价是数据库承担更多读；写和失效失败分别核实 | 旧版反例的缓存段只有有效期数字，读者无法回答共享缓存不可用后发生什么 |
| ⑥ 为什么选它 | 与更简单或常见方案比较效果和代价 | 认证标杆：刷新凭据不轮换减少客户端更新负担，但泄漏后可在有效期内被重复使用 | 旧版反例只强调“不轮换原值、不新增刷新行”，没有连到备选方案和代价 |
| ⑦ 有什么局限 | 当前实现在哪些条件下不成立，保留影响理解的限制 | 缓存示范区分组件的加载锁与用户资料普通缓存调用，避免把组件能力说成所有调用都有的保证 | 旧版反例第四节在主文后堆多块尚待核实的容器细节，局限挤掉了机制本身 |

不要把“用了某组件”当作③的答案。写读、写、失效时分别找真实调用链；组件有某个方法，不等于当前使用点调用了它。适用条件、顺序和异常捕获范围都属于实现的一部分。

## 3. 流程回答六问

| 问题 | 写法 | 合格与不合格示例 |
|---|---|---|
| 起点 | 谁在什么场景发起，带着什么数据 | 认证标杆从用户提交凭据起步；旧版反例的参数串不能替代业务背景 |
| 校验 | 每项拦什么，为什么在这里 | 认证标杆结合连续失败场景讲先查锁的作用；旧版反例只把入口限流参数放在补充块，缺少该层如何拦截 |
| 处理 | 输入经过哪些动作，产生什么、传给谁 | 缓存示范把命中、回填、回源相连；旧版反例“从数据库或缓存装载”省略中间关系 |
| 判断 | 依据何值分叉，各分支去哪里 | 限流标杆把满额拒绝和未满写入分别走完；旧版反例“频率门通过后”没有说明这个通过条件如何得出 |
| 状态与落点 | 哪个状态变化，数据落到哪里 | 认证标杆说清刷新返回新访问凭据与原刷新凭据，并说明同一记录如何更新；不能像旧版反例的数字列举那样只记名称 |
| 接手 | 谁接着执行，是否换请求、线程、事务或进程 | 认证标杆区分失败请求、刷新请求和原请求重放；旧版反例把若干流程压成篇首“覆盖”长句，不能据此判断执行关系 |

决定分支、用于身份或权限或去重、写入持久存储、跨进程传递、参与最终结果的数据，都要追清“谁产生 → 怎样传到这里 → 谁使用或校验 → 何时失效”。从篇尾结果向前倒查一遍。外部提供的数据追到外部责任方与当前接收点即可，不编造外部实现。

## 4. 机制分级与跨篇够用讲解

《篇目规划》先定级。核心机制在主讲篇回答七问；支撑机制在用到的地方至少答①③⑤；细节一句带过或不写，去向记理解稿。链路篇用到其他篇主讲的核心机制，也必须在本篇答①③⑤，通常两到六段（默认值，可后改）。

**读者不翻其他篇，也应理解当前流程为什么这样走。** 讲清后再指向主讲篇，并说明那里增加哪些原理、使用点或方案比较。允许不同篇有够用的重叠；单篇内部不反复完整讲同一件事。

合格示例是缓存示范：身份装载处保留完整读取顺序和故障代价，专题篇再展开全部使用点。旧版反例把核心缓存降成有效期清单、把限流降成入口参数，即使各自写了“见第 NN 篇”，仍不合格。设备标签截断长度这类不改变主流程理解的细节则可留在理解稿；不能和缓存机制获得相同篇幅。

## 5. 原理讲到够理解实现和取舍

只补足当前实现需要的原理。删掉这段后，读者若无法解释后续步骤或备选差别，就保留；否则删减。

合格写法来自限流标杆：说明按时间删旧和计数为什么适合滑动窗口，以及把删旧、判断、写入放在同一原子操作里如何避免并发超放。旧版反例把原理全部转交别篇，读者只能记阈值；这属于讲得不足。技术历史、完整接口手册和与当前用途无关的特性也不必补入。

## 6. “为什么”分三种写

| 类型 | 如何写 | 例子与对照 |
|---|---|---|
| 效果型 | 经行为核实后直接说因果 | 缓存示范解释重新装载用户能让当前角色参与授权；旧版反例每遇到这类可核实因果就加【推导】，会打断阅读，不必照搬 |
| 对比型 | 说明换用另一做法的后果 | 缓存示范比较只有本地缓存和只有共享缓存的代价；旧版反例只列两级有效期，无法回答为什么不用单级 |
| 意图型 | 作者当初的选择、历史背景须有注释、提交或文档出处 | 认证标杆中的版本演进，只有目标项目有相应材料才可写成历史原因；旧版反例大量“这里不能推断”式限定也无须进主文，改写为已核实效果或把缺口移入 99 |

没有意图出处时不猜作者经历。少数对理解确有帮助的推断，说明推断及其前提；不能把猜测包装成已经实现的保证。理解稿记录分类和依据，正文不机械加标签。

## 7. 核验材料放在哪里

| 材料 | 默认位置 | 正文何时需要 |
|---|---|---|
| 文件路径与行号、方法签名 | 理解稿 | 读者需要立刻跳看的少数位置；篇尾通常仅用无行号的代码地图 |
| 测试覆盖与运行情况 | 理解稿、99 | 测试过程本身最适合解释行为时，讲成例子，不列测试名 |
| 迁移、配置差异、部署未确认项 | 理解稿、99 | 会改变主流程理解时简短说明；版本变化用“旧做法 → 问题 → 新做法” |
| 未确认项、与其他资料的冲突 | 理解稿、99 | 不说明就会建立错误模型时用一句话交代 |

旧版反例多次在正文声明“本次未运行”，并列出迁移号和带行号的证据索引；不再这样做。合格做法是保留认证标杆里“连续失败达到阈值”的走查，把测试类、执行记录和源码位置放进理解稿，正文用结果帮助理解。

## 8. 代码片段与篇幅

短片段只有在它比叙述更直接时才保留，例如关键配置、几行算法或状态转换。先用自然语言讲清，再给片段；删掉片段仍能读懂。每段一般不超过约 15 行，每篇一般不超过约 5 段，均为默认值、可后改。不贴整个类或方法，能用伪步骤或表格说清就优先采用。

合格写法取自限流标杆的算法走查：自然语言说明删旧、计数、拒绝或写入后，用几行伪步骤帮助复述。旧版反例虽少贴代码，却把组件名、参数和测试名当作解释；“没有长代码块”并不等于已经讲明白。

笔记与理解稿都不设篇幅上限或比例。每段都应服务理解：删重复、空话和无关核验细节，保留必要背景、原理、实现、例子和取舍。缓存示范把旧版反例的一句缓存参数展开成读写与故障说明，这是有效增加；旧版反例第四节补充块多于主文，却依旧答不出缓存怎样工作，属于主次失衡。判断依据是能否回答追问，不是字数少或多。
