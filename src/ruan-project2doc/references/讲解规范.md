# 讲解规范

本文件定义一篇笔记要讲什么、怎样组织：第一部分是组织规则（全篇、章节、小节、图、00、两类骨架、讲述方案），第二部分是讲解规则（流程与机制各自必须讲清的内容）。措辞规则见《表达规范》，各门怎样检查见《质量门》。读者、成功标准与讲解手法的来源说明见《定位与标杆》。

U-研读据此确定要弄懂并写进理解稿的内容；U-成文据此组织正文，以讲述方案为骨架；U-审读按《质量门》逐项复查。文中例子只说明写法，不代表目标项目有这些组件。

## 一、组织：怎样安排一篇笔记

总原则：**先流程，后重点；先骨架，后细节；先建立因果关系，再解释实现机制。**

### 1.1 三个层次各自的职责

| 层次 | 读者在这里得到什么 | 要求 |
|---|---|---|
| 全篇 | 这件事是干什么的、谁和什么参与、整体怎么走、文章按什么顺序展开 | 先建立可复述的整体模型，再进入细节 |
| 章节 | 现在处于整个过程的哪一步，这一步要产生什么 | 每个主要章节承担一个明确的问题或阶段；标题概括其全部内容 |
| 小节 | 这一步内部的具体过程，以及其中机制怎样运转 | 先走通过程，再展开细节；细节讲完接回主线 |

三个层次执行同一顺序：**先让读者知道“在做什么、结果是什么”，再回答“怎么做、为什么这样做”。** 术语和背景在读者第一次需要它的位置给出，不提前堆放。

### 1.2 篇首与全貌

正文开始处，要让第一次接触本项目的读者建立一个可以复述的模型。固定包含：

1. **一句话主线**：用具体场景或问题开头，说清这件事为谁解决什么问题。不写“本篇介绍某某模块”。
2. **本篇回答的问题**：三到五个具体问题，篇尾小结逐一回答。
3. **前置与关联**：建议先读哪篇；本篇用到的核心机制由哪篇主讲。
4. **全貌一节**（正文第一个一级章节），依次包含：
   - 业务背景：谁、在什么场景下、要得到什么结果，两三段以内；
   - 参与方与核心对象：系统内外有哪些参与者，哪些对象把各环节连起来；容易混淆的对象在这里区分开；
   - **全流程走查**：用一段连续的文字把这件事从发起到结果走完——谁先做什么、留下什么、下一步谁接手。可以先粗后细，但必须真实、连贯，读者据此就能复述；
   - 一张或一组全景图（规则见 1.7）；
   - 术语与落点表：只收理解本篇模型必需的叫法，说明“在本文指什么”，源码名单独一列；
   - 一个贯穿全篇的示例：具体的人或对象、编号、时刻、数字（规则见 2.8）。

**先建立整体，不等于画一张塞满细节的大图。** 全貌必须能被直接复述；完整的失败清单、全部配置项、全部字段不放在这里。但如果一条与默认配置有关的结论会改变读者对“这条流程能否走通”的判断（例如“默认配置下这条链会停在失败”），它必须出现在全貌或一个标题能找到的小节里，不能只藏在后文的补充块中。

### 1.3 组织方式按主题选择

不强制所有内容写成线性流程。一篇有一个主组织方式：

| 一篇的主题 | 主要组织方式 | 必须讲清的关系 |
|---|---|---|
| 一次业务或一次数据处理 | 按执行流程的大阶段 | 每阶段的输入、执行者、结果与交接；请求、线程、事务或进程在哪里改变 |
| 一个对象的建立、使用、变更、终止 | 按生命周期 | 谁在什么条件下触发；哪些操作可选、可重复、可互相替代；不是每次都依次发生 |
| 一组部件或职责的协作 | 按职责与边界 | 谁调用谁、交换什么、状态由谁管理；依赖关系不等于时间顺序 |
| 一个横切机制（专题篇） | 问题 → 原理 → 实现 → 失败 → 取舍 → 使用点 | 哪些能力由机制提供、哪些由使用方决定；适用与失败的范围 |

局部换一种方式时，在切换处用一句话说明关系，例如“下面是凭据已经建立之后，两种各自独立触发的处理”。**不能只因为代码属于同一模块、接口前缀相同，就把管理动作、查询接口、初始化和异常恢复与业务步骤编成同一串步骤。**

### 1.4 内容类别决定位置

| 内容 | 位置与层级 | 不允许 |
|---|---|---|
| 主流程的必经步骤 | 主要章节的主干，按真实顺序 | — |
| 条件分支与判断 | 所属步骤内部，和主路径同样清楚，各分支的去向写明 | 省略；或升格成与阶段并列的章节（除非分支本身就是主题） |
| 被多处共用的横切机制 | 在第一个需要它的使用点给够用讲解；完整讲解放主讲篇 | 在流程开始之前集中罗列全部机制和门禁 |
| 独立触发的操作（重发、轮换、撤销、重放、人工恢复等） | 集中成独立章节，先说明触发条件，以及它和主流程对象的关系 | 伪装成主链的下一步；与必经步骤混编成一条编号链 |
| 旁路与辅助面（只读查询、配置管理、其他入口） | 独立章节，放在主线之后；开头一句说明它和主线的关系 | 插在主线中段打断阅读（除非理解当前步骤确实需要它） |
| 异常与失败出口 | 影响当前步骤理解的就地讲；完整的失败清单放在该步骤之后 | 在正常流程之前集中展开；整篇零散分布 |
| 默认配置与当前限制 | 改变全篇结论的，进全貌或独立小节；局部的，紧邻相关步骤 | 只出现在补充块或 99 里 |
| 实现细节（字段、格式、算法内部） | 读者需要它才能理解当前动作时，放在该步骤的下级 | 以细节开篇；与主线同权 |
| 测试证据、版本演进、核验过程、源码位置 | 理解稿与 99；正文只保留影响理解的结论 | 作为正文内容 |

### 1.5 章节与标题

**核心标准：读者通过标题能看懂整体脉络，通过正文能理解执行过程，通过逐层展开能深入掌握具体实现。** 所有篇目的每个章节都必须满足。

**每个章节先建立清晰、完整的逻辑主干，再围绕主干逐层展开技术实现细节。** 主干负责讲清执行流程、步骤之间的关系和因果逻辑；实现细节负责解释每一步怎样实现、为什么这样设计。主干、子流程、技术实现和补充说明不能全部平铺在同一层级，要按它们真实的逻辑从属关系组织。

章节规则：

1. **同级同依据**：同级章节使用同一种划分依据（阶段、对象、职责或机制）；换依据时要有上位分组或一句清楚的说明。
2. **节首交代位置**：每个主要章节开头用一两句话说明读者现在在哪、已经拿到了什么、这一节要产生什么。纯结构主题说明本节解释哪类职责或关系。写成自然的句子，不机械套用“输入／处理／输出”标签。
3. **多层级递进拆解**：一个章节可以拆成 3.1、3.2；其中某一步内容复杂，再拆成 3.1.1、3.1.2；必要时继续细化。不预设固定的层级深度，层级跟着内容的逻辑从属关系走——子流程从属于它所在的步骤，技术实现从属于它所解释的动作，补充说明从属于它所补充的内容。
4. **层级由内容决定，不为排版强行拆分**：有独立逻辑关系的内容（一个子流程、一个机制的内部、一类独立的处理）使用子标题；同一逻辑下的简单并列细节用列表或段落表达，不为了显得有层次而拆出只有一两句话的小节。
5. **细节放在它所解释的步骤下面**：实现细节紧跟它解释的那一步，在该步骤之下按需要逐层展开。不为了简化结构删减必要的实现细节，也不把全部细节集中堆放在章节末尾。
6. **深入内容出现的时机**：锁、哈希、事务、并发、异常这类内容，放在读者已经知道这一步的正常过程之后；讲完说明此时的结果，以及下一步由谁接手。
7. **复杂子流程单独建骨架。** 满足任一条件即算复杂：跨两个以上参与方或执行体；含三步以上有先后依赖的动作；涉及多份记录的状态变化；它的产物是后续章节的输入。做法：先用一小段把子流程走完（谁 → 做什么 → 产生什么 → 交给谁），再分点展开校验、写入、并发与失败；结束处说明留下的状态和接手者。
8. 层级不断加深以致掩盖主线时，重组章节职责或拆出专题，而不是继续加标题。

标题规则：

1. **每一级标题承载逻辑职责**：准确说明这一部分在整体执行流程或技术机制中的作用，概括从它到下一个同级标题之间的全部主要内容。不随意摘取其中一个技术细节充当标题。
2. 一节包含多个并列内容时，用它们共同的上位概念命名，不挑其中一个局部结论代替整节。
3. 大标题范围大，小标题逐级收窄；小标题同样概括自己下面的全部内容，不退化成一句正文结论。
4. 优先用“对象 + 行为／流程／状态／机制”命名；不用具体实现手段充当上位主题；不用数量充当标题的主体（“五个状态、四个动作”）。
5. 慎用“必须”“真正”“关键是”这类推销式句式；重要结论放在正文里加粗或用提示块。
6. **目录检验**：只读一至三级标题，应能恢复文章的整体结构和执行过程（或主题结构）。如果目录读起来像一串知识点、结论或数量，就重新调整标题体系。
7. 先看正文实际包含什么，再命名标题；不先想好标题再让正文迁就。

### 1.6 小节内部：主干、深入、边界

| 层 | 是什么 | 怎样呈现 |
|---|---|---|
| 主干 | 执行流程、步骤之间的关系与因果逻辑：决定主要结果的动作、关键分支、不可省的前提 | 正文段落，单独读就是完整的过程 |
| 深入 | 每一步怎样实现、为什么这样设计：结构、顺序、机制内部 | 紧跟所解释的步骤，用下级标题或引导段展开，可以多层递进，讲完接回结果 |
| 边界 | 次要的失败与并发细节、设计取舍的补充、版本演进、当前局限的细节 | 紧跟相关步骤的补充块，使用稳定标签：异常情况、并发情况、设计取舍、版本演进、当前局限 |

纪律：

1. **折叠检验**：把深入小节和边界补充块遮住，剩下的文字必须仍然是完整、连贯、正确的过程描述。不满足，就把必要内容提回主干，或补一句承接。
2. **补充块只放可以跳过的内容。** 任何会改变“这条流程能否走通、结果是什么”的事实——默认配置下的停点、未接通的外部依赖、失败时整笔回滚——属于主干或独立小节。
3. 深入内容是讲解的主体：有独立逻辑关系的用下级标题承载，同一逻辑下的简单并列细节用列表或段落；都不放进补充块，也不集中堆到章节末尾。
4. 补充块紧跟它所补充的步骤；块里出现的名词，紧邻正文已经解释过，否则在块内就地补一句。
5. 正常流程与极端情况的分量通过层级体现：并发竞态、依赖故障、部分失败可以写得详细，但在结构上不与正常流程平起平坐。
6. 密度提示（默认值，可后改）：补充块平均每 20 行超过一个，或某一节补充块的字数多于主干时，检查主线是否被切碎、主次是否倒置。
7. 同一结论不反复强调；多轮补充之后重新检查能否精简。

**按内容的性质选择 Markdown 表达形式**，让执行步骤、技术细节、约束条件和补充说明一眼可辨：

| 内容 | 适合的形式 |
|---|---|
| 逻辑主干、子流程、机制内部 | 多级标题；标题层级表示逻辑从属关系 |
| 有先后顺序的执行步骤 | 有序列表 |
| 同一逻辑下的并列细节、条件、字段 | 无序列表；项目多或需要逐项对照时用表格 |
| 对照、状态转换、数据对应关系 | 表格，并在表外用一句话说明怎样读 |
| 约束条件与补充说明 | 引用块加稳定标签 |
| 关键结论 | 加粗或提示块 |
| 很长但可以跳过的清单 | 必要时使用 HTML 标签（如折叠块） |

形式服务于辨认，不为排版堆砌：同一种性质的内容全篇用同一种形式；不用表格或列表代替对过程的讲解。

### 1.7 图

按要回答的问题选图：架构图表达组成与依赖，流程图表达动作与条件分支，时序图表达跨参与方的往返，状态图表达生命周期。不要求每篇集齐图种。

1. **全景图画什么**：主要参与者或执行体、主要阶段、关键结果、必要分支。不放字段值、错误码、配置键、SQL、表名清单。承载语义的关键数字可以保留（如“5 分钟内有效”）。复杂的局部另画细图，不让一张图同时充当接口目录、字段清单和失败清单。
2. **关系类型与画法一致**：同一次执行内的先后、条件分支、并行或独立触发的活动、独立检查，各用可以区分的画法。同一张图不用同一种边同时表示执行先后、调用、数据交接和依赖；必要处在图上注明边的含义。
3. **另一次执行要标出来**：“之后的每个请求”“对端随时发来的回执”“回调”“人工重放”“定时任务”不属于当前这次执行，要在图上标明，不能让读者读成主链的下一步。跨参与方有多次往返时，优先用带参与方的时序图。
4. **图例与图一致**：图里没有判断节点，就不说“菱形是条件分支”；没有虚线，就不说“虚线是失败出口”。
5. **修图优先于补说明**：如果必须靠一段文字才能说清“图上相接的两步其实不是先后”“这一格其实是另一次执行”，说明图需要改——调整布局、拆图，或在图上加注记。不允许在图后附一段通用的读图说明来代替改图。
6. 当前实现、模拟实现与概念示意不画成同一条真实调用路径。
7. 有可用渲染器时实际渲染修改过的图并检查可读性；没有时如实记录人工做了哪些语法与关系核对。

### 1.8 00 总览

00 是读者在读各篇之前和之间使用的系统地图，内容为：

1. 系统解决什么问题：谁在用、处理什么业务对象、解决什么实际问题；
2. 系统由什么组成：一张架构图，说明应用、存储、外部系统之间的关系；
3. 一件事怎样流过系统：一两条代表性主线，说明数据从哪里进入、怎样变化、最后交给谁；
4. 核心机制一览：每个机制一两句话说明解决什么问题，注明主讲篇；
5. 推荐阅读路线与篇目表；
6. 易混淆术语。

要求：

- **规划阶段就要达到最低可用**：第 1、2、5 项，以及第 3 项至少一条主线的文字走查（图可以后补），随规划一起交用户确认。第 4、6 项随各篇补充。
- 每篇成文完成时，把本篇已核实、属于 00 的内容（主线简述、机制一览、易混术语）补进 00，只动与本篇有关的部分。
- 不留空节、“以后回填”的占位说明或未兑现的承诺。尚未核实的内容明确写“待研读后补充”，或暂不设该节。
- 三种关系不混在一张图里：组成与依赖用架构图；数据或状态怎样走用主线图；先读哪篇用篇目表说明。用篇号作图时，先声明箭头表示阅读接续还是依赖。
- 入口清点、配置穷举、核对口径不放在 00，归 99。

### 1.9 两类篇的骨架

骨架可以按内容调整，不是填空表。

**链路篇**

```text
# NN · <对象与过程>

> 本篇回答：<3–5 个具体问题，篇尾逐一回答>
> 前置与关联：<建议先读哪篇；本篇用到的核心机制由哪篇主讲>

<一句话主线>

## 一、全貌
   业务背景；参与方与核心对象；全流程走查；全景图；术语与落点；贯穿示例
## 二…N、<主体章节，按讲述方案确定的组织方式>
   节首：现在在哪、已拿到什么、这一节产生什么
   主干 → 深入（下级标题，可按内容继续拆成 N.1、N.1.1）→ 边界（补充块）
## <独立触发的操作、旁路与辅助面>（需要时，各自成章）
## 设计取舍与局限（可选：把分散的取舍连成整体）
## 本篇小结      逐一回答篇首问题；说明留下什么结果、谁接着处理
## 代码地图      关键文件或类及其职责，不写行号
```

**机制专题篇**

```text
# NN · <机制名>：<它解决的问题>

> 本篇回答：<3–5 个具体问题>
> 使用它的流程：<相关链路篇>

## 一、问题起点      没有它会怎样；哪些流程共同需要它
## 二、需要先知道的原理（够用即止）
```

### 1.10 讲述方案

**讲述方案是研读交给成文的结构设计**，写在理解稿里（《生产流程与交接物》），只在这一处维护。成文以它为骨架，审读对照它检查组织。

```markdown
## 讲述方案

组织方式与理由：<按执行流程 / 按生命周期 / 按职责与边界 / 按机制；一句话说明为什么>
读者先要建立的模型：<参与方、核心对象、它们的关系>
全流程走查：<用一段话把这件事从发起到结果讲完，成文时用于全貌一节>
贯穿示例：<贯穿全篇的人、对象、编号与关键数字；或说明本篇不需要>
哪些内容不是同一次执行：<独立请求、回调、定时任务、管理操作、后续流程，各是什么>

| 章节（暂定标题） | 本节回答什么 | 读者进入本节时已经知道什么 | 本节产物，与前后节的关系 | 深入与边界内容放在哪里 |
|---|---|---|---|---|
| …… | …… | 上一步的产物 / 独立触发 / 共同依赖 | …… | 主干就地讲 / 下级小节 / 补充块 / 留给主讲篇或 99 |

复杂子流程：<只为确有多参与方、多状态或明显嵌套的部分，列出内部步骤和出口；没有就写“无”>
```

要求：

- 它把已经核实的内容**组织给读者**，不复制机制卡，不逐条抄事实。
- 章节的划分与顺序，以“读者先建立什么、再理解什么”为准，不以素材在理解稿里的排列顺序为准。
- “全流程走查”写不出来，说明研读还没有完成。
- 成文时可以按实际内容调整标题、合并或拆分章节，但要同步更新讲述方案，并在成文自查里记录调整了什么。

### 1.11 组织问题的正反例

例子只说明写法；来源见《定位与标杆》。

| 问题 | 例子 | 说明 |
|---|---|---|
| 主流程的第一步是配置停点 | 登录流程第一个编号步骤是“先看默认配置下的停点：模式为 `DISABLED` 时返回 503”，读者还没有看到登录全貌 | 改变全篇结论的配置属于全貌或独立小节；流程第一步应建立整体 |
| 小节从字段和错误码开讲 | 标题“登记一台工位，四组东西在同一个事务里写完”，随即集中讲版本号、令牌长度、哈希、正则和唯一键冲突码，没有先走通一次登记 | 先走通过程，再逐层展开字段与错误码 |
| 独立执行画成一条链 | 换料、结束、更正、作废是四次各自独立的命令，图上是一条实线序列 | 独立触发要标出来，不能读成主链的下一步 |
| 改变全篇结论的事实埋在补充块 | “**异常情况**：默认配置下，一次完整的产出发布实际走不到成功，它会一次次重试，最后停在失败” | 这类事实属于主干或独立小节 |
| 数量声明没有清单 | 写了“七条本地规则”，全篇没有列出 | 数量声明配清单，数目与清单一致 |

正面做法：篇首用三个问题各配一个失败场景，全篇按这三个问题展开；节首一句“这一节只做一件事：把一条消息变成一行能查、能重发、不会被当成新消息的回执。业务办没办，这个阶段还完全没开始”；全貌声明五段各自独立执行，之后五个章节逐一对应。

## 二、讲解：一篇笔记必须讲清什么

### 2.1 两种讲解单元

一篇笔记由两种讲解交织而成：

- **流程讲解**：一件事从开始到结束经过哪些环节，数据怎样流动、状态怎样变化；
- **机制讲解**：流程中某个环节依赖的一套做法怎样工作、为什么这样设计。

流程是骨架，机制讲解放在它被用到的那一步里。

### 2.2 流程六问

| 问题 | 必须讲清什么 |
|---|---|
| 起点 | 谁、在什么场景下发起，带着什么数据来 |
| 校验 | 经过哪些校验，每项拦什么情况，为什么放在这个位置 |
| 处理 | 经过哪些环节，每个环节做什么、产生什么、交给下一步什么 |
| 判断 | 在哪里分叉，依据什么数据判断，各分支去哪里 |
| 状态与落点 | 哪些状态被改变，数据最终写到哪里 |
| 接手 | 谁接着处理；是同一次执行，还是另一次（另一个请求、线程、事务或进程） |

### 2.3 机制七问

| # | 问题 | 合格的样子 | 不合格的样子 |
|---|---|---|---|
| ① | 它解决什么问题 | 说出没有它时，在什么具体情形下出现什么坏结果 | “为了提高性能” |
| ② | 靠什么原理起作用 | 讲到足以理解当前实现的最小原理 | 只写组件或算法的名字 |
| ③ | 本项目怎样实现 | 结构、关键步骤的顺序、参与者怎样配合；给一个能在脑中跑一遍的小场景 | 只列组件名和参数值 |
| ④ | 关键判断与分支 | 每个判断保护什么条件，不同结果各去哪里 | “加锁后进行双重检查” |
| ⑤ | 失败时怎样处理 | 校验不过、依赖出错、并发冲突时，谁处理、留下什么、调用方看到什么、代价是什么 | 不写，或只写“有异常处理” |
| ⑥ | 为什么这样设计 | 与更简单或常见的做法相比，效果和代价各是什么 | 不写，或写成没有依据的意图 |
| ⑦ | 有什么局限 | 在什么条件下不起作用或会出错 | 把所有理论风险列一遍 |

七问是内容要求，不是七个固定标题。确实不适用的写明原因；没查清不能写成不适用。**组件有某种能力，不等于当前使用点走了这条路径**：读、写、失效这类操作，要沿真实调用点分别确认配置、注册、调用分支、事务与异常捕获范围。

### 2.4 关键数据

决定分支、用于身份或权限或去重、写入持久存储、跨组件传递、参与最终结果的数据，都要讲清：谁创建 → 保存在哪 → 怎样传到这里 → 谁读取或校验 → 何时改变或失效。外部提供的数据追到责任方与当前接收点即可，不猜外部实现。写完流程后从结果向前倒查一遍。

多份记录容易混淆时，先说明它们各代表什么，再给必要的表名、关键字段与关联关系。例如“一次登录尝试”“本地员工绑定”“已建立的会话”是三样不同的东西，不能统称“一行身份记录”。

下面这些实现细节在影响理解时必须保留：创建与使用发生在不同请求时，数据靠什么关联；哪些写入在同一事务内，失败时哪些会回滚、哪些外部副作用不会；状态迁移由谁在什么条件下触发；并发时锁住什么对象、解决什么竞争；同名概念是否指不同对象。

### 2.5 机制分级与跨篇够用讲解

| 级别 | 判据（满足任一） | 讲解要求 |
|---|---|---|
| 核心 | 承担安全、一致性、可靠性或性能等关键质量目标；被两条以上主流程依赖；容易被直觉误解；用户点名 | 在主讲篇完整回答七问；在其他用到它的篇给够用讲解 |
| 支撑 | 在流程中有独立作用，但主要服务一两处 | 在用到的地方至少回答①③⑤ |
| 细节 | 不改变读者对流程或机制的理解 | 一句带过或不写，去向记在理解稿 |

**够用讲解**：读者不翻其他篇，也应理解当前流程为什么这样走。链路篇用到别篇主讲的核心机制时，在用到的那一步回答①（在这条流程里它解决什么）、③（在这条流程里它怎样工作）、⑤（在这条流程里失败会怎样），再用一句话指向主讲篇，说明那里还会讲什么。不允许只给名称、参数或数字再写“见第 NN 篇”。不同篇的够用讲解可以重叠；完整讲解只在主讲篇。

“两条以上”是默认值，可后改。不得为省篇幅把用户关心的机制降级。

### 2.6 通用原理讲到哪里

讲到足以理解本项目为什么这样用、和备选做法差在哪为止。检验方法：把这段原理删掉，读者是否还能理解后面的实现与取舍？能，说明多余；不能，说明必要。技术历史、完整接口手册、与当前用途无关的特性不讲。

### 2.7 “为什么”的三种写法

| 类型 | 例子 | 写法 |
|---|---|---|
| 效果型：这样做带来什么效果、避免什么问题 | “先检查锁再比对密码，已被锁定的来源不会再消耗一次密码计算” | 直接陈述。它是可以从行为验证的因果 |
| 对比型：换成另一种做法会怎样 | “只用本机缓存，多个实例各存一份，一个实例改了角色，其他实例不知道” | 直接陈述 |
| 意图型：作者当初为什么选它、在什么背景下引入 | “这个限制是某次事故后加上的” | 有注释、提交记录或项目文档作出处才写；没有出处就改写成效果型或对比型 |

理解稿记录每个解释属于哪一类及其依据；正文不贴分类标签，也不写“这是效果型解释，不代表作者意图”这类说明。

### 2.8 事实、原理与示例要分清

正文里有三种性质不同的陈述，读者必须分得出来：

| 陈述对象 | 可以怎样写 | 不可以怎样写 |
|---|---|---|
| 当前项目的行为 | 有源码和实际调用依据，写明成立条件 | 把未接通的适配器、默认关闭的功能、其他路径的能力写成当前保证 |
| 通用原理或协议的标准做法 | 明确这是理解项目所需的背景，再与当前实现分别对应 | 把标准的完整流程补画成当前实现 |
| 教学示例 | 用虚构的人物、编号、数值走查已核实的规则，标明“假设”“示意” | 把示例值写成生产参数，把模拟运行写成真实实测 |

**教学示例是被鼓励的。** 用“张三登录车间系统”这样的假设场景帮助读者建立认知，比回避举例更好。项目没有接通某项外部能力时，仍然可以用概念场景解释它的职责，只需先说明这是示例，并明确指出当前实现实际停在哪里。不能到篇尾才补一句“实际没实现”。

涉及标准协议或框架行为、而仓内材料不能确认时，查阅与所用版本对应的官方资料，依据记在理解稿。不用未经核实的外部知识填补项目事实的缺口。

### 2.9 什么不进正文

| 内容 | 去处 | 什么时候可以进正文 |
|---|---|---|
| 文件路径加行号、方法签名清单 | 理解稿；篇尾代码地图只列关键文件或类及其职责，不写行号 | 读者很可能要立刻跳过去看的一两处 |
| 测试覆盖与运行情况 | 理解稿、99 | 测试过程本身是解释某个行为的最好例子时，讲成例子，不列测试名 |
| 迁移号、版本号罗列 | 理解稿 | 版本演进能解释当前设计时，讲“旧做法 → 问题 → 新做法” |
| 未确认项、与其他资料的冲突 | 理解稿、99 | 不说明就会让读者建立错误模型时，用一句话交代 |
| 核验过程、来源编号、入口编号 | 理解稿、99 | 不进正文 |

准确性没有降低：这些材料都在，只是不以正文为载体。

### 2.10 代码片段与篇幅

代码片段只在它比叙述更直接时使用（关键配置、几行核心算法、状态转换）。先用自然语言讲清，再给片段；删掉片段正文仍能读懂。单段一般不超过约 15 行，每篇一般不超过约 5 段，均为默认值，可后改。

笔记与理解稿都不设篇幅上限或比例。每一段都应服务理解：删重复、空话和无关的核验细节；保留必要的背景、原理、过程、例子和取舍。
