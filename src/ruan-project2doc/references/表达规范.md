# 表达规范

成文时采用，审读第三轮逐项检查。来源是《定位与标杆》中的 B，按 1.5 设计压缩成下面十五条。精简只删重复、空话和无助理解的细节，不能删去讲清机制所需的背景与原理。

1. **把句子写完整。** 写出谁、对什么、做了什么、产生什么结果，避免只有方向或动作名。
2. 交代动作发生的时间、位置和执行者。把“调用后处理”改成哪个组件收到什么、接下来做什么。
3. 用简单、常见、直接的词。删去装饰性的“钉死、抓手、闭环”等措辞和没有新增信息的模板化转场；技术术语确有必要时保留。
4. 先讲实际发生的事，再补源码名。首次可用“直观叫法（原始名称）”，之后优先直观叫法；删掉代码名，句子仍应能读懂。
5. 术语第一次真正用到时就近解释。同一对象有多个叫法，先说明它们指同一个什么对象，不只并排列名。
6. 标题概括到下一个同级标题之前的全部主要内容。优先“对象 + 行为、流程、状态或机制”；避免用局部结论推销整节。只看目录也应能还原结构。
7. 主线与补充分层。补充紧跟对应内容，使用“异常情况、并发情况、设计取舍、版本演进、当前局限”；从属关系用标题或引用层级体现，不限制讲解下沉层数。
8. 声明 N 步、N 层后，正文逐项对应。子话题使用下级结构，不与已经声明的步骤争同级编号。
9. 异常、调用、数据流转写清承接者和结果。不要只说“冒泡、落到、交给”；继续说明谁收到后如何处理。
10. 区分同一次执行和不同次执行。重试、重放、异步交接、事务提交后的动作都显式交代；表格用次数、时刻或阶段列，不只靠行序暗示时序。
11. “等价、对应、就是”的两端保持同粒度。给机制命名或类比时描述实际作用；类比不合适就改成对象之间的普通关系。
12. 重要结论可加粗或使用提示块。每个一级节通常不超过约 3 处，默认值、可后改；不要靠换句式反复强调同一个结论。
13. 保留有助理解的小场景和具体数字。用户自己写的有效例子优先在原处优化；例子应解释规则，不能取代规则本身。
14. 修改直接落在原位置，最终正文保持连贯。删除“重新核验后、修正补充、此前有误”等修改过程痕迹；被否定的错误分支彻底移除。
15. 必要限定保留在对应的补充块或一句清楚的说明里。不要连续追加“但是、注意、严格来说”打断主线；影响主流程理解的条件不能藏到读者看不到的地方。

## 用同一内容比较

旧版反例第四节“从数据库或用户资料缓存装载当前用户”后紧跟有效期、错误结构、未确认容器行为和测试说明。各句可能有依据，但读者还没弄懂缓存怎样读就被带往旁枝。

缓存示范先说为什么每次请求都需要当前用户，再讲本地命中、共享缓存回填、回源和故障后果；并发条件放在紧邻的“并发情况”块里。它增加了必要解释，同时让主线更清楚。这是本规范所要求的表达改进。

最后用可用的“说人话”类 Skill 自检一次。若没有该能力，在审读记录中说明，并依据本文件人工检查；没有运行不能记成运行过。语气优化不得改变数字、条件、时序、失败行为或结论强度。
