# 概念定义（K 编号）与技术栈映射

**何时读本文件**：U-勘察、U-拆分、U-取证；任何步骤遇到下面这些概念时。正文和其他 references 里凡出现这些词，都以本文件为准。

示例统一使用通用场景（订单、支付、导入任务），**不代表任何项目的领域知识**。

## 附录 F　操作化定义

| ID | 概念 | 操作化定义 | 判定方法 / 产物 | 合格 ✓ / 不合格 ✗ |
|---|---|---|---|---|
| K01 | 入口 | 外部能触发本项目代码开始执行的位置。各技术栈的具体形态见下文附录 G | U-勘察产出入口清单，每个入口注明类型和源码位置 | ✓“`POST /orders`（`src/order/api.py#create`）” ✗“订单模块” |
| K02 | 可观测状态终点 | 链路结束时留下的一个结果，另一个观察者不读本链路代码也能独立检查它。可以是：持久化的记录或状态字段、写出的文件或对象、发出的消息或事件、返回给调用方的响应或返回值、界面上的稳定状态 | 能写出三项：“去哪里查 / 查什么 / 看到什么算到达” | ✓“`orders` 表出现一行 `status=paid`，并且 `order_paid` 事件已入队” ✗“支付处理完成” |
| K03 | 链路 | 从一个或多个入口出发，沿真实的调用、消息、定时扫描关系，走到第一个可观测终点为止的执行路径 | `_拆分方案.md` 每行写：起点入口、终点（按 K02 格式）、途经的跨系统交接 | ✗ 起点或终点只写模块名 |
| K04 | 关键链路（独立成篇的依据） | 对每条链路逐项判断，满足一项计 1 分：① 改变持久状态；② 跨进程或跨系统交接；③ 有显式的失败处理、重试或补偿；④ 产生用户可见结果；⑤ 被其他链路依赖（它的终点是别的链路的起点）；⑥ 用户在开工时点名为重点 | 打分记入 `_拆分方案.md`。**≥3 分**为独立成篇候选；**1–2 分**并入相关篇的补充块，或在 00 的“其他链路速览”中简述；**0 分**写进 00 的不覆盖表并说明原因。用户确认拆分方案时可以手动调整，调整记入 `_拆分方案.md` | ✓ 每条链路都有分数和逐项理由 ✗“这条比较重要” |
| K05 | 关键步骤 | 改变控制流、对象状态、持久状态、缓存、文件、安全上下文、事务边界、消息状态或用户可见结果的动作。附录 G 给出各技术栈的对应项 | 关键步骤覆盖矩阵（`问题清单.md` F01） | — |
| K06 | 关键数据 | 满足任一条即算：决定分支走向；用于身份、权限、幂等或去重；写入持久存储；跨进程或跨系统传递；参与计算最终结果 | 每个关键数据都能在事实摘要里填满四格：来源 → 传递 → 使用或校验 → 生命周期（创建、更新、失效） | ✓“`idempotency_key`：客户端生成 → 请求头传入 → 服务端以它为唯一键插入去重表 → 24 小时后过期” ✗“从请求中获取” |
| K07 | 关键结论（“重点”） | 满足任一条即算：决定后续分支或设计；读者容易凭直觉误解；被其他篇引用；与文档或旧版本的说法不同 | 用加粗或提示块标出；每个一级节最多 3 处（默认值，可后改）。超过就说明重点没有取舍 | ✗ 一段里有一半句子加粗 |
| K08 | “防的是什么” | 写法：“如果不做这一步，或者换成更简单的做法，会在【具体情形】下出现【具体坏结果】” | 两个方括号必须都填上具体内容 | ✓“如果不先锁定库存再扣款，两个并发请求可能都看到库存 1，结果超卖一件” ✗“为了保证可靠性” |
| K09 | 就地展开 | 在主流程的某一步内部，讲清这一步依赖的子机制 | ① 只讲理解当前步骤必需的部分；② 最多展开一层，更深的内容下沉到补充块，或写“详见某篇某节”；③ 展开结束后，下一段必须是主流程的下一个编号。检验：把展开部分整体折叠，主流程编号仍然连续，语义仍然连得上 | ✗ 展开以后接着讲另一个子机制，主流程编号断开 |
| K10 | 回到主线 | 补充块或展开段之后，读者能马上知道回到了第几步 | 下一段以主流程编号开头，或者第一句写明本步的动作 | ✗ 用“回到正题”这类空转场（R40） |

## 附录 G　各技术栈的入口、终点与关键步骤映射

下表只是**发现线索**，最终以目标项目的实际代码为准。识别不出类型时，退回两条通用定义：入口是外部能触发执行的地方（K01），终点是留下可独立检查结果的地方（K02）。

| 项目类型 | 典型入口 | 典型可观测终点 | “状态”主要指什么 | 发现线索（检索模式只是起点） |
|---|---|---|---|---|
| HTTP / RPC 服务端 | 路由与处理函数、过滤器或中间件、RPC 方法、启动钩子 | 数据库记录与状态字段、发出的消息、对象存储、HTTP 响应 | 持久化的行、缓存键、会话或令牌、事务边界 | 各框架的路由注解或注册表；反查写库、发消息、外部调用 |
| 消息 / 任务驱动服务 | 消费者、定时任务、工作线程、批处理入口 | 处理后写入的记录、下游消息、死信、任务状态 | 偏移量或确认、重试计数、幂等记录 | 订阅、监听、调度注册；反查确认与重投 |
| 前端单页应用 | 路由页面、用户操作处理函数、应用初始化、后台轮询 | 发出的请求、本地存储、界面上的稳定状态 | 全局状态仓库、本地缓存、表单状态 | 路由表、状态仓库定义、请求封装层 |
| 移动客户端 | 页面或导航入口、后台任务、推送回调、应用启动 | 本地数据库、发出的请求、通知、界面状态 | 本地持久化、同步游标、令牌 | 清单文件中的组件注册、导航图、后台任务注册 |
| 数据 / 机器学习管道 | 管道或作业入口、调度定义、触发器 | 输出的表、文件或模型产物、指标记录 | 中间产物、检查点、分区或水位 | 作业定义、调度配置、读写数据集的调用 |
| 命令行工具 | 命令与子命令的注册点、主函数 | 写出的文件、标准输出与退出码、外部调用 | 配置文件、本地缓存、进程退出状态 | 参数解析器的注册点 |
| 库 / SDK | 对外公开的 API（导出的函数、类、方法） | 返回值、抛出的错误、回调、对传入对象的修改 | 实例内部状态、全局注册表 | 导出清单、公开接口文档、测试中的调用方式 |
| 多端或单仓多项目 | 各子项目各自的入口 | 跨端交接点（接口契约、共享存储、消息） | 跨端约定的状态与契约 | 按子项目分别套用上面各行，再找跨端交接 |

**库 / SDK 的链路**按“公开 API → 返回值或副作用”划分；全景图和关键步骤矩阵照样适用。

**关键步骤（K05）在不同技术栈里的对应物**，按需取用：

- 服务端：请求入口、过滤器与鉴权、参数校验、业务调用、条件分支、状态机、数据库与中间件访问、事务提交或回滚、提交后回调、线程切换、重试与幂等、文件变化、异常转换、补偿清理、客户端的后续处理；
- 前端与移动端：路由守卫、用户操作处理、状态仓库变更、请求与响应处理、本地持久化、错误提示、重试与离线队列；
- 数据管道：读入、校验与清洗、转换、写出、检查点与水位、失败重跑；
- 命令行与库：参数解析、前置校验、核心计算、副作用（写文件、网络调用）、错误与退出码、返回值。

**问题清单里出现的具体技术词换成通用说法**：F03 的“MySQL、Redis、MinIO、MQ”读作“任意两个以上的独立存储或系统”；F30 的“Controller、Consumer……”读作“本表第二列列出的全部入口类型，加上第三列列出的全部终点类型”；F08 的“Android 与后端”读作“任意两端之间的契约”。
