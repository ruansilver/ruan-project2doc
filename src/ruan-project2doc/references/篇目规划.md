# 篇目规划

U-规划读本文件，用 `_规划方案.md` 记录选择。先发现系统在做哪些事，再决定读者需要哪些篇；篇数和链路分数都不是目标。机制怎样分级见《讲解规范》的“机制分级与跨篇够用讲解”，组织方式的含义见同一文件的“组织方式按主题选择”。

## 1. 找出入口、终点和链路

- **入口**：外部能触发本项目代码开始执行的位置，例如一次用户操作、公开函数调用、消息到达、定时触发。写实际触发点，不只写模块名。
- **终点**：这次执行留下的、可以独立检查的结果，例如响应、返回值、持久记录、文件、下游消息、稳定的界面状态。写具体结果，不只写“处理完成”。
- **链路**：从一个或多个入口出发，沿真实的调用和交接关系，走到这样一个终点的执行路径。

先正向找入口，再从返回、写入和外部交接反向找终点，两边对照补漏。后台清理、订阅回调、定时任务、工作线程也是入口，都要登记去向。有 project-map 时借其主体流程作为候选，不直接采用其模块边界。

| 项目形态 | 入口线索 | 终点线索 | 关注的状态与关系 |
|---|---|---|---|
| HTTP / RPC 服务 | 路由、处理函数、中间件、启动钩子 | 响应、持久记录、消息、外部调用结果 | 身份、持久状态、事务、跨服务交接 |
| 消息或任务服务 | 订阅、监听、调度、批处理注册 | 结果记录、确认、下游消息、失败队列 | 重试、去重、任务状态 |
| 前端应用 | 路由、用户操作、初始化、轮询 | 页面稳定状态、请求、本地保存结果 | 表单、状态仓库、请求与响应 |
| 移动客户端 | 导航、推送回调、后台任务、启动 | 本地记录、界面、通知、请求 | 离线状态、同步游标、跨端契约 |
| 数据或模型管道 | 作业、调度定义、触发器 | 输出数据、文件、模型产物、指标 | 中间产物、检查点、水位、失败重跑 |
| 命令行工具 | 命令注册、参数解析、主函数 | 输出、退出码、文件、外部操作结果 | 参数、配置、执行副作用 |
| 库 / SDK | 导出函数、公开类和方法 | 返回值、错误、回调、传入对象变化 | 实例状态、注册表、调用契约 |
| 多端或单仓多项目 | 各子项目分别发现 | 子项目结果及跨端交接 | 接口、共享存储或消息约定 |

该表只帮助寻找线索，最终以目标项目的代码为准。无法归类时回到入口和终点的定义，不强行套某一技术栈。

## 2. 分数辅助筛选，不替代成篇判断

每条候选链路按六项各记 0 或 1 并写理由：改变持久状态；跨进程或跨系统交接；有失败处理、重试或补偿；产生用户可见结果；终点被其他链路依赖；用户点名。

默认参考（可后改）：3 分及以上是独立成篇的候选；1–2 分优先并入相关篇或在 00 简述；0 分登记为不展开并写原因。分数只辅助筛选：分数够但只有简单增删改查的链路可以合并；分数低但能解释重要机制的链路可以独立成篇；差别只在少量分支的链路按主题合并。所有入口的最终去向进 99。

## 3. 机制定级与主讲篇

按《讲解规范》的分级判据给每个机制定级，级别依据写进机制清单。每个核心机制有且只有一个主讲篇；这是完整讲解的安排，不限制其他篇提供够用讲解。

满足任一条件的核心机制单独成为机制专题篇：被多条链路使用，每处只讲够用部分会让读者始终看不到全貌；有较多需要独立讲解的原理或方案比较，放进任何一条链路都会长时间打断主线；用户点名。只被一条链路使用的核心机制，在该链路篇里就地完整讲。多个小机制属于同一主题时可以合成一篇。

## 4. 组织方式预判与读者负荷

- 为每篇预判组织方式（按执行流程、按生命周期、按职责与边界、按机制）和主要对象，写进篇目表；研读后可以修正，理由记在规划里。
- **读者负荷**：一篇的主体宜为“一条主线”或“一个对象的生命周期”。如果一篇要读者同时记住两套以上的状态机、三条以上互不依赖的流程，或清点大量并列的入口和命令，优先拆篇、拆出专题，或把其中一部分降为简述加去向。这是判断而不是硬限制，取舍写进规划。
- 篇数不追求多，也不为凑整齐而合并。

## 5. 阅读顺序与学习目标

阅读顺序通常是：先读一条最能代表系统的主链路，再读它依赖的机制专题，然后读其他链路。按读者需要调整，不按源码目录排序。每篇写三到五个“本篇回答”的具体问题（数量是默认值，可后改）。

## 6. 追问清单的设计

追问清单在规划时写成，研读时写答案草稿，审读时由独立读者作答。

**每篇必须包含：**

1. **一道整体复述题（必答）**：“不看笔记，说明这件事解决什么问题、由谁发起、按什么顺序经过哪些阶段、每个阶段留下什么、最后交给谁。”
2. **关键子流程复述题（必答，复杂篇一到两道）**：“把〈某个过程〉从开始到结束讲一遍，说清每一步谁对什么做了什么、结果是什么、失败由谁处理。”
3. **机制追问**，按五个层次：

| 层 | 问什么 | 通用例子 |
|---|---|---|
| L1 是什么 | 这个环节或机制做什么 | 这几步分别拦住什么情况？ |
| L2 怎样实现 | 结构、步骤、组件配合 | 一条记录怎样写入、读取、更新和失效？ |
| L3 为什么 | 判断、顺序和条件的作用 | 为什么先检查状态，再执行昂贵的操作？ |
| L4 出问题怎么办 | 校验、依赖、并发失败后的结果与代价 | 依赖不可用时，谁继续、谁拒绝、什么能力减弱？ |
| L5 为什么不用别的 | 备选做法与代价 | 只保留一层，或把两步合并，会有什么差别？ |

   每个核心机制 L1–L5 各至少一题；每个支撑机制至少 L2、L4 各一题；流程中每个关键判断至少一题 L3。跨篇使用的核心机制，题目只问本篇读者必须理解的部分。

4. **用户提出的问题**全部纳入。

**标记**：属于核心机制的题都标为核心题（跨篇使用的核心机制，只出本篇读者必须理解的那部分，同样标核心题）；整体复述题、子流程复述题和用户提出的问题标为必答。审读时核心题与必答题必须全部答得出且正确，其余题按比例（见《质量门》G1）。

**出题纪律：**

- 从读者要建立的理解出发，问结果和关系。题干不把正确的阶段名、对象关系或答案的结构写进去。
- “为什么不能……”“是否等于……”这类界限题，只用于读者确实容易混淆的地方，每篇一般不超过约 3 道（默认值，可后改），不用来凑层次覆盖。
- 一道题可以覆盖多个要求，不为凑数重复出题。

## 7. 规划的产物与确认

`_规划方案.md` 记录：链路候选及打分理由；机制清单、级别与主讲篇；篇目表（类型、标题、范围、组织方式预判与主要对象、不覆盖项及去向、阅读顺序）；每篇学习目标；追问清单；全仓库入口去向；确认记录。

同时产出规划期的 00、术语表初稿和衔接约定。规划期的 00 要达到《讲解规范》规定的最低可用：系统解决什么问题、系统由什么组成、推荐阅读路线与篇目表，以及至少一条主线的文字走查；不留空节和“以后回填”的占位。`_术语表.md` 约定叫法，`_衔接约定.md` 记录流程交接、主讲篇与使用篇的够用范围，以及跨篇共用的示例。

规划内容可以包含待研读核实的候选，但不能把候选写成已经确认的机制保证。

向用户展示篇目与阅读顺序、机制级别与主讲篇、组织方式预判、学习目标、追问清单、规划期的 00，以及用户重点落在哪里。**得到用户确认后**，记录日期和调整内容，才进入交接。已有本次有效授权可以按授权范围执行并如实记载，不伪造用户回答。

研读发现范围或关键认识变化时，先更新规划；涉及篇目或用户重点的实质调整，按授权范围确认后交 ruan-dev-skills 调整后续步骤。旧规划不能反过来限制源码结论。
