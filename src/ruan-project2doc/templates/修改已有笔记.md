# 修改已有笔记：{{仓库名}}

## 使用方法

在「三、用户追加区」新增一行要求（状态写“待处理”），然后对 AI 说“按修改提示词改笔记”。

- 目标篇可以留空：AI 会先列出受影响的篇目和理由，等你确认后再改。
- 类型可以留空：AI 会判断是“表达”“事实”还是“结构”。涉及事实的要求会先回源码核对，再改正文。
- 只改一篇、只涉及表达的要求，AI 可以直接改；涉及事实或多篇的，AI 会交给 ruan-dev-skills 规划成步骤，逐步执行。
- 你的要求和下面的固定规范冲突时，以你的要求为准，AI 会在变更记录里写明偏离了哪条规范。

## 一、固定规范区（项目无关，来自 ruan-project2doc 的 references，勿改）

### 1. 修改原则

1. **先核验，以当前实现为准**：涉及代码事实的改动，先回源码核对（C1）。
2. **只改当前问题**：附近的错误、重复可以一起处理，范围以“同一节”为限（C2、M05）。
3. **优先在原句上增强**：原位置能改，就不在旁边另起一套解释（M03）。
4. **正文不留修改痕迹**：不写“修正补充”“此前理解有误”，痕迹只写在本文件的变更记录（C14、M01）。
5. **清除被否定的错误分支**：用户否定过的内容，不换个形式留下来（M02）。
6. **做减法**：删掉错误、重复、打断主线的内容；每次修改都问一句有没有可以删减或合并的（C3、M07）。
7. **保留用户的解释**：你为帮助理解而写的解释和例子，只要没错、没造成明显重复，就保留，在原表达上优化（C4、M04）。
8. **小知识点不单独成篇或成节**：并到它第一次被用到的地方（M08）。
9. **看出反馈背后的知识缺口**：补充内容服务于当前问题，不借机扩展成无关主题（M06）。

### 2. 主线与补充

主流程优先；异常、版本、测试、限制、并发下沉一级，用固定标签（补充说明 / 版本差异 / 实现限制 / 并发情况 / 异常情况 / 测试证据 / 当前限制），紧跟它补充的步骤。补充块之后的下一句回到主流程的下一个动作。

### 3. 表达

句子写全“谁、对什么、做了什么、结果是什么”；流程句写明何时、在哪个阶段、谁执行。先说实际发生了什么，源码名只用来定位；首次用“直观叫法（原名）”，之后只用直观叫法。陌生用语按“白话 → 最短括注 → 首次稍作展开 → 别篇有主场仍要本句能读懂”的顺序处理。少用模板化转场和 AI 味词。

### 4. 标题

标题概括从它到下一个同级标题之前的全部内容；不用局部结论、金句、推销式说法当标题；只读目录就能还原执行流程。

### 5. 事实、推断与建议

不把推断、设计目标、尽力而为的行为写成确定事实；推断句末标【推导】，缺证据标【未确认】；测试证据只说测试实际断言到的范围。

### 6. 流程与术语

写清去向（谁发出、谁承接、结果）、时序（同一次还是不同次）、同一性（多个叫法是不是同一个东西）；“等价、就是”两边粒度一致。术语以 `_工作区/_术语表.md` 为准。

### 7. 关键数据追溯

关键数据追到真实来源：来源 → 传递 → 使用或校验 → 生命周期。外部系统和配置只写到“由谁提供、从哪里取得”。

### 8. 最终检查

每次修改后按 ID 执行附录 D（M01–M08）和受影响段落相关的附录 A 条目，结果写进变更记录。只写“已检查”视为没有执行。
